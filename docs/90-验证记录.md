## 320 GPU 锚点产物与门槛实测（2026-10-12）

- **产物**：从 `server/data/models/yolo26m_320.onnx` 截掉图内后处理（把 `/model.23/Concat_3_output_0` 提升为模型输出；412 节点、尾部算子 0）→ onnx2tf 转出 `yolo26m_320_anchor_float32.tflite`（78.0 MiB，输入 `[1,320,320,3]` / 输出 `[1,84,2100]`，455 算子，`CAST`/`GATHER`/`GATHER_ND`/`TILE`/`TOPK_V2`/`EXPAND_DIMS` 全 0）。
- **黄金样本与契约测试**：`golden/anchor-m320.{npy,kt}`（参考解码 person 0.9553 / 0.8817、class 56 0.6382）与 `AnchorGoldenFixture320Test`——锚点数 2100 与 640 的 8400 不同，专门守住解析器不依赖锚点数常量；Android 单测通过。
- **门槛实测**（真机 26048RP6AC / MT8910 / API 37，10 帧中位数）：320 档 LiteRT CPU 197.1（1 线程）/ 145.2（4）/ 139.1（8）/ 88.6（XNNPACK 2）/ 86.4（XNNPACK 4）/ 76.4（加速器 API CPU）/ **63.4（加速器 API CPU 关 XNNPACK，4 线程——本运行时最快 CPU 基线）**；GPU 加速器 **26.2**（FP16 27.6 / 纹理权重 25.8 / 关外部张量 25.6）→ **0.41×，按「≤ 同运行时、同精度 CPU 的 0.70×」达标**。同轮 640 对照：GPU 67.8 对 253.4（0.27×）。质量：GPU 档 person 2 个 / 最高分 0.965，与正式模型 0.967 一致。

## 协议版本闸门与服务端杂音归因（2026-10-12）

**起因**：生产服务每 2 小时出现约 700 次 `[WsAuth] auth-rejected reason=invalid-session`，需要查清来源并按 owner 要求让旧版本端点彻底出局。

- **归因方法**：远端三层链路把客户端 IP 抹平（见下条），日志无法定位来源。最终在统一服务本机 `:3000` 上按 pcap 抓一次被拒的 `/ws` 握手并解出掩码 WebSocket 帧，拿到客户端自称的身份。
- **来源**：三台 Windows 安装上的**旧版视觉推理节点驻留程序**，各自约每 10 秒重连一次。其 auth 帧为 `{"type":"auth","role":"windows-resident","apiKey":"XG-VisionGuard-2024","deviceId":…,"deviceName":"MS-KPVKXLBELRGE"|"P4"|"P1-13"}`，三个 deviceId 均不在生产设备注册表内。
- **判据**：服务端只认 `msg.token`（`authenticateNode` → `accountStore.authenticate(value.token)`），旧帧发的是 `apiKey` 字段，当前源码中不存在该字段，因此必然拒绝。即旧包使用 API Key 时代的协议，不是当前实现的问题。
- **闸门实现**：新增 `server/src/services/protocol.ts`。`/ws` 与 `/media/ws` 在鉴权前校验握手消息里的 `version`，不符或缺失即静默出局（关闭码 4001 `protocol mismatch`，**不回 `auth-result`**）；`/api` 前置 426 空响应闸门；旧端仍可访问登录与更新接口，保留自升级路径。各端在 WS 认证、媒体认证与 `/api` 请求中声明本端版本，控制台与 Web 相机取登录响应新增的 `version` 字段。
- **只报数量不刷屏**：出局按版本聚合，每 5 分钟最多输出一行 `[Protocol] legacy-protocol-dropped`（含 `servedVersion` 与版本分布）；单次尝试只留 `socket-open / first-frame / protocol-dropped / socket-close` 四行连接生命周期记录。
- **只约束部署实例**：闸门默认仅当 `NODE_ENV=production` 时启用，本地与测试实例放行所有版本，跑链路和 UI 检查无需对齐各端构建；`VISIONGUARD_PROTOCOL_GATE=1` 可在本地复现门禁，启动日志打印闸门状态。
- **测试**：`test/protocol-gate.test.ts` 覆盖「部署实例只服务本版」「本地实例全放行」「缺字段与旧版本按版本聚合计数」；`ws-auth-diagnostics.test.ts` 覆盖真实连接上的静默出局日志形态；`account.test.ts` 覆盖 HTTP 426 与登录入口不受闸门约束。三个 Android 模块、Windows 驻留与 WPF 均以 Release 编译通过。
- **未覆盖**：闸门尚未部署到线上，线上仍是 0.6.12 无闸门版本；三台机器的旧安装会继续刷日志，直到升到新包。

## 生产链路客户端 IP 丢失（2026-10-12 现场核查）

- **链路**：公网 `:443` → nginx `stream` 按 SNI 分流（`/etc/nginx/streams-enabled/novix-anytls.conf`，`web_https` → `127.0.0.1:9443`）→ `visionguard` vhost（TLS，`listen 127.0.0.1:9443`）→ `127.0.0.1:3000`。
- **后果**：`stream` 层未启用 `proxy_protocol`，内层 nginx 也未配置 `real_ip`，应用拿到的 `X-Real-IP` / `X-Forwarded-For` 恒为 `127.0.0.1`；按 IP 的限流键退化为回环地址，全部公网客户端共享同一限流桶，日志也无法按来源归因。
- **状态**：只读核查，未改配置。修法（`stream` 层加 `proxy_protocol` + 内层 `set_real_ip_from 127.0.0.1; real_ip_header proxy_protocol`）属共享基础设施，需与 `Server-infra` 协调并另行授权。

### 模拟器上的加速档位验证（2026-10-11，Google sdk_gphone64_x86_64 / API 36）

模拟器只用来验证**代码与 API 接线是否正确**，不作为性能依据（其 NNAPI 走软件实现、GPU 走 SwiftShader，方向与真机相反，文档前面已记）。

- **ONNX INT8 + NNAPI 被运行时直接拒绝**（四档全部同一原因）：`ORT_INVALID_ARGUMENT: The input/initializer of graph has unsupported quantized type, name: /model.6/m.0/cv2/act/Mul_output_0_QuantizeLinear type: 2`。`type: 2` 是 `uint8`——ORT 的 NNAPI 提供器不接受 `QUInt8` 激活。**同一台设备、同一份 `yolo26n_320` FP32 模型四档 NNAPI 全部正常工作**（143.8 / 135.8 / 166.3 / 148.7 ms），证明这不是模拟器缺 NNAPI，而是 INT8 图本身不被接受。也就是说 ONNX 这条线的「INT8 + NNAPI」组合基本可以判死，与设备无关。
- **LiteRT 加速器 CPU 档跑通**：`LiteRT · 加速器 API CPU` 中位 67.8 ms，比同运行时老入口的 CPU 1/4/8 线程（82.3 / 93.1 / 90.4 ms）更快。这证明 `CompiledModel` 的接线、CHW→NHWC 转换与张量名都正确。
- 首次运行时 accelerator CPU 档报 `Input tensor not found`，原因是无参的 `createInputBuffers()` / `getInputTensorType()` 在本构建里解析不到默认张量名；改用带签名与张量名的重载（`serving_default` / `images`）后通过。
- **LiteRT GPU 档在模拟器上 `Failed to compile model`**（两档），NPU 档报 `本机不支持 LiteRT 加速器 NPU（可用：GPU,CPU）`。GPU 的失败属模拟器渲染后端限制，不能推断真机；NPU 的不可用与「包里没有 MediaTek NPU dispatch 库」一致。
- 未覆盖：**真机（kpad2）读数仍然没有**；GPU 档在 Mali 上的实际可用性与耗时、NPU 是否需要厂商 dispatch 库，都待真机。

### 全矩阵读数与 GPU 分诊（2026-10-11 下午轮，Xiaomi 26048RP6AC / MT8910 / API 37）

三包全档位在真机跑完（A/B/C 各 4 模型 × 19 档，共 136 格）。读数口径：每档预热 2 帧、10 帧中位数；**每档附质量行**（person 数 / 最高分 / 最高框）。证据在 `.local/model-quant/accel-reports/combined-device-report.txt`（连同 `-2` 的重复轮）。

| 口径 | 搭配 | 依据 |
|---|---|---|
| **CPU 档最快** | **ONNX Runtime · CPU 4 线程 + `yolo26n_320_int8`** | 12 个模型里 CPU 4 线程全场最优；质量过关（person 2→2、最高分 0.881→0.951、中心漂移 0.002） |

### GPU 分诊：拒绝编译的真因是图内 int64 后处理（2026-10-11，Xiaomi 26048RP6AC / API 37）

同一台真机、同一构建，先用**平凡模型**判定"设备到底支不支持 GPU"，再读原生日志定位生产模型为什么不过。工具与证据在 `.local/model-quant/gpu-probe/`、`make-gpu-probe.py`、`accel-reports/probe-gpu2-logcat.txt`、`probe-all-bench.txt`。

- **设备与 GPU 代表本身可用**：9 算子的平凡卷积网（`probe_yoloish_fp32`：Conv×6 + Concatenation + Reshape + Transpose）在 **GPU 四档全部编译通过并出读数**——默认 2.5 ms、FP16 2.3 ms、纹理权重 2.9 ms、关外部张量 2.2 ms（10 帧中位数）。更小的 `probe_minimal` / `probe_tiny` 因 APK 打包器未把小文件纳入包内而未参与本轮，不影响这条判据。
- **生产模型被拒，原因是回退 CPU 的那 29 个算子**：原生日志逐条给出 `Following operations are not supported by GPU delegate`——`CAST: Tensor type(INT64)`、`GATHER: Only support 1D indices`、`GATHER_ND: Operation is not supported`、`RESHAPE/TILE: Tensor type(INT64)`，全部落在图内后处理 `wa/model.23/TopK/Tile/Expand`。分区统计：`yolo26n_320` FP32 为 **392 GPU + 29 CPU**，`_int8` 为 **3241 GPU + 29 CPU**，随后 `Failed to create compiled model: Failed to compile model`。
- **`CompiledModel` 没有 CPU 回退开关**：核对 `litert-api` 2.3.0 的 `CompiledModel$GpuOptions` 全部字段（precision / buffer storage / texture weights / external tensors / serialize / backend / priority / command-buffer 步数等），没有任何"允许混合分区"的选项；代表只接受**整图**编译。这解释了为什么之前"三种模型结构 × 四种 GPU 配置"12 组合全部失败，也说明**补全量化不能解决它**：int8 版同样带这 29 个 CPU 算子。
- **「完整量化」这条路当前工具链走不通（实测）**：`modify_model_interface` 对现有 `.tflite` 直接报 `ERROR: modify_model_interface called on a model without quant/dequant`——接口处没有量化边界，所以此前那份 `*_fullint8.tflite` 的 I/O 仍是 float32（与 float32 版逐算子相同）。`onnx2tf -oiqt -ett full_integer_quant` 走严格全整数量化，在 `StrictFullIntegerQuantizationError`（`conv.cc:353 input_channel % filter_input_channel != 0`，节点 1 CONV_2D）失败；要换 TF `TFLiteConverter` 路线需要 SavedModel，而本机 onnx2tf 的 `tf_converter` 后端缺 `tf_keras`。
- **结论**：这台设备上 GPU 档**无法用于当前模型**，按止损线停止继续投入；要救它需要**图结构侧**改动（让图尾没有 int64 与 Gather/TopK，例如改用不带图内 NMS 的锚点输出），不是补一个量化产物，属独立评估。判据与日志过滤方式已固定，换设备或换运行时可直接复用。

**顺带修掉一个真 bug**：LiteRT 老 `Interpreter` 入口（`LitertEngine`）在真机上**全部 CPU 档**报 `BufferUnderflowException`，栈指向 `readOutput`：`interpreter.run()` 后缓冲位置停在末尾，再按视图当前位置取值即越界读；现在读取前先 `rewind()`，并改为按元素数批量取。修复后同一构建的 LiteRT CPU 档全部正常出读数（`probe_yoloish_fp32` CPU 1/4/8 与 XNNPACK 2/4 线程分别 12.8 / 12.8 / 15.6 / 11.8 / 11.8 ms）。修复前那些"LiteRT CPU 档读数"在真机上其实一条都没取到。

### GPU 打通：截掉图内 NMS 后 GPU 档可编译（2026-10-11 续查，Xiaomi 26048RP6AC / API 37）

上一节把 GPU 判为不可用，本条是续查结果：**判死的结论对（补量化救不了），但成因定位要修正——真正的开关是图尾的 int64 后处理，不是量化。**

- **先排除"通路不同"这个解释**：本分发包里**没有任何 delegate 通路**（`org.tensorflow.lite.Interpreter$Options` 只有 `setNumThreads` / `setUseXNNPACK` / `setCancellable` / `setRuntime`，没有 `addDelegate`，包里也没有 delegate 类），所以平凡探针、截断模型与正式模型**走的是同一条 `CompiledModel` GPU 通路**。差异只能在图本身。
- **做过的图改动**：`nms=False` 导出**关不掉**（YOLO26 的 NMS 在头结构内部，导出后仍带 `TopK 2 / Expand 2`、输出仍是 `[1,300,6]`），于是直接在 ONNX 上截断——把 `/model.23/Concat_3_output_0`（`[1,84,2100]`，"框 + 分数"拼接张量）提升为模型输出、删掉它之后的全部节点。结果：**398 → 378 节点，`TopK/Gather/GatherND/Tile/Cast/Expand/NonMaxSuppression` 全为 0**。工具：`.local/model-quant/truncate-onnx-nms.py`。
- **关键对照（同一台设备、同一个 APK、同一轮测量）**：

| 模型 | 节点 | GPU 档结果 |
|---|---|---|
| `yolo26n_320`（原始，带图内 NMS） | 398 | **四档全部 `Failed to compile model`**（两次独立运行复现） |
| `yolo26n_320_anchor_float32`（截断） | 378 | **四档全部出读数**：默认 17.3 / FP16 20.3 / 纹理权重 14.4 / 关外部张量 15.0 ms |

- **那 29 个 CPU 分区算子不是判据**：截断模型的 GPU 分诊日志里**同样**是 `392 operations will run on the GPU, and the remaining 29 operations will run on the CPU`，却照样编译通过。所以此前"29 个不支持算子导致整图拒绝"的解释**不成立**；拒绝来自图尾那串 int64 计算图。
- **截断后语义未变**：截断模型在桌面 ONNX Runtime 上与正式模型同图同权重，同一张 `person-zidane.jpg` 上 person 分数 0.878 / 0.865（与正式模型 `[1,300,6]` 的检出一致），框中心 (31.2, 121.0)、宽高 (273.7, 248.0)。端侧要接它需要补一条 `[1,84,2100]` 的锚点解析 + NMS（`YoloOutputParser` 现有锚点分支是 `[1,84,N]` 的 YOLOv5u 形态，前 4 通道语义不同，不能直接套用）。
- **统一量化（int8 边界）在本任务里走不通，且原因可判定**：TF `TFLiteConverter` 的 `TFLITE_BUILTINS_INT8` 能出（2.4 MiB），但**类别分数被压成 0**——输出张量把"框坐标（校准集实测 -42~468）"与"类别分数（0~0.954）"放在同一个张量里按同一 scale 量化，scale≈2 时 0.878 的分数直接四舍五入到 0。这不是配置问题，是混量程张量的固有结果。
- **int16 激活路也走不通**：`EXPERIMENTAL_TFLITE_BUILTINS_ACTIVATIONS_INT16_WEIGHTS_INT8` 在转换期报 `RuntimeError: Quantized dimension for tensor property and quantization parameters do not match. Got 3 and 0`。
- **float16 路作废**：onnx2tf 的 float16 产物加载即失败 `transpose.cc:82 op_context.input->type != op_context.output->type (FLOAT32 != FLOAT16)`。
- **结论**：GPU**能打通**（截断图 + float32），但**不划算**——这台设备上 GPU 最快档 14.4 ms，而 CPU 档 `LiteRT · 加速器 API CPU + XNNPACK 4 线程` 同轮 7.4 ms、`ONNX · CPU 4 线程` 13.1 ms；加速门槛（≤ 同运行时 CPU 的 0.70×，即 ≤5.2 ms）无论按哪个基线都不达标。要用它还得付"双格式 + 新解析分支"的长期成本。
- 证据：`.local/model-quant/accel-reports/anchor-run-device-report.txt`、`anchor2-device-report.txt`、`anchor2-logcat.txt`；工具与产物在 `.local/model-quant/{truncate-onnx-nms.py,build-anchor-tflite.py,anchor-tflite/}`。

### 同精度对齐后的 GPU 定论与 int8 负优化（2026-10-11，640 三种尺寸）

此前 GPU 读数都是 FP32 截断图、CPU 参考是 ONNX int8 全图，**跨规格不可比**。本轮把两边对齐：同一张截断图分别出 FP32 与 int8 边界两版，同一轮测量。**结论表见[优化专题](32-推理框架与模型优化.md#各路线定论2026-10-11-定案真机-xiaomi-26048rp6ac-mt8910-api-37)**，这里只记原始读数与失败原文。

- **FP32 截断图 GPU 对同图 CPU**：`yolo26n_640` 23.7 / 39.8 ms、`yolo26s_640` 37.2 / 93.1 ms、`yolo26m_640` 67.5 / 255.7 ms。
- **int8 在这台 Mali 上对 GPU 是负优化**：同一张图 FP32 GPU 67.5 ms 对 int8 GPU 106.6 ms（慢 1.58 倍）；图内 378 处 QDQ 往返在 GPU 上成为额外开销，而 FP32 卷积能被 Mali 原生执行。
- **int8 边界还把分数压成 0**：输出张量把框坐标与类别分数放在一起（`yolo26m_640` 实测 scale 3.07 / zero -98，分数 0.878 量化后回到 0），质量行全为 `person 0 / 最高分 0.000`。
- **质量零损失**：FP32 截断图上 GPU 与 CPU 的质量行逐字节一致（`person 2 / 最高分 0.959 / 中心 0.262,0.485`）。
- **`LiteRT · 加速器 API CPU + XNNPACK 4 线程` 编译失败**（三个模型均报 `Failed to compile model`）——该档位本身不通，与模型无关。
- 端侧读取量化边界的能力同时补上：`TfliteQuantization` + 由 `gen-quant-table.py` 生成的参数表（`CompiledModel` 的 `TensorType` 不暴露 scale / zero point）。
- 证据：`.local/model-quant/accel-reports/aligned640-device-report.txt`、`aligned640-logcat.txt`。

### 锚点档解析对齐：通道配对是「0/2 一对 x、1/3 一对 y」（2026-10-11 续，Xiaomi 26048RP6AC / API 37）
接上一节：GPU 能编译之后，端侧解析必须与正式模型逐位对齐，否则会**静默出错框**（框错位但分数正常，从质量行看不出问题）。本轮把这个坑挖出来并锁死。

- **踩到的坑**：按「前 4 通道 = 中心宽高」读会得到荒谬框；按「= `x1,y1,x2,y2`」读也不对——实测锚点张量的通道是**按轴配对**的：0/2 为一对 x、1/3 为一对 y（全部 8400 个锚点上「通道 0 < 通道 2、通道 1 < 通道 3」成立），**不能照搬端到端档 `[1,300,6]` 的 `x1,y1,x2,y2` 顺序**。
- **怎么发现的**：拿同为 `[1,84,8400]` 的**正式模型**对照——`server/data/models/yolo26m_640.onnx` 在 `person-zidane.jpg` 上的原始输出前三行是
  `202.234 90.582 638.661 562.247 0.967 0`、`0.405 345.142 84.609 561.493 0.762 0`、`155.611 519.824 209.893 565.992 0.237 56`，
  与截断图的锚点张量**逐位相同**（后者的通道 0/1/2/3 恰为 202.23/90.58/638.66/562.25）。地图与数值都没有偏差，差别只在读法。
- **正确结果**：按配对读并把框映射回原图（661×508，letterbox 补上边 74）得到两个 person：`(208.87, 17.12) 450.75×487.00`、`(0.42, 279.96) 86.97×223.39`——一个占画面右侧的主体，一个是左边缘只露一部分的目标，与实例图一致（后者的漏检按口径不算错）。
- **锁定手段**：`.local/model-quant/make-anchor-golden.py` 从真实 `.tflite` 导出黄金样本（全张量校验和 + 6 个最高分锚点的完整 84 通道 + 参考解码结果），Kotlin 侧 `AnchorGoldenFixtureTest` 用同一份数值断言，端侧解析与参考实现从此同源。此前的读数用错了读法（框错位、分数正常），**旧质量行不作为判据**。
- **顺带确认**：`int8` 边界在 GPU 上是负优化这条结论不受影响（那是纯推理耗时，与解析无关）。
- 证据与工具：`.local/model-quant/{make-anchor-golden.py,golden/anchor-m640.npy,anchor-tflite/yolo26m_640_anchor_float32.tflite}`；端侧契约测试 `AnchorGoldenFixtureTest`（2 例）。

### 多路压力：正式档的在册上限（2026-10-11，640 输入，真实实例图）

部署是多个来源同时推理，单路中位数不能代表压力下的表现。本轮加多路测量（同一档位同时开 N 路、每路各建独立会话，每路 8 帧），用**真实人物实例图**作为输入（661×508，含两人；露得很少的那一个漏检不算错，只按主目标判定）。判定口径与建议值见[优化专题](32-推理框架与模型优化.md#门槛硬标准)。

**原始读数（`yolo26m_640`，单路中位 ms / 单路帧率）**

| 路数 | CPU4 · int8 全图（正式档） | GPU · 截断 FP32 | GPU · 截断 int8 |
|---|---|---|---|
| 2 | 156.8 / 6.4 ✓ | 68.1 / 14.7 ✓ | 145.9 / 6.9 ✓ |
| 4 | **545.3 / 1.8 ✗** | 64.2 / 15.6 ✓ | 151.3 / 6.6 ✓ |
| 8 | **1321.3 / 0.76 ✗** | 61.8 / 16.2 ✓ | 123.8 / 8.1 ✓ |
| 16 | **1376.8 / 0.73 ✗** | 61.3 / 16.3 ✓ | 112.3 / 8.9 ✓ |
| **32** | **1381.2 / 0.72 ✗** | **64.8 / 15.4 ✓** | **126.5 / 7.9 ✓** |

同轮另测（截断 FP32，用于确认上限随模型规模变化）：`yolo26n_640` CPU4 在 4 路 171.7 ms（5.8 ✓）、**8 路 303.2 ms（3.3 ✗）**，GPU 到 32 路仍 18.6 ms（53.8 ✓）；`yolo26n_320` CPU4 到 32 路仍 95.2 ms（10.5 ✓），GPU 13.5 ms（74 ✓）；`yolo26m_640` 截断 FP32 的 CPU4 连 2 路都只有 1.5 帧/秒。

- **在册上限（单路 ≥5 帧/秒）**：**CPU4 + int8 全图（正式档）= 2 路**（4 路起崩到 1.8 帧/秒）；**GPU = ≥32 路**（三个尺寸、两种精度都未触底，上限受内存而非算力约束）。
- 形状特征：GPU 的**单路延迟几乎不随路数变化**（m640 FP32：2→32 路 61–68 ms），实质是排队执行、单位时间吞吐恒定；CPU 反之——**总吞吐封顶在 3.8–4.9 帧/秒，单路延迟随路数线性恶化**（m640 从 2 路 157 ms 涨到 32 路 1381 ms）。
- **质量（同一张实例图）**：CPU 正式档 `person 2 / 最高分 0.967` 通过；GPU 截断 FP32 `person 2 / 0.965` 通过；**GPU 截断 int8 为 `person 1 / 最高分 300.456`，分数与框均异常**——与单路轮"int8 在 GPU 上慢 1.58 倍"互相印证。注意：本轮的框读数取自**读法错误的解析分支**（见上节），分数与检出数不受影响，但框位置不可用；修正后的同轮复测见[GPU 端到端：解析已接正式链路与真机复核](#gpu-端到端解析已接正式链路与真机复核2026-10-11-续xiaomi-26048rp6ac-api-37)。
- **误差提示**：CPU 用**全图 int8（自带 NMS）**、GPU 用**截断图 FP32（无 NMS）**，属跨图比较；同精度对齐数据显示截断图在 CPU 上比全图慢约一倍，故 CPU 那列对截断图偏乐观。另有抖动：2 路时 GPU int8 145.9 ms 与单路 106.6 ms 不一致，首轮含缓存/初始化开销，**只用 4 路及以上看趋势**。
- **端到端还缺一段**：GPU 侧测的是纯推理，端侧解码 + NMS 的开销未计入（该分支尚未实现）。
- 证据：`.local/model-quant/accel-reports/prod-sweep-20261011-190708.txt`、`parallel-sweep-20261011-183130.txt`、`parallel-sweep-20261011-183526.txt`、`parallel-sweep-20261011-183705.txt`；工具 `run-prod-sweep.ps1`、`run-stream-sweep.ps1`、`analyze-stream-limit.py`。

### NPU 定论（单独存档，后期有空再评估）

**结论：本机 NPU 在"不向厂商申请"的前提下无路可走**——驱动与运行时都在设备里、芯片也在 Google 支持名单上，缺的是"让第三方 app 用上它"的公开接口。

- **芯片标识要看清**（此前一轮结论有误，已纠正）：`ro.board.platform = mt6993`、`ro.soc.model = MT8910`、`ro.hardware = mt8910`；vendor 的 NPU 运行时按 `mt6993` 打包（`/vendor/lib64/mt6993/{libneuron_runtime.so,libneuron_adapter_mgvi.so,libneuron_wrapper.so}`），且 **MT6993 在 LiteRT 官方 MediaTek 支持列表内**。"型号不在支持列表"的旧说法不成立，依据（`ro.soc.model`）取错了字段。
- **卡点一：NNAPI 对第三方 app 只暴露参考实现**。ORT 日志 `GetCapability: number of partitions supported by NNAPI: 2`（432 节点只有 2 个下沉），执行侧 `compilation finished successfully on nnapi-reference`（Google 的 CPU 参考实现）；原因 `Failed to read /vendor/etc/nnapi_extensions_app_allowlist ; No app allowlisted for vendor extensions use`，且 adb 视角连 `neuralnetworks` 服务都不露（`Can't find service: neuralnetworks`）。
- **卡点二：LiteRT 的 NPU 走"厂商 dispatch 包"机制**。运行时日志 `NPU accelerator could not be loaded and registered: kLiteRtStatusErrorNotFound`；`liblitert_jni.so` 只有 `dispatch_package_path`，按目录找厂商 dispatch 库，而 Google Maven 只有 `litert` / `litert-api` / `litert-gpu`，没有 MediaTek 版。
- **本轮做成的部分（有价值）**：用 `scripts/quantize-onnx-models.py --activation int8` 重造量化模型后，ORT NNAPI 从"直接拒收"（`unsupported quantized type ... type: 2`，uint8 激活）变成**四档都能跑**：`yolo26m_640` CPU8 102.8 ms 对 NNAPI 147.5 ms——但仍慢 1.4 倍，因为只有 2 个节点下沉。
- **后续若要推进**，两条都需要外部条件：① 申请 NeuroPilot / Neuron SDK，自己接 Neuron delegate（设备侧已有 `libneuron_graph_delegate.mtk.so`）；② 由设备方把本应用包名加入 NNAPI vendor 扩展白名单。均不在代码层。
- 证据：`.local/model-quant/accel-reports/nnapi-int8-act-*.txt`、`route640-*.txt`、`aligned640-logcat.txt`。

### Windows 侧量化可用性（2026-10-11，桌面实测）

此前只按「Windows 量化是否可用尚未确定」并存模型；本轮用 **Windows 检测端同一套程序集**（`Microsoft.ML.OnnxRuntime.Managed` + `DirectML` 1.19.0）实测，工具为临时探针 `.local/model-quant/win-probe/`（`dotnet` net8.0 控制台，`cpu` / `directml` 两种提供器，10 帧中位数）。

`yolo26n_320`（320 输入）：

| 组合 | 中位 | 相对 |
|---|---|---|
| FP32 · CPU | 7.6 ms | 1.00× |
| **FP32 · DirectML** | **3.0 ms** | 2.53× |
| INT8 · CPU | 7.6 ms | 1.00× |
| INT8 · DirectML | 6.6 ms | 比 FP32 DML 慢 2.2 倍 |

`yolo26m_640`（640 输入）：

| 组合 | 中位 | 相对 |
|---|---|---|
| FP32 · CPU | 212.2 ms | 1.00× |
| **FP32 · DirectML** | **16.0 ms** | 13.3× |
| INT8 · CPU | 102.5 ms | 2.07× |
| INT8 · DirectML | 37.3 ms | 比 FP32 DML 慢 2.3 倍 |

两次独立复测（15 帧）方向一致：320 上 FP32 DML 2.6 ms 对 INT8 DML 6.8 ms。

**结论**：Windows 上**能用**量化模型、算子也都支持，但**量化只在走 CPU 时有收益**（640 上 2.07 倍），**在 DirectML 上明显负优化**（两种尺寸都慢 2.2–2.3 倍）。而 DirectML 本身才是 Windows 最大的加速来源（640 上比 CPU 快 13.3 倍）。因此 **Windows 侧最佳组合是 FP32 + DirectML**，不是 INT8。

这条正好印证了「并存」而不是替换：Android 用 **INT8 + CPU**（真机最优），Windows 用 **FP32 + DirectML**；同一基名分发两个精度，两端各取各自最优，不需要跨端协商或格式协商。

边界：本机是桌面 x86_64 + NVIDIA 显卡，DML 走的是这块 GPU；检测端真实部署机若没有可用的 DML 设备，INT8 + CPU 会成为 Windows 侧的正解——这一条待真实检测机确认。
