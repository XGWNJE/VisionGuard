## Android 推理节点选 GPU 档闪退的定位与修复（2026-10-14 · 静态定位 + 发行包 DEX 复核，真机复测待 owner）

- **症状**（owner 真机反馈）：Windows 节点推流到安卓推理节点这条链路上，来源用 CPU 档（`yolo26m_*_int8`）能正常推理，改用 GPU 档（`yolo26m_320` / `yolo26m_640`）应用闪退；换本机相机来源同样闪退。生产设备登记里该端为 `视觉推理节点 · KPad`（`android-inference`），已声明 `0.7.4`。
- **根因**：LiteRT 的原生桥（`liblitert_jni.so`）按**硬编码类名**查找 Java 类型来构造返回值与抛异常；R8 把这些类删掉后，原生层走的是**致命 CHECK**（库内条件串 `element_type_class != nullptr` / `layout_class != nullptr` / `tensor_type_class != nullptr` / `ex_class != nullptr`，失败文案 `Failed to find ElementType class.` 等，前缀 `LiteRT check failed:`）→ 直接 `abort` 进程，Kotlin 侧 `runCatching` 抓不住。生产链路里 **LiteRT 只用于 GPU 档**（CPU 档走 ONNX Runtime），所以只有 GPU 档中招，与来源是推流还是本机相机无关。
- **证据**（全部离线可复核，未上真机）：
  - APK 内 `classes.dex` 字符串表（复核脚本 `.local/litert-dex-scan.js`，按类名逐包计数）：`com.google.ai.edge.litert.TensorType$ElementType` / `TensorType$Layout` / `TensorBufferRequirements` / `LiteRtException` 在 debug 包里分别出现 5 / 5 / 4 / 2 处，在 release 包里**一处都没有**；`Environment` / `CompiledModel` / `TensorBuffer` / `TensorType` 两种包都保留（它们带 native 方法，命中 Android 默认的「保 native 方法类及其签名用到的类」规则，嵌套类型不在任何被保签名里）。**0.6.12 / 0.7.0 / 0.7.4 三个 release 包完全一致**——不是后来的改动引入的。
  - R8 产物：`mapping.txt` 里 `Accelerator -> b1`、`CompiledModel$Options -> tt`、`GpuOptions -> st` 等同批改名，`usage.txt` 列出被删的上述四类；LiteRT 的 AAR 自带规则只保 `@UsedByReflection` 标注的成员，而这四个类只有 `kotlin.Metadata`。
  - 原生库：`libLiteRt.so` / `liblitert_jni.so` / `libLiteRtClGlAccelerator.so` 在 0.6.12 与 0.7.4 的包里逐字节相同；`liblitert_jni.so` 内含上述四个类名与全部 CHECK 条件串。

## 通知节点协议版本冻结在 0.7.1 的定位与同版本替换（2026-10-14 · owner 授权，不 bump 版本）

- **现象**：owner 真机登录通知节点，登录后立刻回到登录页且没有任何提示。服务端日志：`POST /api/account/login` → 200（HTTP 通道过了闸门），紧接着 WS 连接 `[WsAuth] protocol-dropped reason=protocol-version`、`[Protocol] byVersion={"0.7.1":5,...}`；设备记录 `通知节点 · KPad2` 的声明版本是 `0.7.1`。App 收到 `4001` 后按 `NotificationNodeService.onClosing` 清会话并回登录页，所以看不到「密码错误」这类提示。
- **根因**：通知节点是全项目唯一直接引用 `BuildConfig.VERSION_NAME` 的地方；Java `static final` 常量会被 Kotlin 在编译期内联成字面量，而承载该引用的 `NotificationNodeService$connect$1.class` 是 2026-10-12 14:06（0.7.1 构建）的产物，0.7.2 / 0.7.3 的增量构建直接复用了它。证据：三个已发布通知节点包（0.7.1 / 0.7.2 / 0.7.3）`classes.dex` 字符串表里只有 `0.7.1`、没有各自版本号；对照推理节点与相机节点 0.7.3 包为 `0.7.3`。manifest 与设置页显示的 0.7.3 是对的，因此肉眼与常规检查都看不出来。
- **影响**：严格闸门实例上通知节点无法建立控制通道（HTTP 能登录、WS 必被切）；0.7.1 起的三个发行包都如此。
- **修复（两轮）**：第一轮把通知节点 WS 认证帧的版本从 `BuildConfig.VERSION_NAME` 换成新增的 `AppConstants.VERSION`（定义为 `val VERSION: String = BuildConfig.VERSION_NAME`）——**不够**：Kotlin 同样会把 `BuildConfig` 的 Java 常量内联进 `AppConstants` 自己的 class，0.7.4 发布构建时被新护栏抓到（包内仍是 0.7.3）。第二轮按相机节点既有的正确模式收口：三个 Android 端的协议版本都写成**由 `scripts/sync-version.js` 收管的 `const val VERSION = "x.y.z"` 源码字面量**（Kotlin 源码常量变化会被增量编译跟踪并触发重编译，生成的 Java 常量不会），推理节点 `AppConstants.VERSION` 由 `BuildConfig` 派生改为字面量，通知节点重建同款 `AppConstants.kt`；`scripts/check-docs.js` 同步校验三处字面量等于根 `VERSION`，`scripts/check-protocol-declarations.js` 增加 `version-runtime-source` 检查：声明处出现 `BuildConfig.VERSION_NAME` 即报错。

### 同精度对齐后的 GPU 定论与 int8 负优化（2026-10-11，640 三种尺寸）

- 真机 kpad（MT8910 / API 37）截断 FP32 图的 GPU / 同图 CPU：N640 23.7 / 39.8 ms、S640 37.2 / 93.1 ms、M640 67.5 / 255.7 ms。M640 INT8 GPU 为 106.6 ms，且混量程整数边界使分类归零，不能用于正式 GPU 档。证据 `.local/model-quant/accel-reports/aligned640-device-report.txt`、`aligned640-logcat.txt`。
- 正确解析接入后，M640 GPU 端到端约 67.0 ms、解码 / NMS 0.9–1.8 ms，person 2、最高分 0.967，与正式模型及黄金样本一致。证据 `gpu-e2e-20261011-194106.txt`；早期错误解析的框读数作废。

### 多路压力：正式档的在册上限（2026-10-11，640 输入，真实实例图）

- 同机真实人物图、独立会话每路 8 帧：M640 INT8 CPU 两路约 156.8 ms / 6.4 FPS，四路降至 545.3 ms / 1.8 FPS；GPU 32 路单路约 63.0 ms（P95 71.7 / 最大 76.8）。M320 后续补测 INT8 四路 159.5 ms / 6.3 FPS，八路不达 5 FPS；GPU 32 路仍约 21.0 ms。
- 当前在册 CPU M320 / M640 为 4 / 2 路，GPU 均封顶 32；GPU 未测到吞吐极限，不能把理论封顶当作所有设备可承载保证。实际 FPS 仍受采样与全链路约束。证据 `.local/model-quant/accel-reports/` 内 `prod-sweep-*`、`parallel-sweep-*`、`stream-single-*`。
