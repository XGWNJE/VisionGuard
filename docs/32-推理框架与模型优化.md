# 推理框架与模型优化

负责：推理端（Android / Windows）运行时与模型的优化路线、验收口径与未决项。不负责：任务状态或验证报告。更新时机：优化路线、实测基线或验收口径变化时。任务归属见[任务清单](06-任务清单.md)，实测证据见[验证记录](90-验证记录.md)。

本专题属于 `feature/inference-optimization` 分支的落点；主线当前固定走 CPU，理由见下。

## 现状基线

真机 kpad2（MediaTek MT8910，Android 17，arm64-v8a），`yolo26m_640.onnx`（78 MiB，FP32），单张合成输入连续 6 帧均值：

| 方案 | 平均 | 最小 | 最大 |
|---|---|---|---|
| NNAPI · 仅加速器 | 1737.8 ms | 1706 | 1786 |
| NNAPI · FP16 | 1882.7 ms | 1634 | 2234 |
| NNAPI · 默认 | 1911.2 ms | 1611 | 2946 |
| NNAPI · NCHW | 2251.8 ms | 2036 | 2514 |
| **CPU · 4 线程** | **334.8 ms** | 318 | 343 |
| CPU · XNNPACK（2 线程） | 335.0 ms | 326 | 363 |

同机小模型 `yolo26n_320.onnx`（9.4 MiB）此前实测 NNAPI 为 77 ms/帧（3.0 FPS 采样）。

x86_64 模拟器（pixel_tablet，无加速器）对照：NNAPI 各档 88–116 ms，CPU 7.8–10.0 ms，方向与真机相反，说明模拟器数据不能代表真机。

## 为什么当前没有加速收益

1. **运行时层面**：ONNX Runtime 官方 Android 包（`onnxruntime-android`）在 Java 侧只提供 NNAPI 与 CPU 两个执行提供器；它的 GPU 提供器（CUDA / TensorRT / DirectML）全部面向桌面，Android 不可用，也没有 OpenCL / Vulkan 版本。因此当前技术栈不存在 GPU 通道。
2. **算子层面**：NNAPI 只把厂商驱动认识的算子下沉，其余回退 CPU。YOLO 的后处理与部分算子不被 MediaTek Neuron 接受，图被切成多段，每跨边界一次就要同步并搬运张量；模型越小，加速省的绝对时间越少，搬运开销占比越高，于是出现"用加速反而更慢"。
3. **精度层面**：现有 12 个模型（yolo26 与 yolov5 两族 × n/s/m × 320/640）全部是 FP32。移动加速器最擅长 INT8、其次是 FP16，FP32 输入往往需要在主机侧插入格式转换。

判定依据：NNAPI 的 FP16 与默认精度两档耗时几乎相同（1882.7 与 1911.2 ms）。若计算真正落在加速器上，半精度应明显更快。

## 量化现状（2026-10-11）

脚本 `scripts/quantize-onnx-models.py`：静态（QDQ，需校准画面）与动态（只量化权重）两种模式，产物默认 `*_int8.onnx`。两条已实测的硬约束：

1. **必须用真实画面校准**。只用夜间截图校准时，类别分数被截断在同一个上限（多张画面最高分都停在 0.676）。改用真实照片校准后：`yolo26n_320` 在 4 张真实照片上与 FP32 的 person 检测框数量一致、逐框 IoU ≥ 0.90、中心偏移 ≤ 4 px，最高分偏差 ≤ 0.10。
2. **必须排除"大小量程混用"的检测头**。YOLO26 与 YOLOv5u 的图尾都是 `Concat(门控框坐标 0–675, Sigmoid(类别分数 0–0.44))`；逐张量激活量化只有一个 scale，该 Concat 一旦量化，类别分数被压成 0，检测输出全空（实测前 5 框分数全为 0）。脚本默认 `--exclude head`：从图输出回溯到那个混用 Concat，取它的前向依赖（两分支各自的检测头卷积）留浮点，其余算子（主干、训练分支）照常量化。`yolo26n_320` 即 398 个节点里排除 21 个。

桌面 x86 参考（`yolo26n_320`，产物 9.4 MiB → 2.9 MiB）：单线程 FP32 14.6 ms → INT8 8.5 ms（1.72×），4 线程 6.3 → 5.3 ms（1.19×）。线程越多加速越小，是内存带宽与浮点并行度共同限制，属常规现象。

产物与质量（校准集 12 张真实照片，MinMax 校准）：

| 模型 | 体积 FP32 → INT8 | person 框数与 FP32 一致 | 逐框 IoU | 带标注验证集上保留 FP32 检出 |
|---|---|---|---|---|
| `yolo26n_320` | 9.4 → 2.9 MiB | 4/4 张一致 | 0.899–0.975 | 19/20（95%） |
| `yolo26n_640` | 9.5 → 3.0 MiB | 2/4 张一致（另两张 1 框出入） | 0.83–0.98 | 29/29（100%） |
| `yolo26s_320` | 36.4 → 9.8 MiB | 4/4 张一致 | 0.905–0.939 | 25/28（89%） |
| `yolo26s_640` | 36.5 → 9.9 MiB | 4/4 张一致 | 0.913–0.977 | 33/38（87%） |
| `yolo26m_320` | 78.1 → 20.4 MiB | — | — | 26/31（84%） |
| `yolo26m_640` | 78.2 → 20.4 MiB | 4/4 张一致 | 0.855–0.966 | 42/44（95.5%） |
| `yolov5nu_320` | 10.2 → 2.9 MiB | 最高分类别一致（锚点输出） | — | — |

`yolo26` 家族（n/s/m × 320/640）已全部产出 INT8；`yolov5` 家族只做了 `n·320` 的入口验证（Android 走现代档，legacy 模型的量化留待 Windows 侧评估）。

**I/O 契约不变，端侧无需改代码**：逐模型核对量化前后输入张量都是 `float32`、形状一致（`yolo26` 为 `[1,3,S,S]` → `[1,300,6]`，`yolov5u` 为 `[1,3,320,320]` → `[1,84,2100]`）。QDQ 的量化只发生在图内部，端侧仍按 float32 送数、按同一套解析器读结果。

「保留 FP32 检出」= 在 COCO12-Formats 带标注集（12 张、54 个真值框）上，INT8 结果里能找到同类且 IoU ≥ 0.5 对应的 FP32 框占比。该集合的绝对召回很低（`yolo26m_640` 的 FP32 也只命中 8/54），因此它用来判「量化有没有打坏已有检出」，不能当作整体精度指标；`yolo26n_640` 的检出数还比 FP32 多，属于阈值附近的抖动。

YOLOv5u（opset 12，输出 `[1,84,N]` 原始锚点）需要先把 opset 升到 13，脚本会自动完成并核对升级前后输出一致。

已知限制：

- 校准集目前借用仓库内的真实照片夹具（12 张）；正式校准集应来自相机推流或本机相机采集，覆盖白天 / 夜间 / 不同角度。
- 上面全部是桌面 x86 读数与离线精度：ARM 的整数卷积核与 NNAPI 接受度必须真机实测，加速门槛尚未判定。
- 主线的加速诊断已随档位移除；本分支已补上真机测量入口（见上），不需要另建诊断界面。

### 校准算法与"分数上限"排查（2026-10-11）

`yolo26n_640` 曾在多张画面上把最高分报成 0.946，一度怀疑是量化把分数截顶。实测推翻了这个怀疑：同一张 `person-umbrella.jpg` 上 **FP32 自身就是 0.9463**，INT8 是 0.946（差 0.0003）；`zidane` 是 0.901 → 0.946、`bus` 0.918 → 0.946，偏差 ≤ 0.045，属于检测头卷积的权重量化误差，不是截断。

顺带固定了校准算法的选择（`CalibrationMethod` 对比，同一模型同一校准集）：

| 算法 | 该画面最高分 | 结论 |
|---|---|---|
| MinMax（当前默认） | 0.9463 | 与 FP32 一致，采用 |
| Entropy | 0.9463 | 与 MinMax 相同 |
| Distribution | 0.8312 | 掉点，不采用 |
| Percentile | 0.0397 | 直接崩坏，不采用 |

另核对过校准集本身的量程：12 张照片在 `yolo26n_640` 上的类别分数峰值为 0.928（中位）/ 0.946（最高）；平板夜间截图 80 张的中位只有 0.064、最高 0.753，作为校准数据代表的分布过窄，只适合作为补充而不是主体。

## 真机测量入口（本分支专用）

**交付形态是自包含 APK：模型与测试画面随包分发，装完点一下就跑，不需要 adb、不需要电脑、不需要登录。** 测量构建的首屏就是测量页（「快速测量」只跑加速档与其 CPU 基线；「完整测量」另跑逐线程 CPU 档），结果上屏、写设备诊断文件、可经系统分享发回；底部保留「进入完整应用」才走登录。把入口放在登录之前的原因：测量只用本机算力与包内模型，而登录要求服务可达、账号可用，测量现场不一定满足。正式构建与 UI 预览包没有这个首屏，设置里也不显示测量分区。

同一个逻辑还有一个无界面入口，供自动化验证复用（不需要登录）：

```bash
adb shell am start -n com.xgwnje.visionguard.inference/com.xgwnje.visionguard.inference.MainActivity \
    --ez benchmark true [--ez benchmark_full true]
adb logcat -d -s VGInferenceBench:V
```

档位表：

| 运行时 | 档位 |
|---|---|
| ONNX Runtime | CPU 1 / 4 / 8 线程，NNAPI 默认 / FP16 / NCHW / 仅加速器 |
| LiteRT（`Interpreter` 入口） | CPU 1 / 4 / 8 线程 |
| LiteRT（`CompiledModel` 加速器入口） | CPU、GPU、GPU FP16、NPU |

报告首行是**设备指纹**，含厂商/型号/API/芯片/核心数（`SOC_MODEL` 需 API 31+，取不到就跳过），例如
`设备：Xiaomi 26048RP6AC / API 37 / MT8910 / 8 核`。带这一行是因为「CPU 4 线程最优」这个结论
是否随核心拓扑变化，只能靠芯片与核心数判断——不同芯片的机器上 4 线程未必还是最优。每档还会带上
实际生效的设置（如 `XNNPACK flags=-1，线程 4`、`输入 FLOAT32 / 输出 FLOAT32`、`可用加速器 GPU,CPU`），
避免「有没有真的开」靠猜。

加速器档位开跑前先问 `getAvailableAccelerators()`：本机不支持就记一条带可用列表的失败，不静默回落 CPU。

读数口径：每档预热 2 帧、最多 10 帧，报中位数 / 最小 / 最大；报告按**各自运行时的 CPU 基线**给「加速档 ÷ CPU」比值与是否达标（门槛 ≤ 0.70×），跨运行时不混算。输入是与正式链路同一套 letterbox 预处理生成的真实画面。报告写入设备 `files/diagnostics/acceleration-bench-*.txt`，界面上可直接分享文本。

输入默认用脚本推送的真实画面（与正式链路同一套 letterbox 预处理）；画面缺失时退回固定种子的合成画面并在报告里记一条失败。质量另按上面的离线对比方法核对。报告同时写入设备 `files/diagnostics/acceleration-bench-*.txt`，脚本会取回一份。

提交读数时请附：设备型号与 Android 版本、模型基名、各档完整行（含失败项原文），以及报告文件内容。

运行时侧已核对的静态事实：随 APK 分发的 `onnxruntime-android` 1.30.0 的 arm64 库里带 `QuantizeLinear` / `DequantizeLinear` 的 NNAPI 构建器（`dequantizelinear_op_builder.cc`、带 scale 校验），Java 侧只暴露 CPU / NNAPI 两个可注册提供器（`NNAPIFlags` 仅 USE_FP16 / USE_NCHW / CPU_DISABLED / CPU_ONLY，GPU 类提供器不在这个包里）。也就是说 INT8 走 NNAPI 在运行时层面是有路径的，能不能达标只能靠上面这次真机测量。

量化产物的形态契约由单测固定（`QuantizedModelContractTest`）：700 字节的 QDQ 探针模型入库，断言它是 QDQ INT8 图且 opset ≥ 13，并断言端侧按 `<键>_int8.onnx` 找文件。JVM 单测**不加载 ONNX Runtime**——Android 版只有 .so，测试 JVM 拿不到 `java.library.path`（试过把 AAR 里的 x86_64 库解到 `jniLibs`，仍加载失败），因此「运行时真的接受这个图」由真机测量证明：建会话失败会作为失败项原样进报告。

## 路线

### 一、INT8 量化（进行中）

改动小、收益明确，且不改推理端代码（模型下载与加载逻辑与格式无关）。

做法：在现有导出管线 `scripts/export-yolov5-models.py` 之后接量化步骤，产出 `*_int8.onnx`；服务端 `/models/<键>.onnx` 直接多分发一个文件；端侧仍走 CPU（或按门槛重新评估 NNAPI）。

服务端发布前需落实：模型目录与 `releases.json` 的声明方式与现有键名约定一致；新键加入前确认控制台与 Android 的模型列表契约。

落地的具体卡点（本轮核对）：模型键由端侧上报、服务端按端侧列表校验（`ControlProtocol` 的 `modelOptions`），下载走 `/models/<键>.onnx`。

**分发方式当前状态：取消投放，保持原样。** owner 已决定在推理路线定案前不投放量化模型，服务端仍是 12 个 FP32 本体；端侧 `ModelKeys.keys` 只列本体（量化键不在可选清单里——清单直接驱动参数抽屉的模型选择器，未下载的会显示下载入口，服务端没有文件时用户点了必然失败）。

取消前已核对的契约（将来启用时可复用）：

| 环节 | 现状 | 是否要改 |
|---|---|---|
| 服务端模型键校验 | 没有白名单，只校验 `[A-Za-z0-9_-]{1,64}`、上限 16 项 | **不用改**（启用后为 12 项，仍在上限内） |
| 服务端分发 | `/models` 静态目录按文件名分发 | **不用改**，放文件即可 |
| 端侧清单 | `ModelKeys.keys` 现只有 6 本体；派生清单在 `derivedKeys()` | 启用时把 `keys` 改回 `derivedKeys()` |
| 下载路径 | `ModelStore` 统一走 `ModelKeys.fileName(key)` | 已就位，无需再改 |
| 推理链与解析器 | 量化前后 I/O 契约一致（float32 进、float32 出、类别数不变） | **不用改** |
| 控制台目标选择 | 标签由端侧固定 COCO 类表生成，不读模型文件 | **不用改** |
| Windows 端 | `detector/windows-wpf/Utils/ModelManager.cs` 有**自己的**键列表 | **不受影响** |

启用时顺序不能随意调整：`InferenceRuntime.defaultModelKey()` 取「第一个已下载的键」，量化键必须排在各自本体之后，新装设备的默认模型才仍是 FP32。这条由 `ModelKeysTest` 守住（当前断言派生清单的顺序，同时断言量化键不在可选清单里）。

模型文件本身不入版本控制，启用时才需要另行投放到 `server/data/models/`（生产环境走发布授权）。投放脚本 [deploy-int8-models.ps1](../scripts/deploy-int8-models.ps1) 已就绪（VPS 目标默认只读预检，需 `-Confirm` 才写）。

**投放脚本**：[deploy-int8-models.ps1](../scripts/deploy-int8-models.ps1)。做四件事，任何一步失败就整体中止（不做部分投放）：

1. 逐个用 ONNX Runtime **真加载并跑一帧**——只看文件大小会漏掉半截文件；
2. 校验目标侧 FP32 **本体存在**（量化版是并存，本体缺了就是配置错误）；
3. 目标侧余量检查（VPS 额外查磁盘余量）；
4. 投放后逐个比对 sha256，不一致即判失败。

```powershell
pwsh scripts/deploy-int8-models.ps1 -WhatIf               # 本地演练：只校验与预览
pwsh scripts/deploy-int8-models.ps1                       # 投放到 server/data/models
pwsh scripts/deploy-int8-models.ps1 -Target Vps           # VPS 只读预检 + 预览上传命令
pwsh scripts/deploy-int8-models.ps1 -Target Vps -Confirm  # 真正上传（发布动作，需授权）
```

**VPS 目标默认只做只读预检**，不加 `-Confirm` 不写任何文件。路径不靠猜：脚本按候选探测，全都不存在就中止并要求 `-VpsDir`。2026-10-11 实测：`visionguard.service` 的 `WorkingDirectory` 是 `/opt/visionguard-server`，模型在 `/opt/visionguard-server/data/models`（12 个 FP32 本体，余量 2751 MiB，本次需约 131 MiB）。

本地已验证：6 个文件共 66.6 MiB 投入后，在隔离测试服务上按端侧实际路径 `/models/<键>.onnx` 取回 **HTTP 200 且长度与本地一致**（`yolo26n_320_int8` 3,129,467 字节）。VPS 侧只读预检已通过，**尚未上传**（发布动作，待 owner 授权）。

### 完整量化（int8 I/O）暂时造不出来

加速器通常只接受**输入输出都为整数**的完整量化模型，而现有 `.tflite` 都是 float32 边界、图内 int8。尝试用 `onnx2tf` 的严格全整数量化（`-oiqt -ett full_integer_quant`）生成时，在 YOLO 的解码段失败：

```
StrictFullIntegerQuantizationError: Unsupported op for strict full integer quantization: index=2 op_type=ROUND
```

因此 **GPU 路线还剩最后一种未排除的可能**（原生 int8 I/O 的模型），但它卡在转换工具对 `ROUND` 算子的支持上，不是卡在设备。要打通得换转换路径（例如从 PyTorch 侧直接导出 LiteRT，需要 Linux x86 或 macOS 环境）。

### 四、官方对 CPU / GPU / NPU 的口径（2026-10-11 核对官方仓库）

LiteRT 官方 README 的加速分工写得很明确：**CPU 走 XNNPACK，GPU 走 ML Drift，NPU 走厂商 dispatch**；`CompiledModel` 的卖点是「自动选择加速器、无需显式 delegate」。平台支持矩阵里 Android 一栏：CPU ✅、GPU ✅ OpenCL + OpenGL、NPU ✅ Broadcom / Google Tensor / Intel / **MediaTek** / Qualcomm / S.LSI。

**NPU 在本机不通，有两条硬理由（都已核实）**：

1. **SoC 不在支持列表里**。官方 `litert/vendors/mediatek/supported_soc.csv` 列出的是 MT6895/MT6897/MT6983/MT6985/MT6989/MT6991/MT6993/MT8171/MT8188/MT8189/MT8196——**没有 MT8910**（kpad2 / Xiaomi 26048RP6AC 的芯片）。NPU 档报「本机不支持」与此一致，不是配置问题。
2. **NPU 需要厂商 dispatch 库，且拿不到**。`litert/vendors/mediatek/dispatch` 要从源码编译，依赖联发科 Neuron SDK；Google Maven 上**没有** `litert-sdk-mediatek`（只有 `litert` / `litert-api` / `litert-gpu`，均 2.3.0）。另有官方 issue 说明：动态链接构建下若未设 `kLiteRtEnvOptionTagDispatchLibraryDir`，NPU 会**静默回落 CPU**（Java/Android 路径由 JNI 自动设置该目录，所以我们的「不支持」是真实的注册失败，而不是静默回落）。

**GPU 才是本机唯一现实的加速路径**：Android 上 ML Drift 的 `libLiteRtClGlAccelerator.so` 同时支持 OpenCL 与 OpenGL，Mali 驱动两条都可能有。真机上加速器能被识别（`可用加速器 GPU,CPU`），失败集中在编译模型这一步，需要原生日志才能继续定位。

**CPU 侧之前漏测了官方的 XNNPACK 路径**：老 `Interpreter` 档可以 `setUseXNNPACK(true)`，而官方把 XNNPACK 定义为 LiteRT 的 CPU 加速库。已补 XNNPACK 2 / 4 线程两档一起测——这可能直接改变结论，因为我们的现状就是 CPU 已经很快（8.3 ms）。

### 二、换推理运行时（LiteRT / TFLite + delegate）——已获 owner 授权，进行中

owner 已明确授权更换运行时以取得最佳加速效果，本节按此推进。真正吃到硬件加速的路线：LiteRT 有 GPU delegate（Mali 走 OpenCL）与厂商 NPU delegate。代价是换引擎级别的工程：ONNX → LiteRT 转换、输入预处理与输出后处理对齐（NMS 段最易出偏差）、精度回归。

本轮核实的平台与工具事实：

- 本机是 Windows，**没有 WSL、没有 Docker**；`ultralytics` 的 LiteRT/TFLite 导出直接拒绝在 Windows 运行（`LiteRT export only supported on Linux x86 and macOS`）。因此这条路只能走 Windows 可用的 ONNX → TFLite 转换（`onnx2tf`），或另备一台 Linux x86 机器。
- `ultralytics` 的 PyTorch 权重（`yolo26n.pt`，5.3 MB）可下载，其原始输出是 `[1,84,2100]` 锚点格式，与生产 ONNX 的 `[1,300,6]`（图内 NMS）不同；端侧 `YoloOutputParser` 已支持锚点档，因此两条输出形态都能接。
- ONNX Runtime 侧的替代加速提供器都不适用：QNN/NPU 面向高通，CoreML 面向 Apple，DirectML/CUDA 面向桌面；联发科的 NeuroPilot 需要单独申请 SDK，不在公开分发包里。

**转换链路已在 Windows 跑通**（`onnx2tf` + TensorFlow，本机 Python 3.12）：

| 步骤 | 结果 |
|---|---|
| `yolo26n_320_int8.onnx` → LiteRT | 产出 float32 / float16 两个 `.tflite`；float16 版有 `TRANSPOSE` 类型不一致，运行失败，不可用 |
| `yolo26m_640_int8.onnx` → LiteRT | 同上，float32 版可用 |

float32 版 `.tflite` 的**数值与 ONNX INT8 几乎一致**（同一批真实照片，输出余弦：`yolo26n_320` ≥ 0.9999；`yolo26m_640` 0.8166–0.8910 对 ONNX INT8 的 0.8252–0.8924，差异 ≤ 0.004），最高分完全一致。它内部**确实是 INT8 计算**：5339 个张量里 378 个 `int8`，带我们从 QDQ 校准得到的 scale（例如 `wa/model.0/conv/Conv_output_0`，scale 0.5338），输入输出保持 float32——正是端侧需要的形态。

Android 侧依赖与 API 现状（LiteRT 2.3.0，坐标在 Google Maven 上确认存在）：

- `com.google.ai.edge.litert:litert` / `litert-api` / `litert-gpu` 均存在；`litert-gpu` 的 arm64 目录带 `libLiteRtClGlAccelerator.so`（OpenCL/GL 加速器）。
- 新 API 里有 **NPU 入口**：`NpuCompatibilityChecker`（含 `Mediatek` 实现）、`Accelerator`、`CompiledModel.GpuOptions/QualcommOptions`，以及 `BuiltinNpuAcceleratorProvider`。这是 MediaTek 平台上公开可得的 NPU 路径。
- **老的 Delegate 入口在这套分发里不可用**：`InterpreterApi.Options` 只暴露 `setNumThreads`，没有 `addDelegate`；Play Services 的 `GpuDelegate` 实现的是另一套 `Delegate` 基类，接不上 LiteRT 的 `Interpreter`。
- **GPU / NPU 已接到 `CompiledModel` 加速器 API**（本轮落地）：用 `Accelerator` 枚举（`NONE` / `CPU` / `GPU` / `NPU`）选择加速器，`Environment.getAvailableAccelerators()` 在运行前问出本机支持哪些；`CompiledModel.GpuOptions(precision = FP16)` 控制 GPU 精度。开跑前先检查可用性，**不支持就记一条带可用列表的失败，不静默回落 CPU**——静默回落会把「GPU 没生效」误报成「GPU 不快」。
- 加速器原生库随 APK 分发：`litert` 带 `libLiteRt.so`（5.37 MiB，CPU）、`litert-gpu` 带 `libLiteRtClGlAccelerator.so`（3.10 MiB，GL/CL 即 Mali GPU），`litert-api` 带 `liblitert_jni.so`。**没有 MediaTek NPU 的专用 dispatch 库**，所以 NPU 档在 MT8910 上大概率报「本机不支持」；真机报错原文就是结论，需要时再评估申请厂商 SDK。
- 本轮的落点：Android 侧同时装 ONNX Runtime 与 LiteRT，**同一个模型基名可分别喂 `.onnx` 与 `.tflite`**，一次测量跑完 ONNX 七档 + LiteRT 七档（含 GPU / GPU FP16 / NPU）。

**NNAPI 的分段计数无法在桌面上取得**（Windows 没有 NNAPI 提供器；ORT 的 profiling 只会报 CPU 节点），所以「NNAPI 到底把图切成了几段」只能在真机上用 `--es frame` 那次测量间接受证据。

### 三、厂商 NPU SDK

MediaTek NeuroPilot SDK（`.dlc`）性能上限最高，但要申请 SDK、集成额外 `.so`、绑定芯片平台。需要 owner 先去申请，拿到 SDK 才谈得上集成。

## 验收口径

### 门槛（硬标准）

- **加速门槛**：硬件加速（NNAPI、LiteRT GPU/NPU 等）必须比**同运行时、同精度的 CPU** 快 **30% 以上**，即耗时 ≤ CPU 的 70%；达不到就按"放弃该加速档"处理。
- **多路压力门槛**：部署是多来源同时推理，判定看**单路帧率 ≥5 帧/秒**（等价单路中位 ≤200 ms），不只看总吞吐——总吞吐高但单路排队几百毫秒等于来源卡死。
- **耗时口径**：每档预热 2 帧、10 帧取中位数。**跨会话不可直接比**（同一配置在两次会话间可达 2–4 倍差异，与系统限速 / 电源状态有关），定档只用同一次会话内的横向比较。
- **精度口径**：同一画面上目标类别的检出数量与位置不出现肉眼可见退化；实例图上**露出很少的目标漏检不算错**，只按主目标判定。
- 证据：真机读数与原始日志进[验证记录](90-验证记录.md)，含设备、模型、帧数与失败原文。

### 各路线定论（2026-10-11 定案，真机 Xiaomi 26048RP6AC / MT8910 / API 37）

| 路线 | 状态 | 关键读数 | 适用条件与代价 |
|---|---|---|---|
| **ONNX CPU（正式档）** | ✅ 采用 | `yolo26n_320_int8` 单路 5.9–14 ms；4 线程一致优于 1/8 线程；int8 比同结构 FP32 快 1.5–2.0 倍 | 无额外代价。**多路上限随模型定**：320 → 32 路、640-n → 4 路、640-m → **2 路** |
| **LiteRT GPU（截断图 + FP32）** | ✅ 可用待落地 | 端到端（推理 + 解码 + NMS）同轮比同 API CPU 基线快 **4.3×**（640-m：67.0 对 290.2 ms，解析仅 0.9–1.8 ms）；质量与正式模型逐位一致 | **只在 640 及以上值得用**（320 反而输：14.4 对 7.4 ms）；代价是双格式 + 端侧锚点解析（已落地）。多路到 32 路仍是 15.9 帧/秒 |
| **NNAPI / NPU** | ❌ 放弃 | NNAPI 只跑 Google CPU 参考实现（`nnapi-reference`，分片 2/432）；NPU 缺公开接口 | 不申请厂商 SDK 则无路可走，单独存档 |

三条地图结构与精度都实测对齐过，细节与失败原文见[验证记录](90-验证记录.md)：[GPU 打通与 int8 负优化](90-验证记录.md#同精度对齐后的-gpu-定论与-int8-负优化2026-10-11640-三种尺寸)、[多路上限](90-验证记录.md#多路压力正式档的在册上限2026-10-11640-输入真实实例图)、[NPU](90-验证记录.md#npu-定论单独存档后期有空再评估)。

### GPU 跨平台适配（Qualcomm SoC）

**结论：GPU 路线不绑定 GPU 厂商，Qualcomm 可用；缺的是实测，不是适配。** 依据（2026-10-11 核对分发包本体，非文档推断）：

- 加速器是厂商中立的 ML Drift OpenCL/OpenGL 实现。`litert-gpu-2.3.0.aar` 只含一个 `libLiteRtClGlAccelerator.so`（arm64 3.10 MiB）、无 Java 类、不依赖任何厂商 SDK；它的 `DT_NEEDED` 同时含 `libOpenCL.so`、`libEGL.so`、`libGLES_mali.so`，驱动按运行期探测。
- **Adreno 是一等后端，优化已内含**。同一个 `.so` 里带 Adreno 专用分支：`Adreno 8xx with compiler E031.47.12.xxx is not well supported in MLDrift OpenCL`（按驱动编译器版本做规避）、`Async execution is not supported on Adreno and PowerVR`，以及 `cl_qcom_dot_product8` / `cl_qcom_inline_asm` / `cl_qcom_accelerated_image_ops` / `cl_qcom_recordable_queues` 等 Qualcomm 扩展的 `#pragma` 路径。
- **本机是 Mali 侧特化**：`libGLES_mali.so` 是 MT6993 专有驱动名，我们全部读数来自这台 MT8910 设备，不能外推。
- **打通 GPU 的那一步对跨厂商是加分项**：截断图内 int64 后处理（TopK/Tile/Gather 等）是去掉 `CompiledModel` 在 GPU 上编不过的算子，Adreno 同样编不过这些，属于通用约束而非 MediaTek 特性。
- 档位已备好 Adreno 偏好的变量：`LITERT_GPU_FP16`（精度 FP16）与 `LITERT_GPU_TEXTURE`（纹理权重），无需新增代码。

**未验证的边界**：Adreno 与 Mali 的实测差距可能很大——既有的「同图同精度比 CPU 快 1.7–3.8 倍」是 Mali 读数，Qualcomm 上可能更高也可能不达门槛（≤CPU 70%），**只能上机实测定论**。GPU 路线与 SoC 厂商的 NPU 通道无关，不继承 NPU 在各家的可用性差异。

### 正式档位与限制

- **正式档 = ONNX Runtime · CPU 4 线程**（`InferenceProvider.production = ONNX_CPU4`），FP32 本体与 INT8 量化版都能跑；量化版更快、更省内存，是 CPU 路线上的优选。
- **加速档 = LiteRT GPU + 截断图**，已接进正式链路并**纳入主线支持范围**（2026-10-11 定案）：来源启动时按「该模型有 GPU 产物且已下载」自动选择后端——能用 GPU 就用，用不了显式回落 CPU 并把原因写进来源状态（`backendNote`，例如「未下载 GPU 模型」「GPU 模型加载失败」）。
- **每个模型跑在哪，界面直接标**：模型资源列表每项在名称旁显示后端标签（`GPU` / `CPU` / `CPU · INT8`），判定与 `InferenceEngineFactory`、`ModelInferenceTarget` 同一口径。
- **量级结论目前只来自 MT8910（Mali）**，Qualcomm 真机待测（见 [GPU 跨平台适配](#gpu-跨平台适配qualcomm-soc)）。
- **模型分发**：清单 12 项（6 个基名 × 本体 / 量化），另有 1 个 GPU 产物 `yolo26m_640_gpu.tflite`。同键的另一个文件、按文件名静态分发，不需要映射表；投放用 `scripts/deploy-int8-models.ps1 -Kind Quantized|Gpu`（带真加载校验）。**12 个 ONNX 与 GPU 产物均已投放**（公开端点核对 200、字节与本地一致）；320 档不开放 GPU 产物。
- **多路限制**：端侧按「模型 + 后端」硬拦截，数值与依据见下；新增来源（本机相机与服务端下发的远程流）都过同一道关，超限时给出可读原因而不是静默卡死。
- **契约**：模型键名、下载路径、`DetectionParams` 校验、心跳字段（`inferenceLimits` / `inferenceBackends` / `overConcurrencyLimit` / 逐来源 `concurrencyLimit`）的变化须同步端、服务与测试。

### 多路限制（单路 ≥5 帧/秒）

| 配置 | 上限 | 依据（同轮实测） |
|---|---|---|
| ONNX CPU 4 线程 + `yolo26m_640` | 2 路 | 2 路 6.4 帧/秒；4 路掉到 1.8 |
| ONNX CPU 4 线程 + `yolo26n_640` | 4 路 | 4 路 5.8 帧/秒；8 路掉到 3.3 |
| ONNX CPU 4 线程 + 320 档 | 32 路 | 32 路仍 10.5 帧/秒，未触底 |
| LiteRT GPU + 截断图（`yolo26m_640`） | 32 路 | 32 路仍 15.4 帧/秒，受内存而非算力约束 |

- 数值是**实测下限**，不是理论值；未在册的组合按最保守的 2 路处理（宁可先跑通，也不要静默卡死）。实现与单测见 `InferenceLimits`。
- 判定取已配置来源里**最重**的那个配置的上限：多路限制是设备级约束，来源可以先后启动，保守口径才不会让用户在某一路上把设备压死。
- 控制台按服务端口径显示：服务端用**运行中**来源各自的 `concurrencyLimit` 取最小值为设备上限，超出即在这台设备的来源面板上给出提示；检测端自评（已配置来源数）另存上报值作参考。

## 判定流程

1. 量化产物先在 CPU 上测（这一步本身是净收益，与是否用加速无关）。
2. 加速档与**同运行时、同精度**的 CPU 对照，按门槛判定；达不到就放弃该加速档。
3. 多路场景单独跑压力测量，按单路 ≥5 帧/秒 定路数上限。
4. 每步真机读数进[验证记录](90-验证记录.md)。

## 下一步与未决项

1. **GPU 落地的剩余部分**：端侧解析、加速链路与模型投放已完成；**服务端与接收端的多路限制代码尚未部署到 VPS**（发布动作），部署后还需按真实服务器独立通道跑一遍「下载 GPU 模型 → 来源自动走 GPU」的端到端核对。任务见[任务清单](06-任务清单.md#推理加速落地)。
2. 校准集换成真实场景画面（相机推流或本机相机采集），不再借用照片夹具。
3. **并发上限与设备面**：GPU 上限只扫到 32 路未触底；更小内存设备需重测。
4. **Windows 端量化：已实测，结论是不需要**（2026-10-11，用检测端同一套 `Microsoft.ML.OnnxRuntime.Managed` + `DirectML` 1.19.0 程序集）：

| 组合（桌面实测，10 帧中位数） | `yolo26n_320` | `yolo26m_640` |
|---|---|---|
| FP32 · CPU | 7.6 ms | 212.2 ms |
| **FP32 · DirectML** | **3.0 ms** | **16.0 ms** |
| INT8 · CPU | 7.6 ms | 102.5 ms |
| INT8 · DirectML | 6.6 ms | 37.3 ms |

DirectML 才是 Windows 的主要加速来源（640 上比 CPU 快 13.3 倍），而 INT8 在 DML 上比 FP32 慢 2.2–2.3 倍；量化只在纯 CPU 时有收益（640 上 2.07 倍）。**Windows 侧最佳组合是 FP32 + DirectML**。两端因此各自最优、互不冲突：Android 用 INT8 + CPU，Windows 用 FP32 + DirectML，同一基名分发两个精度即可，不需要跨端协商。边界：实测机是桌面 x86_64 + NVIDIA 显卡；检测端真实部署机若没有可用的 DML 设备，INT8 + CPU 会成为 Windows 侧正解，待真实检测机确认。
4. 完整量化（int8 I/O）的 LiteRT 产物造不出来（`onnx2tf` 严格全整数量化在 YOLO 解码段报 `Unsupported op: ROUND`），这是 GPU 路线唯一未排除的可能，要打通需换转换路径（Linux x86 / macOS）。
