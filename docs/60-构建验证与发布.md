# 构建验证与发布

负责：构建、验证和发布入口及授权边界。不负责：其他模块事实、任务状态或重复验证记录。更新时机：操作入口或约束变化时。


本文只维护可执行入口、授权边界和验证分类。模块事实见对应专题，验证结果见[验证报告](90-验证记录.md)，不在此复制完整报告。

## 内测迭代

测试默认使用当前版本的全套组件和当前配置、数据格式。协议或结构变更时同步相关端，按需重新配置或重建测试环境；不默认验证旧版本混用、增加数据迁移或保留旧入口。兼容需求只按 owner 明确指定的版本或数据范围执行，规则见 [AGENTS.md](../AGENTS.md#内测开发与迭代原则)。

## 授权保护

`node scripts/install-git-hooks.js` 为本 checkout 安装受版本管理的 `.githooks/`；已有其他 hook 时拒绝覆盖。pre-commit 默认拒绝暂存区的 VERSION 变化，pre-push 默认拒绝推送。`sync-version.js` 在写入前校验目标版本，`publish-release.ps1` 在非预检 / 非 DryRun 执行前校验发布版本。

只有 owner 已明确授权对应操作后，才在本次进程设置 `VISIONGUARD_OWNER_VERSION=<授权版本>`、`VISIONGUARD_OWNER_PUSH=1` 或 `VISIONGUARD_OWNER_RELEASE=<授权版本>`，结束后移除；发布授权允许该版本同步，不自动授权额外 push。这些变量是误操作保护，不能代替人类授权；测试只在独立临时仓库或夹具中设置。

合并后的本地任务分支自动清理，无需再次授权：先用 `git merge-base --is-ancestor <分支> main` 与 `git rev-list --count main..<分支>` 确认全部提交已在主线，并核对相关工作树干净。仍检出该分支的工作树先在原提交执行 `git switch --detach HEAD`，保留目录、忽略资料和证据，再从主线执行 `git branch -d <分支>`；删除成功后清理待办中的分支归属，未完成事项交主线承接。

项目 `.codex/rules/project.rules` 对直接的 push、tag 和 GitHub Release 写操作要求审批；规则依赖可信项目配置层、重启和沙箱审批路径，当前 full-access / never 会话不保证启用。参见 [Codex 官方规则说明](https://learn.chatgpt.com/docs/agent-configuration/rules)。规则按命令前缀匹配，不覆盖任意脚本包装、全局参数或 API 调用；Git 没有通用 pre-tag hook，直接 tag 也不能只靠 hook 保护。hook 可被 --no-verify 或配置绕过，脚本变量可被自行设置，因此仍保留 AGENTS 授权红线。新 checkout / worktree 需安装 hook；已有其他 hook 要手动整合，不修改全局配置。

发行说明读取 `docs/releases/v<版本>.md`，只在该目录 README 登记。普通迭代不运行发布入口，预检继续可用。

## 构建

仓库组件的统一构建入口（客户端 Release、服务含 Web）：

```powershell
powershell -ExecutionPolicy Bypass -File .\.agents\skills\visionguard-build\scripts\build-all.ps1 -Target All
```

可用目标为 `Server`、`WPF`、`WindowsResident`、`AndroidDetector`、`AndroidInference`、`AndroidNotifier`，也可使用组合目标 `Windows`、`Android`（包含相机、推理和通知三个 Android 工程）。脚本只编译并检查产物，不打包、不上传、不部署、不改版本。

视觉推理节点内部驻留程序的生命周期命令以源码为准：`open-detector`、`close-detector`（随主程序启动，主界面关闭后继续运行）。

构建结果必须按组件分别报告，并在完成后检查：

- 统一服务及 Web：`server/dist/index.js`、`server/dist/console/index.html`、`server/dist/camera/index.html`；先分别运行 `npm --prefix server ci`、`npm --prefix receiver/web ci` 与 `npm --prefix detector/web ci`，需要 Node.js 22.18 或以上
- 视觉推理节点统一入口：`detector/windows-package/bin/Release/VisionGuard.Detector.Windows.exe`；内部运行时位于 `runtimes/modern/` 与 `runtimes/legacy/`，各自只保留匹配的 `native\modern\`、`native\legacy\`，包根目录不得残留 `onnxruntime.dll` 或 `DirectML.dll`
- 视觉推理节点内部驻留程序：`detector/windows-resident/bin/Release/net472/VisionGuard.Resident.Windows.exe`
- 相机推流节点（Android）：`detector/android/app/build/outputs/apk/release/app-release.apk`
- 相机推流节点（Web）：`server/dist/camera/index.html`；快速回归在 `detector\web` 执行 `npm test`，构建用 `npm run build`（含 `tsc --noEmit`）
- 视觉推理节点（Android）：`detector/android-inference/app/build/outputs/apk/release/app-release.apk`；快速回归在 `detector\android-inference` 执行 `.\gradlew.bat :app:testDebugUnitTest :app:lintDebug`。已接入发布平台表 `android-inference`（产物 `VisionGuard-Inference-v<版本>.apk`，`-Target AndroidInference` 可单独发）；应用内更新入口在「设置 → 维护」，查 GitHub 稳定发行
- 通知节点：`notifier/android/app/build/outputs/apk/release/app-release.apk`

Windows 发行输出不得包含 `.pdb`、`.lib`、`.dll.config`、`.onnx`、`Assets/` 或 `alerts/`；模型按需下载，不随发行包分发。详细模型与项目文件边界见[模型资源](35-模型资源.md)。

## 仓库清理

[clean-repository.ps1](../scripts/clean-repository.ps1) 默认只预览一次性输入 helper 的 APK、class / dex 和专用测试签名产物，保留 Java / Manifest / 构建脚本。`-IncludeBuildIntermediates` 另纳入 Git 忽略的 MSBuild `obj` 与 Android `app/build` 下的 `intermediates`、`tmp`、`generated`、`kotlin`；不清空整个 `.local` 或 `build`。

```powershell
# 当前 checkout 的预览；可选中间文件也只列计划。
& .\scripts\clean-repository.ps1 -IncludeBuildIntermediates
# 只执行默认 helper 清理；可用 -WhatIf 再预演。
& .\scripts\clean-repository.ps1 -Apply
# 确认计划后删除中间文件；先结束构建 / Gradle / Kotlin 进程。
& .\scripts\clean-repository.ps1 -IncludeBuildIntermediates -Apply
# 多个明确指定的 checkout；脚本须从包含该入口的分支调用。
& .\scripts\clean-repository.ps1 -RepositoryRoot @('C:\Repo\VisionGuard','C:\Worktree\VisionGuard') -IncludeBuildIntermediates
```

计划与结果写入第一个目标仓库的 `.local/repository-cleanup-plan.json`。删除前重新核对绝对路径、Git 索引和目录内容，拒绝链接 / Junction / 越界路径、已跟踪文件及未知 helper 内容；构建中间目录含安装包、模型、凭据或性能轨迹时保留整个目录。源码、实际发行 / 测试包、运行目录、模型、签名 / 私有配置 / 账号、原始验证证据、依赖和共用 Gradle / Maven 缓存默认保留。脚本不结束进程，不接触设备、VPS 或 Git 状态；真实清理结果仍以报告为准。

## 控制台认证连接诊断

控制台出现认证超时后，先保留原标签页。开发者工具 Console 可按 `[RelayAuth]` 筛选；刷新过的页面可读取本标签页有界记录：

```javascript
JSON.parse(sessionStorage.getItem('visionguard.connection-log') || '[]')
```

记下 `attemptId` 和发生时段，服务端读取同一时段 `journalctl -u visionguard.service` 的 `[WsAuth]`，按相同 `traceId` 关联；没有客户端标识的节点仍有服务端随机 `connectionId`。每次尝试单独计时，不用两端墙钟相减推断网络耗时。只记录建连 / 认证 / 关闭等状态变化，不输出周期心跳。

- 浏览器 `connect-timeout` 且同标识无服务端接入记录：尚不能确认已到达应用 WebSocket 层；DNS、TCP、TLS、代理与浏览器回调延迟需结合浏览器 Network 另查。源码提示为“网络连接超时”，与打开后独立计时的“认证响应超时”区分；两类超时均按退避自动重试，真实会话失效才要求重新登录。重试独立于心跳轮询；后台浏览器节流可能推迟回调。部署状态见[验证记录](90-验证记录.md)。
- 服务端 `socket-open` 后 `auth-timeout`，`firstFrameReceived=false`：已接入，但认证首帧没有到达服务端处理器。
- 服务端 `auth-success`，浏览器却等待认证超时：服务端已接受认证；回执传输或浏览器处理仍需核对，不能把发送等同于收件。
- `auth-rejected` / `invalid-session`：服务端实际拒绝了会话，区别于前端建连计时超限。

浏览器仅同一标签页保存最近 100 条，每次写入清理 24 小时以前记录；存储禁用时使用 Console。日志不含凭据或原始消息。这个能力需要将相应服务 / Web 改动部署后才在线生效；构建和回归不代替生产取证。

## 协议版本闸门

内测阶段各端版本快速更替，旧安装不该继续占用生产资源或刷日志。统一服务在**上线部署实例**上启用闸门：只服务与本版同版本的端点。

- 各端在 WS 认证、媒体通道认证和 `/api` 请求里声明本端版本；其余端取自身发布版本，控制台与 Web 相机是服务端托管的页面、启动时先读 `/health` 的 `version` 再发请求（登录响应里的版本只用于校验已保存的会话）。缺字段（API Key 时代的旧包）与版本不符一并出局。**媒体通道按连接的第一条消息判闸门**：客户端必须把带 `version` 的认证作为首帧，心跳等其它消息都要等认证回执之后才发（Android 推理节点曾因看门狗抢发心跳，整条媒体连接被判 `protocol mismatch`，见[验证记录](90-验证记录.md)）。
- 出局方式为静默：WS 关闭码 4001 `protocol mismatch` 且**不回 `auth-result`**；HTTP 返回 `426` 空响应。既不解释也不保留兼容分支，避免旧端重试放大日志。
- 出局对 `/api` 全路径生效，**包括登录与更新查询**：旧安装既登不上、也查不到更新，只能手动装包。这是内测不保留兼容的代价（实测不带版本头的 `POST /api/account/login` 与 `GET /api/update` 均返回 `426`）。
- **声明的版本同时决定可见性**：闸门开启的实例上，端点只有按本版协议声明过才出现在节点目录（`GET /api/devices`、控制台推送的 `device-list` 与控制台节点名册 `notification-scopes`）和推流视图里。被拒端点会在出局前把这次声明写进设备记录（控制通道 `auth`、媒体通道 `media-auth`、`/api` 请求头；登录请求头也一并记录），因此目录、名册、推流列表、绑定关联随之隐藏，直到它按本版协议重新声明；声明缺失同样按未声明处理。登录即声明，值没变时不重复落盘。本地/测试实例（闸门关闭）不隐藏任何设备。**三条控制台通道共用同一道判定**（`AccountStore.visibleUnderGate`）：`/api/devices` 与 `device-list` 走 `directoryDevices`，节点名册走 `identities` → `registeredNodes`，漏掉任何一条都会让旧端点在控制台里残留。
- 闸门只按版本聚合计数，每 5 分钟最多输出一行 `[Protocol] legacy-protocol-dropped`（含 `servedVersion` 与出局版本分布），不逐条打印。
- **本地服务默认不启用闸门**：跑链路、跑 UI 检查可以用任意端版本，不必对齐构建。需要本地复现门禁时设 `VISIONGUARD_PROTOCOL_GATE=1`；部署实例由 `NODE_ENV=production` 默认启用，启动日志会打印闸门状态。
- **闸门与版本声明由 CI 守**：`scripts/check-protocol-declarations.js` 在 Development checks 与 Documentation audit 两个工作流里跑，逐条断言——三条通道都过闸门（控制 WS、媒体 WS、`/api`）、每个端在每条通道都声明本端版本（Windows / Android 三个端 / 控制台 / Web 相机）、推流端在媒体通道声明来源身份、节点目录可见性与解除绑定权限按本版声明判定、版本只有一个来源（根 `VERSION` → `server/package.json` → `config.version` → `PROTOCOL_VERSION`）、以及**代码里出现版本字面量的文件必须被 `scripts/sync-version.js` 收管**（否则发版后这个端仍声明旧版本，会被闸门当成旧端踢掉）。规则改动与护栏一起改，别只改一处。
- **打包产物也要按版本声明查**：`scripts/check-apk-protocol-version.js` 解析 APK 内 `classes*.dex` 的字符串表，断言包内出现文件名里的版本号；发布流程在写发行元数据前对每个 Android 产物强制跑一遍。成因是 Kotlin 会把 Java 的 `static final` 常量（`BuildConfig.VERSION_NAME`）在编译期内联成字面量，而且增量构建不跟踪这个生成文件的变化，复用旧 class 时包就会一直声明旧版本，而 manifest 与设置页显示的版本仍是对的（2026-10-14 通知节点 0.7.3 的包实测声明 0.7.1，0.7.4 构建又抓到同类残留，见[验证记录](90-验证记录.md)）。因此三个 Android 端的协议版本都写成**由 `scripts/sync-version.js` 收管的源码字面量**（Kotlin 源码常量变化会被增量编译跟踪），`check-protocol-declarations.js` 的 `version-runtime-source` 检查禁止声明处再出现 `BuildConfig.VERSION_NAME`。
- 连带成本：服务端升级后，未升级的端会被拒，窗口期内要先升级再连接。升级路径：Android 三个端与 Windows 都有应用内更新（推理节点的入口随 0.7.0 上线），Web 两侧随服务发布，统一服务自身由发布流程更新。通知节点没有应用内更新，只能手动装包。

## 服务器资源维护

保留策略以 [AGENTS.md](../AGENTS.md#服务器资源与保留) 为准。只读盘点不构成删除、部署或重启授权；共享 journal 保留调整由 `Server-infra` 协调并另行授权。实施状态只在[待办](06-待办.md#待办)维护，实际清理与未覆盖项只记在[验证记录](90-验证记录.md)。

[cleanup-pending-resources.ps1](../scripts/cleanup-pending-resources.ps1) 仅处理已核对的三个本机残留文件、两个空目录及 journal 只读盘点。它与上方通用仓库清理入口范围不同，仅接受固定路径和 2026-10-09 盘点的 SHA256；内容变化、Git 已跟踪、链接 / Junction 或目录出现任何文件时保留并报非零退出码。删除前检查相关任务进程与打开文件，不结束进程。输出文件逻辑字节数，不宣称实际磁盘释放量；其他 `.local` 内容、保留清单、工具、签名、证据及当前 Python 缓存保留。

```powershell
# 在当前项目目录运行预览；目标可明确指定另一 checkout。
& .\scripts\cleanup-pending-resources.ps1 -RepositoryRoot 'C:\Users\xgwnj\Documents\XGWNJE\VisionGuard'
# 确认上一步计划后，本机删除；可先加 -WhatIf 预演。
& .\scripts\cleanup-pending-resources.ps1 -RepositoryRoot 'C:\Users\xgwnj\Documents\XGWNJE\VisionGuard' -Apply
# 可选：只读连接 SSH 配置中的别名，读取 journal 用量、磁盘与保留参数。
& .\scripts\cleanup-pending-resources.ps1 -InspectJournal -SshAlias xgwnje
```

已交付到主工作目录 `.local/cache-maintenance/cleanup-pending-resources.ps1` 的副本可直接运行，自动定位所属 checkout。默认不联网；`-InspectJournal` 使用已有 SSH 密钥和已知主机记录，不输出日志正文，不修改 journal、服务、回滚点或生产资料。只读盘点失败时本机删除尚未开始；重复执行时缺失项显示 `Absent`。拒绝项保留，其余合格项仍可删除；`Preserved` / `Failed` 表示保留或失败，不能当成全部清理完成。

正式发布仍只用 `publish-release.ps1`。上传 / 替换前短暂停止原服务，备份代码、依赖、账号 / 配置 / 私有数据、systemd / Nginx 配置、Node 运行时及旧元数据引用的安装包和模型；随后恢复原服务。不可变模型、包及运行时用硬链接降低占用，私有数据独立复制并核验 SHA256 / 属主。备份放在服务 `backups/snapshot-*`，`previous.json` 指向唯一完整回滚点。公网上线健康、发行文件和 WebSocket 核验全部成功后，核验待保留快照、更新指针，再核对进程占用，删除未使用的旧快照及当前 / 回滚元数据均未引用、未被读取的历史包。发布失败保留原回滚点和 `transaction.json` 对应的待核验快照，后续发布停止，须先查明失败并处理该事务；不自动删除失败备份或重试部署。`server-resource-maintenance.py` 是发布脚本内部备份助手，不是另一个发布入口。

Web「设置 → 统一服务缓存」可盘点 / 清理当前账号；管理员还可处理旧公共截图目录。只删除超过 `SCREENSHOT_TTL_HOURS`（默认 72 小时）且无有效事件引用的图片，保留有效事件引用至事件期限；无法读取引用记录时保留并报失败。后台按 `CLEANUP_INTERVAL_MS`（默认 1 小时）执行相同策略，覆盖账号与旧目录。不会操作账号、配置、模型、发行包、备份或任意输入路径。

节点详情的「节点缓存」要求在线且声明 `cache-maintenance`，通过 `cache-inspect` / `cache-clean` 和匹配的 completed 回执展示实际文件结果。Windows 视觉推理节点按 7 天 / 1 GB / 5000 张清理截图；读取中删除失败会计入失败数。Android 包暂存按 7 天回收，下载 / 校验与维护使用同一锁，准备安装的包受保护，交给安装器时续期 7 天；下载缓存上限 256 MB，超限拒绝新增。通知节点当前账号诊断导出保留 24 小时、单份最多 3 MB、至多 20 份 / 总量 40 MB；近期分享文件、持久音频、报警、配置和活动日志不清理。历史无账号归属的诊断导出不开放远程删除。

盘点 / 清理结果列总文件与字节、可回收文件与字节、删除数量和失败数。服务端按 inode / 链接计磁盘块，保留硬链接不计释放；节点无法可靠计量释放块时明确显示未计量。清理结果是本次操作前的盘点快照，完成后可再次盘点；连接中断或超时显示结果待核实，不计作成功。

测试资料先核对当前服务、进程打开文件和其他任务占用；正在使用的独立通道、可复用工具 / 夹具、源码、必要原始证据及签名 / 私有配置保留，只删除明确失效的一次性 staging、旧测试备份和已解压下载压缩包。节点日志有界：通知日志 1 MB + 一份旧日志，Windows 驻留日志 1 MB + 一份旧日志、报警投递日志同样轮换；正常服务只记录首个检测心跳，周期诊断仅在 `VISIONGUARD_MEDIA_DIAGNOSTICS=1` 时输出。

自行验收：部署同契约的服务 / Web / 节点后，在设置盘点与清理当前账号截图；普通账号不得清理旧公共目录或另一账号。在各在线节点盘点、清理、再盘点，核对过期减少、近期 / 使用中数据保留、离线禁用、重复清理为零及失败 / 超时提示。真实 UI、下载 / 安装期间清理、持续运行和下一次真实发布的备份轮换由 owner 验收，不以本地模拟替代。

## 运行与设备验证

### 设备验收操作

- 视觉推理节点的运行、交互、采集验收默认启动 Release 真实 WPF 主程序并保持可见；不得用隐藏 / 无头测试窗或生产类库 smoke 替代，结束关闭本轮启动的窗口。
- WPF 人员 smoke 使用独立可见动态视频窗口，经 WindowHandle 捕获，逐路断言至少一帧 person 与 FPS；窗口数量随覆盖来源数量，四路保留回归基线，容量扩展同步脚本。静态图片不能替代动态视频；维护脚本的既有覆盖限制单独报告。
- Android 真机 UI / 运行 ADB 和模拟器调试保持 scrcpy、模拟器窗口或等效预览可见，结束关闭；纯构建、签名验证和只读设备信息可不启动预览。
- Android 推理节点的构建、单元测试与 lint 只证明代码级契约，不证明加速档在具体设备上的实际生效与回落、持续推理的发热与功耗、长时间锁屏存活、远程镜头弱网表现或平板布局；这些必须真机验证，由 owner 目检，结果与未覆盖项登记到[验证记录](90-验证记录.md)。
- 表单优先 ACTION_SET_TEXT 一次填写，先核对应用与字段，不用软键盘逐字输入；凭据不经系统剪贴板或命令参数，临时输入工具 / 请求文件验收后移除。
- 不擅自修改锁屏、休眠、唤醒设置；没有 owner 明确授权的解锁方式或唤醒异常时停止，等待 owner 处理。UI 分批交付由 owner 真机目检；视觉和较长验证先交 owner 选择。
- owner 已授权小米 15 的软件锁屏测试自动解锁。先核对连接设备为小米 15，再通过 `[Environment]::GetEnvironmentVariable('VISIONGUARD_XIAOMI15_UNLOCK_PIN', 'User')` 读取当前 Windows 用户环境变量，使用系统锁屏键盘输入；变量缺失时停止。密码值不打印、不写入仓库、文档或测试日志，不经系统剪贴板或命令参数；该授权不允许修改设备安全设置。
- **Android 装包 / 重装统一走 `scripts/install-android-apk.ps1`，不要用裸 `adb install` 反复重试**。部分厂商（MIUI / HyperOS 等）会弹带倒计时的「USB 安装」确认；错过一次就是一次全量上传重来，几十到几百 MB 白扔。脚本的做法：安装命令后台跑，同时按 ~350ms 轮询焦点窗口，只在安装器 / 安全中心在前台时才解析界面并点确认；按钮坐标从 `uiautomator dump` 的节点 bounds 算（不写死），普通点击点不动自动升级长按；判定成功不看弹窗消失、也不只看 adb 退出码，而是独立核对包版本、最后更新时间（必须刷新）与已安装 APK 字节数（与本地包一致）。参数：`-PackageName` 必填才能做上述核验，`-ForceSystemInstaller` 强制走系统安装器（已验证倒计时确认只在这条路径出现时用），`-RespondOnly` 只补确认已弹出的弹窗而不重传。厂商弹窗可能要等它自己联网查询后才出现（实测 MIUI 的「未查询到此应用的 ICP 备案信息」慢到两分钟以上），所以等待窗口默认 300 秒；设备锁屏时无法响应确认，脚本会明确报错而不越权解锁。报告与界面转储写在 `-EvidenceDirectory`（默认 `.local/apk-install/<时间戳>/`）。

### 基础账号与客户端登录

一个账号对应一套系统。统一服务自动初始化管理员 `xgwnje`，现有同名账号沿用密码；全新数据目录的随机初始密码保存在 `VISIONGUARD_DATA_DIR/initial-administrator.json`，仅在私有环境查看，不上传或写入公开配置。已有有效管理员时不重新初始化。管理员从 Web 控制台的“账号管理”创建账号、启用/禁用、重置密码与设置管理员权限；至少保留一个启用的管理员，禁用、重置密码和变更权限会撤销该账号会话。

离线维护仍可在服务停止时指定独立数据目录使用 CLI；密码仅经环境变量或标准输入传入：

```powershell
$env:VISIONGUARD_DATA_DIR = '<absolute-private-data-directory>'
$env:VISIONGUARD_ACCOUNT_PASSWORD = '<private-password-at-least-8-characters>'
node scripts/provision-account.js <username>
Remove-Item Env:VISIONGUARD_ACCOUNT_PASSWORD
```

账号库存储在数据目录的 `accounts.json`，密码与会话分别保存派生值和摘要；该文件与账号数据必须保持私有。当前 JSON 存储只支持单服务进程，不提供公开注册入口。在线修改账号应通过账号 API，不与离线创建命令同时写库。

Web 打开同服务 `/console/` 输入账号密码；Android 和 Windows 登录同一账号，设备自动登记，驻留自动获得主节点子会话。Web 会话在页面内存，Android 用 Keystore、Windows 用 DPAPI 保存会话。四个登录入口支持可选的账号密码记忆，规则及检查见[账号密码记忆](#账号密码记忆)。退出、改密和解绑会撤销相关会话。Web 节点详情可改名、解绑及选择镜头目标；账号内只有一个推理节点时自动关联。

Release 内置正式地址 `https://visionguard.xgwnje.cn`，登录只填写账号密码，初始设备名称由服务自动生成，进入程序后再修改。Android Debug 与 Windows Debug/显式隔离配置才允许填写测试地址；旧 Android 隔离会话在 Release 中不使用。Web 使用当前页面同源服务。测试不得混用正式账号库；统一时间与通知范围均按账号保存，历史不触发声音。

### 账号密码记忆

Web、Windows / Android 视觉推理节点、Android 相机及通知节点的登录页默认未勾选“记住账号密码”。勾选后仅在登录成功时保存，下次进入登录页自动填入并恢复勾选；取消立即清除，退出登录保留记忆。未新增自动登录，Windows / Android 的原会话恢复方式保留。账号字段为 3–64 个 ASCII 字母、数字、点、横线或下划线且首字符为字母或数字，登录密码为 1–256 个 UTF-16 单元；改密的最小长度仍为 8。

Windows 使用当前用户 DPAPI，记忆文件与会话分开、按规范化服务地址隔离；Android 使用本应用 Keystore / AES-GCM，绑定服务地址和组件，排除备份与设备转移。Web 在同源 IndexedDB 保存不可导出的 AES-GCM 密钥与密文，要求 HTTPS 或 localhost，密钥仍可供同源脚本使用；不降级为明文保存。Web / Android 在本机改密成功后清除旧记忆；其他设备修改或重置密码后，原记忆须由用户重新填写并登录更新。

快速回归：Web 控制台运行 `npm --prefix receiver/web test`、Web 相机运行 `npm --prefix detector/web test`，三个 Android 工程运行 `:app:testDebugUnitTest`、`:app:lintDebug`；Windows 实际 DPAPI 检查运行 `powershell -ExecutionPolicy Bypass -File scripts/check-remembered-login-windows.ps1`，仅使用 `.local/remember-login-windows-probe/accounts/` 的临时随机凭据，不启动主窗或连接服务器。

真实界面由 owner 自行检查四个入口：首次未勾选；勾选登录后退出再进入，确认自动填入且勾选恢复；取消后重新打开，确认不再填入；重新勾选并登录另一账号，确认下次填入新账号。Android / Windows 的有效会话可能直接恢复，需退出后检查登录表单。本机模拟预览只证明 UI；本轮覆盖和产物见[验证记录](90-验证记录.md)。

### 本地服务

本地服务是跑在本机、面向局域网的隔离统一服务实例，只用于 UI 模拟预览、开发中的验收与调试。所有组件统一使用本地账号与模拟临时数据；流程与字段边界见[本地预览与数据边界](70-UI设计规范.md#本地预览与数据边界)。合成节点、事件、截图和回执只能证明 UI 预览，不构造本地模拟业务链路。

预览、验收、调试只有一条入口，地址与端口由服务启动时确定，各端从端点清单与局域网信标取：不手填地址、不做 adb reverse、不区分第二种包形态。

```powershell
# 起本地服务（自动挑空闲端口、写端点清单、广播发现信标、打印资源摘要）
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Service
# 只有要检查「有数据」的样子时才打开模拟数据（场景节点 / 事件 / 截图）
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Service -MockData -Scene limits
# 构建并装到真机（默认先清理该组件已装的发行版 / 本地版实例）
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Android -Component Inference -Install -DeviceSerial <序号>
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Windows -Scene limits
# 只校验并复用资源缓存（加 -Refresh 才补缺失项）
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Resources
# 结束本轮（含 Windows 隔离实例及驻留）
powershell -ExecutionPolicy Bypass -File .\scripts\ui-preview.ps1 -Target Stop
```

- **端点清单**：`.local/e2e-server/local-service/endpoint.json` 记 `lanUrl`（真机用）、`loopbackUrl`（同机 Windows / Web 用）、`emulatorUrl`、端口、账号文件与数据目录。服务端口每次从 `4320–4399` 取空闲且与上轮不同；控制台即 `loopbackUrl/console/`。
- **模拟数据是开关，默认关闭**：只有需要检查「有数据」的样子时才加 `-MockData`（可选 `-Scene normal|limits|empty`），场景页固定 `http://127.0.0.1:4319/`。其余流程默认不启动它，并且会把上一轮遗留的停掉——停止时脚本会解绑自己的模拟节点，所以别的流程里不会出现模拟设备，也不会被误当成真实节点。模拟数据产生的历史事件保留在事件记录里。
- **自动识别**：服务每 2 秒往局域网广播 UDP 信标（`udp/45899`，载荷含 `service=visionguard-local`、通道与端口）；Android 本地服务版启动先按通道找服务、找到就用它，找不到才回落到构建时内置的局域网地址，因此换端口不需要重新构建或安装。信标与本地发行源只在设了对应环境变量的本地实例启用，部署实例行为不变。
- **账号与数据**：`vg-test` 供有数据界面，`vg-isolation` 供空账号；随机密码在 `.local/e2e-server/local-service/test-accounts.json`，管理员 `xgwnje` 初始密码在同目录 `initial-administrator.json`，凭据不写到说明或终端。数据目录跨会话复用，不因新一轮调试重建账号或设备登记。
- **资源缓存（唯一一份）**：模型只放 `server/data/models`（`/models/<文件>`，投放用 [deploy-int8-models.ps1](../scripts/deploy-int8-models.ps1)）；组件包只放 `server/data/releases`（`/releases/<文件>`，元数据 `server/data/releases.json`）。`-Target Resources` 逐个核对大小与 SHA256，只补缺失项（从 GitHub 稳定发行取同名资产），不重建已有缓存；Windows 预览的模型目录直接指向同一份缓存。`-FixtureComponent` / `-FixtureVersion` 可把本地构建登记成本地夹具包（写忽略的 `releases.local.json`，仅本地实例可见），`-ClearFixtures` 清理。
- **组件下载一致**：本地实例提供与部署实例同形状的 `/api/update`（叠加本地覆盖层）与 `GET /api/local/releases`（GitHub 发行形状，下载地址为指向本实例的绝对地址）；Android 本地服务版与 Windows 隔离环境把更新查询指向本地服务，离线也能走完检查 → 下载 → 校验。模型下载同样取**当前会话的服务地址**：登录在本地服务上就从局域网 `/models/<文件>` 取，不再回落到构建时内置的正式地址。
- **实例清理**：同一条流程内允许卸载该组件已装的发行版 / 本地版实例，避免新旧实例互相干扰；只限 `com.xgwnje.visionguard.{detector,inference,notifier}` 与同名加 `.uipreview` 的精确包名，逐个核对后执行并留证，`-SkipInstanceReset` 可保留。
- **只动自己起的进程**：`Stop` 只停端口属主能核对到本项目脚本的实例，未知占用直接报错。

Windows 从真实 Release 统一入口启动，账号、配置与日志位于 `.local/console-preview/windows/`，按预览账号**静默登录**（脚本把凭据经 `VISIONGUARD_PREVIEW_SIGNIN` 递给应用；`-LoginUi` 停在登录页，并先清掉已保存会话）；正常 4 路、上限 16 路、空场景为 1 路未配置来源，监控保持关闭，`PrepareWindows` 只准备数据。Android 经 [ui-preview.init.gradle](../scripts/ui-preview.init.gradle) 从 Release 配置构建，包名追加 `.uipreview`、标签带“UI预览”，构建时注入通道、端点与 `vg-test` 账号，**装完打开即已登录**，不覆盖正式包；APK 与摘要在 `.local/console-preview/packages/`。构建同时跑现有 JVM 单元测试，测试结果不替代设备验收。**Web 两侧（控制台与 Web 相机）同样免登录**：实例把测试账号经 `VISIONGUARD_PREVIEW_SIGNIN` 交给服务端，`/api/account/preview-signin` 只对回环请求返回凭据（部署实例不设该变量、返回 404），页面先读 `/health` 就位协议版本再自动登录；地址带 `?login` 停在登录界面走完整流程。

### 真实服务器独立测试通道

业务逻辑整体链路验收统一在真实服务器上另开测试通道，由实际镜头、推理、统一服务、控制台和通知组件完成业务流程。服务实例、监听入口、运行目录、账号库与数据独立于正式业务；`VISIONGUARD_CHANNEL` 只是实例标签，不能单独承担隔离。不得用本地服务、合成节点、直接注入报警或伪造收件回执替代链路验收；本地编译、单元、契约与组件探针保留为补充检查。

## 发布授权

先从当前 Server-infra 服务归属确认目标，再传 `-ServerEnvPath`；旧 `server.local.env` 可能仍指向迁移前主机。预检按公网健康与 SSH 目标进程的运行时间核对路由，不匹配即在写入前停止。现有普通 SSH 账号可在私有连接文件设置 `SSH_SUDO=1`，通过既有免密 sudo 执行发布与 SFTP；不修改 SSH、sudo、DNS 或代理授权。

内测源码使用 `0.x.y`，根 `VERSION` 仍是唯一权威版本源。owner 只授权调整源码版本时使用：

下列写入命令均须先按[授权保护](#授权保护)设置本次进程的对应版本变量；预检和 DryRun 不需要。执行结束移除变量，不能把它持久化到用户环境或生产配置。

```powershell
node scripts/sync-version.js <version> --source-only
```

它同步 Windows 入口、运行时及驻留、Android 三个工程、服务、Web 与 README；通知节点直接读取根版本。已有测试下载包的 `server/data/releases.json` 保留实际版本、文件名和大小，不指向未生成的 0.x 发行包。Android 版本重置后 versionCode 也降低，已有 4.x 安装不能直接覆盖安装当前 0.x 包；需在独立测试设备中重新安装。本机私有验收包和已运行测试服务不随源码同步自动更新。

正式发布唯一入口：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\publish-release.ps1 -Version <version> -Target All -UploadVps
```

该命令会同步版本、构建、准备签名包、更新 release 元数据、按目标上传并可部署统一服务；每一步都需要明确发布授权。仅检查前置条件时使用 `-PreflightOnly`，明确只发客户端时使用 `-SkipServerDeploy`。GitHub push、tag 和 Release 仍需显式开关。

发布预检的第一道闸门是 **CI 必须绿**：脚本按 `-GitHubTagTarget`（默认 `HEAD`）查该提交最近一次 Development checks 运行，不是 success（含 cancelled、仍在跑）立即中止并打印结论与运行链接；提交还没推上去时 GitHub 没有运行记录，同样拒绝——**先推送、等 CI 跑完再发布**，本地绿灯不能顶替。GitHub-only 入口跑同一条检查。v0.7.0 与 v0.7.1 都是在 CI 红着的情况下发出去的（发布脚本原先只核对本地构建、签名、上传与线上端点），该闸门用于堵住这个缺口；CI 工作流本身不改。

发布的 `All` 包含 Windows 整包、相机 / 通知 / 推理三个 Android 签名包、服务及 Web；`Android` 发布这三个 Android 包，Android 控制台源码、构建、发布及接入已移除。通知节点可用 `-Target AndroidNotifier`、推理节点可用 `-Target AndroidInference` 单独发布（默认 `All` 行为不变）。服务端更新查询键为 `wpf`、`android-detector`、`android-notifier`、`android-inference`；历史 `android-receiver` 下载元数据保留，不能作为新发布目标；相机与通知客户端改查 GitHub 稳定发行；推理节点的应用内更新入口在「设置 → 维护」，同样查 GitHub 稳定发行（需发布时把推理节点包上传到 GitHub 发行）。当前基础设施已迁入同级 `Wenje-Server/Server-infra`，发布时显式传入 `-ServerEnvPath ..\Wenje-Server\Server-infra\server.local.env`；其他工作区按实际位置解析。不能改写真实凭据或沿用旧路径。上线前备份运行代码、配置和私有数据；发布上传按 SHA256 跳过相同文件，同时核验 Windows 所需公共模型。

部署使用统一服务专属的 Node.js `24.21.0`，可用 `-ServerNodeVersion` 指定其他 24.x 版本。脚本从官方发行目录下载 Linux x64 运行时并校验 SHA256，保存在运行根目录的 `runtime/`；systemd drop-in 指向该运行时，不修改其他服务的全局 Node.js。部署后核对实际进程路径与服务版本。

发布前必须确认 Android 签名材料、Windows ZIP 清洁度、元数据大小和目标范围；发布后才可执行公网 `/health`、`/api/update`、`HEAD 200` 和 byte-range `206` 验证。正式反向代理须同时升级 `/ws` 与 `/media/ws`，配置模板为 `server/nginx-visionguard.conf`；控制连接成功不能证明媒体入口可用。`node scripts/check-websocket-entrypoints.js` 无需账号，分别断言两条入口的 101 与握手摘要，不发送业务数据；部署后及公开 GitHub 发行前必须通过，失败保留草稿。发布脚本是唯一的正式打包/部署实现。

需要停留在草稿供 owner 确认时，使用 `-GitHubOnly -CreateTag -CreateGitHubRelease -DraftOnly`，复用已构建且签名校验通过的包；该模式禁止 VPS 上传及部署，后续经授权去掉 `-DraftOnly` 公开发行。

全套版本已部署、但后续公网检查中断且 `backups/transaction.json` 仍保留时，使用同一入口的 `-FinishRelease -Target All -CreateTag -CreateGitHubRelease`，并传入原标签提交 `-GitHubTagTarget` 与实际 `-ServerEnvPath`。它核对运行服务、服务器版本 / 代码 / 元数据 / 发行附件摘要及原待确认回滚备份，再重新检查健康、更新 / 下载和两条 WebSocket 入口，成功后完成备份轮换与公开草稿；不重新同步版本、构建、上传或部署。版本、附件或备份不匹配时保留事务并停止；没有待确认事务时使用普通或 GitHub-only 流程，不删除事务文件来重试。

GitHub 发布先创建草稿，上传后逐个核对文件名、数量、上传状态、大小与 GitHub SHA256 摘要，再公开稳定版。草稿通过已认证的 `gh release view` 取得发行 ID，按 ID 读取完整资产；REST 标签入口只返回已公开发行，不能用来验证草稿。校验失败保留草稿；已公开的同版本发行拒绝覆盖，须使用新的授权版本。Windows、相机、通知与推理节点按组件查 GitHub 稳定发行；Web 和统一服务通过源码／服务发布更新，不采用客户端更新器；推理节点另有统一服务 `/api/update?platform=android-inference` 的元数据与资产。上述脚本实现不构成实际发布授权。

**分端上线（某端本次不发布）**：`-Target` 是单值，要发多个端就按端分批跑（例如 `-Target Windows -UploadVps`、`-Target AndroidNotifier -UploadVps`、`-Target Server -UploadVps`）。未发布的端在 `server/data/releases.json` 的**该平台条目内部**标 `"heldBack": true` 并保持上一个已发布版本，使更新接口继续返回旧版本而不是指向不存在的文件；`sync-version.js` 与 `publish-release.ps1` 会保留并跳过该条目。`check-docs`、`publish-release.ps1` 的 GitHub-only 资产收集与 `.github/workflows/release.yml` 都会跳过 heldBack 平台并给出提示；但 GitHub Release 两条入口在「一个平台都没对齐目标版本」时仍会失败，避免版本号打错时发出空 Release。

## Android 更新器专用回归

通知工程的 `ClientUpdaterTransportTest` 需要隔离的旧 Debug 应用和同包名／签名的当前 APK。使用[测试专用 Gradle 初始化器](../scripts/android-update-test-fixture.gradle)，先构建当前包，再把它作为 `current-client.apk` 加入旧版测试 APK：

```powershell
# 在 notifier/android 执行；保持已连接设备的可见预览
.\gradlew.bat -I ../../scripts/android-update-test-fixture.gradle :app:assembleDebug
New-Item -ItemType Directory -Force ../../.local/updater-device-fixture/assets | Out-Null
Copy-Item ../../.local/updater-device-fixture/current/app/outputs/apk/debug/app-debug.apk ../../.local/updater-device-fixture/assets/current-client.apk
.\gradlew.bat -I ../../scripts/android-update-test-fixture.gradle -PvisionguardUpdateFixtureOld=true :app:assembleDebug :app:assembleDebugAndroidTest
```

旧包与测试包位于 `.local/updater-device-fixture/old/app/outputs/apk/`，仅安装到选定的测试设备并运行该类；若已存在 `.acceptance` 包，先确认属于本轮测试，不能为避免降级限制删除用户原应用。初始化器只允许明确 Debug／测试任务：旧版号只用于本机测试夹具，根 `VERSION` 和正式版本不变。普通测试 APK 不携带该资产时会跳过此类。GitHub 元数据和下载地址仅在测试 APK 中拦截，实际 HTTP 下载、大小／摘要、PackageManager 身份和 FileProvider 校验照常执行；显式 instrumentation 参数 `-e liveUpdates true` 另启用真正 GitHub 查询及 UI 线程退出回归。

默认只验证权限页交接。获得实际安装授权后，先在系统界面允许本轮隔离包安装，再以 `-e installHandoff true -e class com.xgwnje.visionguard.notifier.ClientUpdaterTransportTest#actualInstallerHandoffWithOperatorApproval` 单独运行安装测试。调用者与候选文件保留 60 秒，供处理厂商确认页；提前结束调用者可能撤销 URI 读取授权。测试完成只证明交接，必须另核验安装后的包名、版本、签名和 APK 摘要。USB 安装提示有倒计时，应在安装命令运行期间观察并及时确认，不能等命令超时后再检查；不能凭授权提示消失判断安装成功。不要在 instrumentation 使用 UiAutomation 时并发运行另一个 `uiautomator dump`。结束后卸载本轮测试包，关闭预览。

## 配置与服务边界

- 统一服务真实账号库、会话、TLS 私钥及生产配置使用独立私有目录或部署环境变量，不能提交。
- 发行客户端只填写账号密码，服务地址内置；设备、默认名称、组件与驻留身份由服务签发，不注入 API key、设备 ID 或通道。Windows Debug 或显式隔离配置可使用 `VISIONGUARD_SERVER_URL`，Android Debug 可在登录页的本地服务设置里改地址；普通 Release 不受测试地址覆盖。
- 本地签名配置位于被忽略的 `.local/` 和 Android `local.properties`，不与账号配置混用；移工作区时按需额外备份签名材料，不能提交到 Git。
- 服务默认 HTTP；配置 `VISIONGUARD_TLS_CERT_FILE` 与 `VISIONGUARD_TLS_KEY_FILE` 可启动独立 HTTPS/WSS 测试实例。测试需独立进程、端口、数据目录和账号库，不覆盖线上目录、监听或代理配置。
- 开发 CI 在 `.github/workflows/development.yml`：服务/Web 契约与构建、文档及 `check-ui-theme.js` 跨端主题/文字对比守卫、`python scripts/generate-icons.py --check` 品牌导出一致性、三个 Android 的 Debug 单测/lint/构建与 Release lint/编译检查，以及 Windows 双档构建与媒体探针。Release 编译仅在 Gradle 命令行使用 unsigned 开关，不配置签名、不发布包。品牌导出检查依赖 Pillow，安装及再生成方式见 [`icon/README.md`](../icon/README.md)。CI 不使用生产凭据、不发布，云端执行结果须单独核实。
- VisionGuard 正式域名：`https://visionguard.xgwnje.cn`；根域 `https://xgwnje.cn` 不是新客户端服务地址。
- 当前 VPS/DNS/SNI 事实由 `Server-infra` 项目维护；不要运行旧式 `server/deploy.sh --nginx` 覆盖现有 SNI 架构。
- `VERSION` 只由 owner 明确授权的版本流程修改；普通构建、测试、修复和文档治理不得改动它。

## 文档审核

```powershell
node scripts/check-docs.js
node scripts/scan-guardrails.js --check
node --test scripts/check-docs.test.js scripts/release-workflow.test.js scripts/check-powershell-encoding.test.js scripts/scan-guardrails.test.js
```

审核会检查 Markdown 链接和锚点、UTF-8 无 BOM、版本来源、组件入口、四个 WS 角色、模型打包边界、Skill 与脚本契约、现有组件命名与产品边界和旧入口不存在。新增或删除文档/Skill/入口后必须先更新对应唯一来源，再运行审核。

`.github/workflows/docs-audit.yml` 在 PR 与 `main` 推送时运行上述静态检查，其中 `node scripts/scan-guardrails.js --check` 是护栏体检的硬门禁——工作流引用了不存在的脚本或目录、步骤带 `continue-on-error: true`、检查脚本里有恒真断言、非测试检查脚本引用了仓库里不存在的目标，命中即红，不需要谁复核。每次 GitHub Release 发布、每周一 03:17 UTC（北京时间 11:17）及手动触发时，额外运行 `node scripts/check-online-release-contract.js`。该巡检请求正式服务的 `/health`、各平台 `/api/update`、发行包 `HEAD` 与 Range 下载，并将返回的版本、URL、大小与 `server/data/releases.json` 对照；它用于发现仓库发布元数据和线上实际服务的漂移，不替代正式发布后的人工验收。

`.github/workflows/guardrail-scan.yml` 每周一 04:07 UTC（北京时间 12:07）出启发式候选报告——重复修复聚类、反复出现的主题、硬规则与现有检查对照、目标重叠、长期未动——写进运行页并留 30 天 artifact。它只列候选、不自动改文档：要做的由 owner 看过后写进[待办](06-待办.md)，能固化的落成脚本或工作流检查，全程不依赖任何会话是否在运行。
