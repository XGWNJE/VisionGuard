# 构建验证与发布

负责：构建、验证和发布入口及授权边界。不负责：其他模块事实、任务状态或重复验证记录。更新时机：操作入口或约束变化时。


本文只维护可执行入口、授权边界和验证分类。模块事实见对应专题，验证结果见[验证报告](90-验证记录.md)，不在此复制完整报告。

## 内测迭代

测试默认使用当前版本的全套组件和当前配置、数据格式。协议或结构变更时同步相关端，按需重新配置或重建测试环境；不默认验证旧版本混用、增加数据迁移或保留旧入口。兼容需求只按 owner 明确指定的版本或数据范围执行，规则见 [AGENTS.md](../AGENTS.md#内测开发与迭代原则)。

## 授权保护

`node scripts/install-git-hooks.js` 为本 checkout 安装受版本管理的 `.githooks/`；已有其他 hook 时拒绝覆盖。pre-commit 默认拒绝暂存区的 VERSION 变化，pre-push 默认拒绝推送。`sync-version.js` 在写入前校验目标版本，`publish-release.ps1` 在非预检 / 非 DryRun 执行前校验发布版本。

只有 owner 已明确授权对应操作后，才在本次进程设置 `VISIONGUARD_OWNER_VERSION=<授权版本>`、`VISIONGUARD_OWNER_PUSH=1` 或 `VISIONGUARD_OWNER_RELEASE=<授权版本>`，结束后移除；发布授权允许该版本同步，不自动授权额外 push。这些变量是误操作保护，不能代替人类授权；测试只在独立临时仓库或夹具中设置。

项目 `.codex/rules/project.rules` 对直接的 push、tag 和 GitHub Release 写操作要求审批；规则依赖可信项目配置层、重启和沙箱审批路径，当前 full-access / never 会话不保证启用。参见 [Codex 官方规则说明](https://learn.chatgpt.com/docs/agent-configuration/rules)。规则按命令前缀匹配，不覆盖任意脚本包装、全局参数或 API 调用；Git 没有通用 pre-tag hook，直接 tag 也不能只靠 hook 保护。hook 可被 --no-verify 或配置绕过，脚本变量可被自行设置，因此仍保留 AGENTS 授权红线。新 checkout / worktree 需安装 hook；已有其他 hook 要手动整合，不修改全局配置。

发行说明读取 `docs/releases/v<版本>.md`，只在该目录 README 登记。普通迭代不运行发布入口，预检继续可用。

## 构建

仓库组件的统一构建入口（客户端 Release、服务含 Web）：

```powershell
powershell -ExecutionPolicy Bypass -File .\.agents\skills\visionguard-build\scripts\build-all.ps1 -Target All
```

可用目标为 `Server`、`WPF`、`WindowsResident`、`AndroidDetector`、`AndroidNotifier`，也可使用组合目标 `Windows`、`Android`（包含通知节点）。脚本只编译并检查产物，不打包、不上传、不部署、不改版本。

视觉推理节点内部驻留程序的生命周期命令以源码为准：`open-detector`、`close-detector`（随主程序启动，主界面关闭后继续运行）。

构建结果必须按组件分别报告，并在完成后检查：

- 统一服务及 Web：`server/dist/index.js`、`server/dist/console/index.html`；先分别运行 `npm --prefix server ci` 与 `npm --prefix receiver/web ci`，需要 Node.js 22.18 或以上
- 视觉推理节点统一入口：`detector/windows-package/bin/Release/VisionGuard.Detector.Windows.exe`；内部运行时位于 `runtimes/modern/` 与 `runtimes/legacy/`，各自只保留匹配的 `native\modern\`、`native\legacy\`，包根目录不得残留 `onnxruntime.dll` 或 `DirectML.dll`
- 视觉推理节点内部驻留程序：`detector/windows-resident/bin/Release/net472/VisionGuard.Resident.Windows.exe`
- 相机推流节点：`detector/android/app/build/outputs/apk/release/app-release.apk`
- 通知节点：`notifier/android/app/build/outputs/apk/release/app-release.apk`

Windows 发行输出不得包含 `.pdb`、`.lib`、`.dll.config`、`.onnx`、`Assets/` 或 `alerts/`；模型按需下载，不随发行包分发。详细模型与项目文件边界见[模型资源](35-模型资源.md)。

## 仓库清理

[clean-repository.ps1](../scripts/clean-repository.ps1) 默认只预览一次性输入 helper 的 APK、class / dex 和专用测试签名产物，保留 Java / Manifest / 构建脚本。`-IncludeBuildIntermediates` 另纳入 Git 忽略的 MSBuild `obj` 与 Android `app/build` 下的 `intermediates`、`tmp`、`generated`、`kotlin`；不清空整个 `.local` 或 `build`。

```powershell
# 当前 checkout 的预览；可选中间文件也只列计划。
& .\scripts\clean-repository.ps1 -IncludeBuildIntermediates
# 只执行默认 helper 清理；可用 -WhatIf 再预演。
& .\scripts\clean-repository.ps1 -Apply
# 确认计划后删除中间文件；先结束构建 / Gradle / Kotlin 进程。
& .\scripts\clean-repository.ps1 -IncludeBuildIntermediates -Apply
# 多个明确指定的 checkout；脚本须从包含该入口的分支调用。
& .\scripts\clean-repository.ps1 -RepositoryRoot @('C:\Repo\VisionGuard','C:\Worktree\VisionGuard') -IncludeBuildIntermediates
```

计划与结果写入第一个目标仓库的 `.local/repository-cleanup-plan.json`。删除前重新核对绝对路径、Git 索引和目录内容，拒绝链接 / Junction / 越界路径、已跟踪文件及未知 helper 内容；构建中间目录含安装包、模型、凭据或性能轨迹时保留整个目录。源码、实际发行 / 测试包、运行目录、模型、签名 / 私有配置 / 账号、原始验证证据、依赖和共用 Gradle / Maven 缓存默认保留。脚本不结束进程，不接触设备、VPS 或 Git 状态；真实清理结果仍以报告为准。

## 控制台认证连接诊断

控制台出现认证超时后，先保留原标签页。开发者工具 Console 可按 `[RelayAuth]` 筛选；刷新过的页面可读取本标签页有界记录：

```javascript
JSON.parse(sessionStorage.getItem('visionguard.connection-log') || '[]')
```

记下 `attemptId` 和发生时段，服务端读取同一时段 `journalctl -u visionguard.service` 的 `[WsAuth]`，按相同 `traceId` 关联；没有客户端标识的节点仍有服务端随机 `connectionId`。每次尝试单独计时，不用两端墙钟相减推断网络耗时。只记录建连 / 认证 / 关闭等状态变化，不输出周期心跳。

- 浏览器 `connect-timeout` 且同标识无服务端接入记录：尚不能确认已到达应用 WebSocket 层；DNS、TCP、TLS、代理与浏览器回调延迟需结合浏览器 Network 另查。源码提示为“网络连接超时”，与打开后独立计时的“认证响应超时”区分；两类超时均按退避自动重试，真实会话失效才要求重新登录。重试独立于心跳轮询；后台浏览器节流可能推迟回调。部署状态见[验证记录](90-验证记录.md)。
- 服务端 `socket-open` 后 `auth-timeout`，`firstFrameReceived=false`：已接入，但认证首帧没有到达服务端处理器。
- 服务端 `auth-success`，浏览器却等待认证超时：服务端已接受认证；回执传输或浏览器处理仍需核对，不能把发送等同于收件。
- `auth-rejected` / `invalid-session`：服务端实际拒绝了会话，区别于前端建连计时超限。

浏览器仅同一标签页保存最近 100 条，每次写入清理 24 小时以前记录；存储禁用时使用 Console。日志不含凭据或原始消息。这个能力需要将相应服务 / Web 改动部署后才在线生效；构建和回归不代替生产取证。

## 服务器资源维护

保留策略以 [AGENTS.md](../AGENTS.md#服务器资源与保留) 为准。只读盘点不构成删除、部署或重启授权；共享 journal 保留调整由 `Server-infra` 协调并另行授权。实施状态只在[任务清单](06-任务清单.md#服务器资源与缓存清理)维护，实际清理与未覆盖项只记在[验证记录](90-验证记录.md)。

正式发布仍只用 `publish-release.ps1`。上传 / 替换前短暂停止原服务，备份代码、依赖、账号 / 配置 / 私有数据、systemd / Nginx 配置、Node 运行时及旧元数据引用的安装包和模型；随后恢复原服务。不可变模型、包及运行时用硬链接降低占用，私有数据独立复制并核验 SHA256 / 属主。备份放在服务 `backups/snapshot-*`，`previous.json` 指向唯一完整回滚点。公网上线健康、发行文件和 WebSocket 核验全部成功后，核验待保留快照、更新指针，再核对进程占用，删除未使用的旧快照及当前 / 回滚元数据均未引用、未被读取的历史包。发布失败保留原回滚点和 `transaction.json` 对应的待核验快照，后续发布停止，须先查明失败并处理该事务；不自动删除失败备份或重试部署。`server-resource-maintenance.py` 是发布脚本内部备份助手，不是另一个发布入口。

Web「设置 → 统一服务缓存」可盘点 / 清理当前账号；管理员还可处理旧公共截图目录。只删除超过 `SCREENSHOT_TTL_HOURS`（默认 72 小时）且无有效事件引用的图片，保留有效事件引用至事件期限；无法读取引用记录时保留并报失败。后台按 `CLEANUP_INTERVAL_MS`（默认 1 小时）执行相同策略，覆盖账号与旧目录。不会操作账号、配置、模型、发行包、备份或任意输入路径。

节点详情的「节点缓存」要求在线且声明 `cache-maintenance`，通过 `cache-inspect` / `cache-clean` 和匹配的 completed 回执展示实际文件结果。视觉推理节点按 7 天 / 1 GB / 5000 张清理截图；读取中删除失败会计入失败数。Android 包暂存按 7 天回收，下载 / 校验与维护使用同一锁，准备安装的包受保护，交给安装器时续期 7 天；下载缓存上限 256 MB，超限拒绝新增。通知节点当前账号诊断导出保留 24 小时、单份最多 3 MB、至多 20 份 / 总量 40 MB；近期分享文件、持久音频、报警、配置和活动日志不清理。历史无账号归属的诊断导出不开放远程删除。

盘点 / 清理结果列总文件与字节、可回收文件与字节、删除数量和失败数。服务端按 inode / 链接计磁盘块，保留硬链接不计释放；节点无法可靠计量释放块时明确显示未计量。清理结果是本次操作前的盘点快照，完成后可再次盘点；连接中断或超时显示结果待核实，不计作成功。

测试资料先核对当前服务、进程打开文件和其他任务占用；正在使用的独立通道、可复用工具 / 夹具、源码、必要原始证据及签名 / 私有配置保留，只删除明确失效的一次性 staging、旧测试备份和已解压下载压缩包。节点日志有界：通知日志 1 MB + 一份旧日志，Windows 驻留日志 1 MB + 一份旧日志、报警投递日志同样轮换；正常服务只记录首个检测心跳，周期诊断仅在 `VISIONGUARD_MEDIA_DIAGNOSTICS=1` 时输出。

自行验收：部署同契约的服务 / Web / 节点后，在设置盘点与清理当前账号截图；普通账号不得清理旧公共目录或另一账号。在各在线节点盘点、清理、再盘点，核对过期减少、近期 / 使用中数据保留、离线禁用、重复清理为零及失败 / 超时提示。真实 UI、下载 / 安装期间清理、持续运行和下一次真实发布的备份轮换由 owner 验收，不以本地模拟替代。

### 设备验收操作

- 视觉推理节点的运行、交互、采集验收默认启动 Release 真实 WPF 主程序并保持可见；不得用隐藏 / 无头测试窗或生产类库 smoke 替代，结束关闭本轮启动的窗口。
- WPF 人员 smoke 使用独立可见动态视频窗口，经 WindowHandle 捕获，逐路断言至少一帧 person 与 FPS；窗口数量随覆盖来源数量，四路保留回归基线，容量扩展同步脚本。静态图片不能替代动态视频；维护脚本的既有覆盖限制单独报告。
- Android 真机 UI / 运行 ADB 和模拟器调试保持 scrcpy、模拟器窗口或等效预览可见，结束关闭；纯构建、签名验证和只读设备信息可不启动预览。
- 表单优先 ACTION_SET_TEXT 一次填写，先核对应用与字段，不用软键盘逐字输入；凭据不经系统剪贴板或命令参数，临时输入工具 / 请求文件验收后移除。
- 不擅自修改锁屏、休眠、唤醒设置；没有 owner 明确授权的解锁方式或唤醒异常时停止，等待 owner 处理。UI 分批交付由 owner 真机目检；视觉和较长验证先交 owner 选择。
- owner 已授权小米 15 的软件锁屏测试自动解锁。先核对连接设备为小米 15，再通过 `[Environment]::GetEnvironmentVariable('VISIONGUARD_XIAOMI15_UNLOCK_PIN', 'User')` 读取当前 Windows 用户环境变量，使用系统锁屏键盘输入；变量缺失时停止。密码值不打印、不写入仓库、文档或测试日志，不经系统剪贴板或命令参数；该授权不允许修改设备安全设置。

### 基础账号与客户端登录

一个账号对应一套系统。统一服务自动初始化管理员 `xgwnje`，现有同名账号沿用密码；全新数据目录的随机初始密码保存在 `VISIONGUARD_DATA_DIR/initial-administrator.json`，仅在私有环境查看，不上传或写入公开配置。已有有效管理员时不重新初始化。管理员从 Web 控制台的“账号管理”创建账号、启用/禁用、重置密码与设置管理员权限；至少保留一个启用的管理员，禁用、重置密码和变更权限会撤销该账号会话。

离线维护仍可在服务停止时指定独立数据目录使用 CLI；密码仅经环境变量或标准输入传入：

```powershell
$env:VISIONGUARD_DATA_DIR = '<absolute-private-data-directory>'
$env:VISIONGUARD_ACCOUNT_PASSWORD = '<private-password-at-least-8-characters>'
node scripts/provision-account.js <username>
Remove-Item Env:VISIONGUARD_ACCOUNT_PASSWORD
```

账号库存储在数据目录的 `accounts.json`，密码与会话分别保存派生值和摘要；该文件与账号数据必须保持私有。当前 JSON 存储只支持单服务进程，不提供公开注册入口。在线修改账号应通过账号 API，不与离线创建命令同时写库。

Web 打开同服务 `/console/` 输入账号密码；Android 和 Windows 登录同一账号，设备自动登记，驻留自动获得主节点子会话。Web 会话在页面内存，Android 用 Keystore、Windows 用 DPAPI 保存会话。四个登录入口支持可选的账号密码记忆，规则及检查见[账号密码记忆](#账号密码记忆)。退出、改密和解绑会撤销相关会话。Web 节点详情可改名、解绑及选择镜头目标；账号内只有一个推理节点时自动关联。

Release 内置正式地址 `https://visionguard.xgwnje.cn`，登录只填写账号密码，初始设备名称由服务自动生成，进入程序后再修改。Android Debug 与 Windows Debug/显式隔离配置才允许填写测试地址；旧 Android 隔离会话在 Release 中不使用。Web 使用当前页面同源服务。测试不得混用正式账号库；统一时间与通知范围均按账号保存，历史不触发声音。

### 账号密码记忆

Web、Windows 视觉推理节点、Android 相机及通知节点的登录页默认未勾选“记住账号密码”。勾选后仅在登录成功时保存，下次进入登录页自动填入并恢复勾选；取消立即清除，退出登录保留记忆。未新增自动登录，Windows / Android 的原会话恢复方式保留。账号字段为 3–64 个 ASCII 字母、数字、点、横线或下划线且首字符为字母或数字，登录密码为 1–256 个 UTF-16 单元；改密的最小长度仍为 8。

Windows 使用当前用户 DPAPI，记忆文件与会话分开、按规范化服务地址隔离；Android 使用本应用 Keystore / AES-GCM，绑定服务地址和组件，排除备份与设备转移。Web 在同源 IndexedDB 保存不可导出的 AES-GCM 密钥与密文，要求 HTTPS 或 localhost，密钥仍可供同源脚本使用；不降级为明文保存。Web / Android 在本机改密成功后清除旧记忆；其他设备修改或重置密码后，原记忆须由用户重新填写并登录更新。

快速回归：Web 运行 `npm --prefix receiver/web test`，两个 Android 工程运行 `:app:testDebugUnitTest`；Windows 实际 DPAPI 检查运行 `powershell -ExecutionPolicy Bypass -File scripts/check-remembered-login-windows.ps1`，仅使用 `.local/remember-login-windows-probe/accounts/` 的临时随机凭据，不启动主窗或连接服务器。

真实界面由 owner 自行检查四个入口：首次未勾选；勾选登录后退出再进入，确认自动填入且勾选恢复；取消后重新打开，确认不再填入；重新勾选并登录另一账号，确认下次填入新账号。Android / Windows 的有效会话可能直接恢复，需退出后检查登录表单。本机模拟预览只证明 UI；本轮覆盖和产物见[验证记录](90-验证记录.md)。

### 本机隔离测试

本机隔离服务仅作为 UI 模拟预览入口。所有组件统一使用隔离账号与模拟临时数据；流程与字段边界见[本地预览与数据边界](70-UI设计规范.md#本地预览与数据边界)。通过真实组件界面检查显示，合成节点、事件、截图和回执只能证明 UI 预览，不构造本地模拟业务链路。

### 真实服务器独立测试通道

业务逻辑整体链路验收统一在真实服务器上另开测试通道，由实际镜头、推理、统一服务、控制台和通知组件完成业务流程。服务实例、监听入口、运行目录、账号库与数据独立于正式业务；`VISIONGUARD_CHANNEL` 只是实例标签，不能单独承担隔离。不得用本地服务、合成节点、直接注入报警或伪造收件回执替代链路验收；本地编译、单元、契约与组件探针保留为补充检查。

```json
  "settingsPath": "C:\\VisionGuardTest\\settings.ini",
```


确定性 WPF 报警传输探针仅作为补充：先用 `tests/AccountMedia.Probe` 的 `--login` 命令与私有 `VISIONGUARD_LOGIN_PASSWORD` 在相同独立账号目录登录，再运行 `tests/WpfAlertChain.Probe`。它不证明真实采集或人员推理。

结果分类不能合并：

- `ServerBuild` 只验证 TypeScript 编译和 `server/dist/index.js` 产物；兼容别名 `ServerSmoke` 也只做同一件事，不是 HTTP/WS 运行测试。
- Android 启动 smoke 只验证安装、启动、前台服务/进程状态和观测窗口内无崩溃，不验证视觉推理节点→统一服务→通知节点完整报警链。
- `WpfPersonDetection` 按 `-WpfSourceCount`（默认 4）由脚本内的 `Start-WpfFixtureWindows` 创建可见 WinForms 静态图片窗口，经 `WindowHandle` 捕获后逐路验证 `person`、FPS 和来源隔离；夹具图片数量不得少于来源数。它是类库推理补充证据，不能替代真实 WPF 主程序、动态视频、报警链或 UI 目检。
- 组件补充探针（不显示窗口、不建推理会话）：`CardLayoutPlan` 入口驱动等比画面／检测坐标和真实 WPF 控件量测，断言主卡自适应高度、来源卡高度边界、五个设置分类与统一控件高度，并量测独立侧栏调宽及拖动上下界；离屏像素检查覆盖两种卡片尺寸及 96／120／144 渲染 DPI 的四角描边，滚动检查覆盖轨道留白、内容位移和滚动槽宽度稳定。Benchmark `--source-lifecycle` 使用独立配置验证未配置过滤、临时草稿隔离、失联绑定保留、替换失败回退和空列表；`SourceAutoSave` 保留参数与持久化检查。`PerformanceWatchdog` 验证实测 < 目标×80%、30 秒持续时间及提示口径。这些不替代真实主窗目检、实机帧率或完整报警链。
- `WpfParserContract` 按推理档位各构建一次 `tests/WpfInference.Benchmark` 并对真实图片断言输出形态、形态与档位一致、未知长度被拒、原生 ONNX Runtime 来自档位目录、解析出预期业务目标（默认 `person`，置信度 ≥0.5）。不打开窗口、不依赖 GPU，只证明「模型 → 解析 → 检测框」。
- `ResidentLaunch` 创建独立账号库并使用账号登录；它按 `-ResidentPort`（默认 3123，端口被占用会直接报错而不复用旧实例）启动隔离统一服务，对两个档位分别断言「检测端拉起同目录驻留 → 驻留在超时内进入单实例握手 → 服务端 device-list 报 `components.resident = running`」。它只会结束自己拉起的驻留（按驻留配置路径匹配），不使用真实 settings。不覆盖远程 `open-detector`/`close-detector` 实际动作、登录自启与重启恢复。
- 真实窗口采集、真机 UI、完整报警链、持续运行和故障恢复分别记录为人工/真机/完整 E2E 结果。
- 视觉推理节点内部驻留程序使用 .NET Framework 4.7.2 x64；构建和组件 smoke 仍不能替代 Win7 SP1 x64 目标环境中的启动、WSS、登录重启和网络恢复验收。
- Win7 SP1 x64 前置环境可在虚拟机共享目录中双击 `scripts/run-win7-prerequisites.cmd` 核验；它调用 `scripts/check-win7-prerequisites.ps1` 检查系统版本、KB4490628、KB4474419、KB3140245、WinHTTP TLS 1.2 注册表、KB4019990 与 .NET Framework 4.7.2，并把机器可读结果写入 `artifacts/e2e/win7-prerequisites.json`。共享目录必须临时允许虚拟机写入该报告，验收后可恢复只读。

证据写入 `artifacts/e2e/<timestamp>/`。不要为了本地验证清除应用数据，除非任务明确要求；脚本启动的模拟器必须在结束时关闭。未明确要求时不操作生产服务。

该命令会同步版本、构建、准备签名包、更新 release 元数据、按目标上传并可部署统一服务；每一步都需要明确发布授权。仅检查前置条件时使用 `-PreflightOnly`，明确只发客户端时使用 `-SkipServerDeploy`。GitHub push、tag 和 Release 仍需显式开关。

发布的 `All` 包含 Windows 整包、相机与通知两个 Android 签名包、服务及 Web；`Android` 只发布相机和通知，Android 控制台源码、构建、发布及接入已移除，`All`／`Android` 只编译相机和通知。通知节点可单独发布 `-Target AndroidNotifier`。服务端更新查询键仍保留 `wpf`、`android-detector`、`android-notifier`；历史 `android-receiver` 下载元数据保留，不能作为新发布目标；相机与通知客户端改查 GitHub 稳定发行。当前基础设施已迁入同级 `Wenje-Server/Server-infra`，发布时显式传入 `-ServerEnvPath ..\Wenje-Server\Server-infra\server.local.env`；其他工作区按实际位置解析。不能改写真实凭据或沿用旧路径。上线前备份运行代码、配置和私有数据；发布上传按 SHA256 跳过相同文件，同时核验 Windows 所需公共模型。

部署使用统一服务专属的 Node.js `24.21.0`，可用 `-ServerNodeVersion` 指定其他 24.x 版本。脚本从官方发行目录下载 Linux x64 运行时并校验 SHA256，保存在运行根目录的 `runtime/`；systemd drop-in 指向该运行时，不修改其他服务的全局 Node.js。部署后核对实际进程路径与服务版本。

发布前必须确认 Android 签名材料、Windows ZIP 清洁度、元数据大小和目标范围；发布后才可执行公网 `/health`、`/api/update`、`HEAD 200` 和 byte-range `206` 验证。正式反向代理须同时升级 `/ws` 与 `/media/ws`，配置模板为 `server/nginx-visionguard.conf`；控制连接成功不能证明媒体入口可用。`node scripts/check-websocket-entrypoints.js` 无需账号，分别断言两条入口的 101 与握手摘要，不发送业务数据；部署后及公开 GitHub 发行前必须通过，失败保留草稿。发布脚本是唯一的正式打包/部署实现。

需要停留在草稿供 owner 确认时，使用 `-GitHubOnly -CreateTag -CreateGitHubRelease -DraftOnly`，复用已构建且签名校验通过的包；该模式禁止 VPS 上传及部署，后续经授权去掉 `-DraftOnly` 公开发行。

全套版本已部署、但后续公网检查中断且 `backups/transaction.json` 仍保留时，使用同一入口的 `-FinishRelease -Target All -CreateTag -CreateGitHubRelease`，并传入原标签提交 `-GitHubTagTarget` 与实际 `-ServerEnvPath`。它核对运行服务、服务器版本 / 代码 / 元数据 / 发行附件摘要及原待确认回滚备份，再重新检查健康、更新 / 下载和两条 WebSocket 入口，成功后完成备份轮换与公开草稿；不重新同步版本、构建、上传或部署。版本、附件或备份不匹配时保留事务并停止；没有待确认事务时使用普通或 GitHub-only 流程，不删除事务文件来重试。

GitHub 发布先创建草稿，上传后逐个核对文件名、数量、上传状态、大小与 GitHub SHA256 摘要，再公开稳定版。草稿通过已认证的 `gh release view` 取得发行 ID，按 ID 读取完整资产；REST 标签入口只返回已公开发行，不能用来验证草稿。校验失败保留草稿；已公开的同版本发行拒绝覆盖，须使用新的授权版本。Windows、相机与通知节点按组件查 GitHub 稳定发行；Web 和统一服务通过源码／服务发布更新，不采用客户端更新器。上述脚本实现不构成实际发布授权。

**分端上线（某端本次不发布）**：`-Target` 是单值，要发多个端就按端分批跑（例如 `-Target Windows -UploadVps`、`-Target AndroidNotifier -UploadVps`、`-Target Server -UploadVps`）。未发布的端在 `server/data/releases.json` 的**该平台条目内部**标 `"heldBack": true` 并保持上一个已发布版本，使更新接口继续返回旧版本而不是指向不存在的文件；`sync-version.js` 与 `publish-release.ps1` 会保留并跳过该条目。`check-docs`、`publish-release.ps1` 的 GitHub-only 资产收集与 `.github/workflows/release.yml` 都会跳过 heldBack 平台并给出提示；但 GitHub Release 两条入口在「一个平台都没对齐目标版本」时仍会失败，避免版本号打错时发出空 Release。

## Android 更新器专用回归

通知工程的 `ClientUpdaterTransportTest` 需要隔离的旧 Debug 应用和同包名／签名的当前 APK。使用[测试专用 Gradle 初始化器](../scripts/android-update-test-fixture.gradle)，先构建当前包，再把它作为 `current-client.apk` 加入旧版测试 APK：

```powershell
# 在 notifier/android 执行；保持已连接设备的可见预览
.\gradlew.bat -I ../../scripts/android-update-test-fixture.gradle :app:assembleDebug
New-Item -ItemType Directory -Force ../../.local/updater-device-fixture/assets | Out-Null
Copy-Item ../../.local/updater-device-fixture/current/app/outputs/apk/debug/app-debug.apk ../../.local/updater-device-fixture/assets/current-client.apk
.\gradlew.bat -I ../../scripts/android-update-test-fixture.gradle -PvisionguardUpdateFixtureOld=true :app:assembleDebug :app:assembleDebugAndroidTest
```

旧包与测试包位于 `.local/updater-device-fixture/old/app/outputs/apk/`，仅安装到选定的测试设备并运行该类；若已存在 `.acceptance` 包，先确认属于本轮测试，不能为避免降级限制删除用户原应用。初始化器只允许明确 Debug／测试任务：旧版号只用于本机测试夹具，根 `VERSION` 和正式版本不变。普通测试 APK 不携带该资产时会跳过此类。GitHub 元数据和下载地址仅在测试 APK 中拦截，实际 HTTP 下载、大小／摘要、PackageManager 身份和 FileProvider 校验照常执行；显式 instrumentation 参数 `-e liveUpdates true` 另启用真正 GitHub 查询及 UI 线程退出回归。

默认只验证权限页交接。获得实际安装授权后，先在系统界面允许本轮隔离包安装，再以 `-e installHandoff true -e class com.xgwnje.visionguard.notifier.ClientUpdaterTransportTest#actualInstallerHandoffWithOperatorApproval` 单独运行安装测试。调用者与候选文件保留 60 秒，供处理厂商确认页；提前结束调用者可能撤销 URI 读取授权。测试完成只证明交接，必须另核验安装后的包名、版本、签名和 APK 摘要。USB 安装提示有倒计时，应在安装命令运行期间观察并及时确认，不能等命令超时后再检查；不能凭授权提示消失判断安装成功。不要在 instrumentation 使用 UiAutomation 时并发运行另一个 `uiautomator dump`。结束后卸载本轮测试包，关闭预览。

## 配置与服务边界

- 统一服务真实账号库、会话、TLS 私钥及生产配置使用独立私有目录或部署环境变量，不能提交。
- 发行客户端只填写账号密码，服务地址内置；设备、默认名称、组件与驻留身份由服务签发，不注入 API key、设备 ID 或通道。Windows Debug 或显式隔离配置可使用 `VISIONGUARD_SERVER_URL`，Android Debug 可在隔离测试设置中修改地址；普通 Release 不受测试地址覆盖。
- 本地签名配置位于被忽略的 `.local/` 和 Android `local.properties`，不与账号配置混用；移工作区时按需额外备份签名材料，不能提交到 Git。
- 服务默认 HTTP；配置 `VISIONGUARD_TLS_CERT_FILE` 与 `VISIONGUARD_TLS_KEY_FILE` 可启动独立 HTTPS/WSS 测试实例。测试需独立进程、端口、数据目录和账号库，不覆盖线上目录、监听或代理配置。
- 开发 CI 在 `.github/workflows/development.yml`：服务/Web 契约与构建、文档及 `check-ui-theme.js` 跨端主题/文字对比守卫、`python scripts/generate-icons.py --check` 品牌导出一致性、两个 Android 的 Debug 单测/lint/构建，以及 Windows 双档构建与媒体探针。品牌导出检查依赖 Pillow，安装及再生成方式见 [`icon/README.md`](../icon/README.md)。CI 不使用生产凭据、不发布，云端执行结果须单独核实。
- VisionGuard 正式域名：`https://visionguard.xgwnje.cn`；根域 `https://xgwnje.cn` 不是新客户端服务地址。
- 当前 VPS/DNS/SNI 事实由 `Server-infra` 项目维护；不要运行旧式 `server/deploy.sh --nginx` 覆盖现有 SNI 架构。
- `VERSION` 只由 owner 明确授权的版本流程修改；普通构建、测试、修复和文档治理不得改动它。

## 文档审核

```powershell
node scripts/check-docs.js
node --test scripts/check-docs.test.js scripts/release-workflow.test.js scripts/check-powershell-encoding.test.js
```

审核会检查 Markdown 链接和锚点、UTF-8 无 BOM、版本来源、组件入口、四个 WS 角色、模型打包边界、Skill 与脚本契约、现有组件命名与产品边界和旧入口不存在。新增或删除文档/Skill/入口后必须先更新对应唯一来源，再运行审核。

`.github/workflows/docs-audit.yml` 在 PR 与 `main` 推送时运行上述静态检查；每周一 03:17 UTC（北京时间 11:17）及手动触发时，额外运行 `node scripts/check-online-release-contract.js`。该巡检请求正式服务的 `/health`、各平台 `/api/update`、发行包 `HEAD` 与 Range 下载，并将返回的版本、URL、大小与 `server/data/releases.json` 对照；它用于发现仓库发布元数据和线上实际服务的漂移，不替代正式发布后的人工验收。
