## 未完成事项

### 推理加速落地（前置关系：先 1 与 2，再 3）

- [ ] **1. 端侧锚点解析与 NMS**：GPU 路线用的截断图输出 `[1,84,8400]`（4 框 + 80 类分数，无图内 NMS），需在 `YoloOutputParser` 补这一形态的解码与 NMS；现有锚点分支是 `[1,84,N]` 的 YOLOv5u 语义，不能直接套。参考实现（Python 已跑通）见[验证记录](90-验证记录.md#gpu-打通截掉图内-nms-后-gpu-档可编译2026-10-11-续查xiaomi-26048rp6ac-api-37)。
- [ ] **2. GPU 模型分发（发布动作，需授权）**：服务端目前只有 12 个 FP32 本体，GPU 需要单独的截断 TFLite 产物（FP32 边界；int8 在 GPU 上更慢且分数归零，不用）。需定键名与投放方式，并考虑是否同时恢复 int8 本体投放。
- [ ] **3. 多路限制落地**：建议值（CPU 按模型 32 / 4 / 2 路，GPU 32 路）见[优化专题](32-推理框架与模型优化.md#验收口径)；需落到 UI 输入边界、服务端校验、心跳上报字段与单测，各端口径一致。
- [ ] **4. 补齐 GPU 端到端数字**：现测的是纯推理，端侧解码 + NMS 开销未计入；落完第 1 项后补测，并跑一次 8 路真实链路。
- [ ] **5. 校准集换成相机实拍**：量化校准仍借用照片夹具，应按[优化专题](32-推理框架与模型优化.md#量化现状2026-10-11)的说明改用推流或本机采集画面。
- [ ] **6. 并发上限与设备复测**：GPU 上限未触底（本次只扫到 32 路），且更小内存的设备需重测；GPU 内存随路数线性增长，是真实约束。
- [ ] **7. 测量报告记录 GPU 厂商与驱动**：现有报告的「设备」只到机型与 SoC，跨厂商读数会被混在一起，需补 GPU 渲染器/驱动与 SoC 厂商字段（跨平台结论见[优化专题](32-推理框架与模型优化.md#gpu-跨平台适配qualcomm-soc)）。
- [ ] **8. Qualcomm 真机验证（待硬件）**：GPU 路线兼容 Qualcomm 已核实（分发包内含 Adreno 分支与 `cl_qcom` 扩展），本机只有 MT8910，缺 Qualcomm 实测；拿到设备后按 640 三尺寸 + FP16/纹理两个变体复测，并用第 7 项的字段留证。
