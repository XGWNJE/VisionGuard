## 现在要做的

已经在做或已排期的事。排序口径：先看是否卡住别人，再看影响面（影响真实部署的优先），最后看性价比。编号长期沿用、不重排，检索历史时按编号对应。每条用几句短要点写清：要什么、为什么、条件与影响面。

### 高：能被立刻解决、且不解决就一直硌着

#### 18. Windows 推流节点多来源并行推流

- **要什么**：推流态下主动方可以同时把多个本机来源推给同一个在线的被动方推理节点；主动方每多推一个来源，被动方来源列表就同步多一个；各来源独立推流状态与帧率；被动方可从本机解除绑定，控制台也能解除绑定。
- **为什么**：媒体契约按「发布端设备」建模——每设备只保留一条发布连接、一条流、一套序号，而 Windows 每个来源各自建一个发布服务，第二个来源一起推就把第一个顶掉（4000 `publisher replaced`，表现为交替抢连接），结果推流态只能推一路来源。
- **影响面**：统一服务媒体契约（流按「发布端 + 来源」建、绑定与流分离、新增解除绑定接口与权限）、Windows 发布端与本机推流界面、控制台推流关联与解绑入口、被动方解绑入口；接收端已按 `streamId` 记账，不需要为此改协议。分支 `feature/multi-source-push`。
- **方案**：[Windows 推理节点推流](75-Windows推理节点推流.md)与[统一服务](20-统一服务.md#实时媒体)。

#### 15. 来源抽屉与设置抽屉的分区清点

- **要什么**：来源抽屉由三页拆成六页（运行 / 来源 / 参数 / 模型 / 目标 / 遮罩），每页在参考设备上不滚动就能看全；设置抽屉按设置项的真实归属重分区（账号 / 连接 / 模型 / 外观 / 后台 / 维护），去掉与来源抽屉重复的内容，文案统一精简。
- **为什么**：三页抽屉每页都超出内容区（参数页约 990dp、可用约 384dp），模型插片与检测目标被挤到折叠线以下，遮罩列表同样看不到；设置里的推理状态、模型概览、遮罩合计、运行来源、远程来源与来源抽屉和来源列表重复。
- **影响面**：只动 Android 视觉推理节点的界面结构与文案；不改检测参数、遮罩模型、协议、持久化与版本号。分支 `feature/inference-drawer-regroup`。
- **方案**：[来源抽屉与设置抽屉分区清点](74-来源抽屉与设置抽屉分区清点.md)——六页与六分区的完整清单、去重与文案、高度预算与验收口径。

### 中：影响真实部署质量，但可以排期

#### 6. 校准集换成相机实拍

- **要什么**：把量化校准换成相机实拍的画面，替掉现在的照片夹具。
- **为什么**：真实镜头的分布（夜视、逆光、抖动）跟照片不一样，会影响量化后的分数上限。
- **条件**：等 owner 交付实拍画面（先 10 张小批）；质量提升，不阻塞发布——当前照片校准版已获准按正式版发布。
- **影响面**：只影响 Android INT8 模型；Windows 走 FP32 + DirectML，不需要校准集。
- **取材清单**：[取材范围、格式与验收门槛](32-推理框架与模型优化.md#校准集取材清单)。

#### 11. Android CI 覆盖 release 变体

- **要什么**：CI 至少编译一次 release 变体，并跑 release lint。
- **为什么**：Android job 现在只跑 `assembleDebug` + `lintDebug`；发布用的 `assembleRelease` 与签名验证只在本地发布脚本里，混淆与资源收缩这类只在 release 出现的问题 CI 看不到。
- **怎么做**：矩阵 job 增加 `assembleRelease` 与 `lintRelease`；无签名材料时用 `-PVISIONGUARD_ALLOW_UNSIGNED_RELEASE=true` 只做编译验证，失败即红。
- **条件**：确认该开关只用于编译验证，不进任何发行产物。

#### 12. 测试夹具与版本解耦

- **要什么**：凡写死版本号的测试改成从根 `VERSION` 推导。
- **为什么**：`scripts/launcher-update.test.js` 的夹具写死 `v0.7.0`，客户端升到 0.7.1 后「缺 SHA256 / 缺下载地址」两个用例走不到校验分支、静默失效，CI 长期红灯被当噪声；同类隐患可能还有。
- **怎么做**：扫一遍 `scripts/` 与 `tests/` 里的版本字面量，能推导的都改推导——launcher 那条已按「读 VERSION 后 patch+1」改好，可作范例。
- **影响面**：只动测试夹具，不改被测实现。

#### 14. 定期护栏扫描（重复犯错与自动化候选）

- **要什么**：每周扫一遍仓库，双向体检——① **补缺口**：同一文件或主题被反复修复、`AGENTS.md` 硬规则还没有自动化检查；② **减冗余**：现有检查里的失效引用、目标重叠、恒真断言、skip 条件与长期僵化。目标是护栏的总量与价值平衡，不持续膨胀。
- **怎么做**：`scripts/scan-guardrails.js` 把硬规则与现有检查脚本并列供对照，并体检失效引用、工作流指向、`continue-on-error`、目标重叠、恒真断言与长期未动；`guardrail-scan.yml` 每周一 04:07 UTC 跑一次，报告进运行页并留 30 天 artifact。
- **谁来跑**：DSH 会话自动任务「VisionGuard 护栏扫描」每周一 12:00（北京时间）唤起复核并登记，CI 那条只负责扫描留痕。分工是「CI 采集、会话复核登记」——CI 不依赖 DSH 是否在运行，会话任务负责把候选变成清单条目；DSH 停机跨过的周期只会补最近一次。
- **产出怎么用**：脚本只列候选、不自动改文档；复核后把确认要做的写进本节，能固化的落成脚本或工作流检查。
- **影响面**：只读扫描，不改代码、不发布。

### 低 / 待外部条件

#### 13. 线上发布契约的校验频率

- **要什么**：线上契约校验在发布后也跑，而不是只靠每周一 03:17 UTC 的定时任务。
- **为什么**：发布当天线上元数据或资产若有问题，最坏要等一周才被自动发现；发布脚本的在线验证只覆盖发布当次。
- **怎么做**：给 `docs-audit` 的 `online-release-contract` job 增加 `release: published` 触发，或改成每日一次。

#### 3. 通知节点小米 15 锁屏漏收根因

- **要什么**：查清锁屏后收不到报警的根因。
- **为什么**：静音锁屏回归有收件证据，但最初漏收的根因仍未确认。
- **线索**：同一账号在小米 6X 上没这问题；该机售后换电池时 UI 健康度与系统日志不一致，工作人员可能调整过后台策略——更像设备端问题，故降级。
- **条件**：等换机或系统重置后再看；专项证据见[验证记录](90-验证记录.md#节点改名web-会话与小米-15-静音锁屏专项2026-10-08)。

#### 7. Qualcomm 真机验证

- **要什么**：在 Adreno 设备上复测 GPU 加速档。
- **为什么**：兼容性已核实（分发包内含 Adreno 分支与 `cl_qcom` 扩展），但本机只有 MT8910。
- **怎么做**：按 640 三尺寸 + FP16 / 纹理两变体复测，留下后端、帧率与单帧耗时作证据。
- **条件**：需要硬件。

#### 8. 并发上限与设备复测

- **要什么**：确认更小内存设备上的多路上限。
- **现状**：上限已在 26048RP6AC 回填——CPU 为 320 INT8 四路、640 INT8 两路；GPU 两档 32 路未触底。
- **条件**：需要设备，没有硬件就只是记着。

#### 9. 服务器维护：journal 保留策略

- **要什么**：决定是否调整共享 journal 的保留策略。
- **现状**：已复核并决定本轮不动——占用 901.3 MB、上限约 960 MB，journald 会自动轮转，其中只有约 5% 来自本项目单元。
- **条件**：需动时与 `Server-infra` 协调；判断依据见[验证记录](90-验证记录.md#共享-journal-处置结论2026-10-11-复核)。

## 以后要做的

还没启动的方向：要新建能力、跨组件、工程量中等以上，需要 owner 定顺序。编号从 1 连续、跟着内容自适应重排；每项几条短要点，写清要解决什么、为什么难、怎么验、卡在哪。

### 1. 局域网与公网两种部署模式

- **要解决**：局域网部署换更低的延迟、更大的带宽吞吐，画面和报警数据也不用离开本地网络。
- **怎么做**：两套独立部署。公网沿用统一服务转发；局域网由本地网络里一台终端承载服务，各组件指向它。
- **不做**：双入口探测、自动降级、在线切换——换部署就是换一套安装和配置。
- **卡在哪**：局域网用哪类终端承载、怎么接入，启动时再规划。

### 2. 除手机推流节点以外的硬件节点

- **方向 A · 兼容品牌成品**：蓝牙 PIR 成品铺高密度点位，一个 ESP32 网关扫广播、按现有传感器事件上报。不计入首轮 500 元预算，确认真需要高密度低价点位再启动，不先铺点位。
- **方向 B · 自定义硬件传感器（含原型与集成优化）**：先用现成传感器加开发板和电池做原型——室外固定，按 25 米级雷达标称上限定经过检测目标，看人经过、设备被移动或拆走、突发大声或撞击；首轮 500 元以内，先走 Wi-Fi 或手机热点。现场验证后再做传感器融合、结构与电路板优化，不提前设计 PCB。
- **不算在内**：手机和平板推流走「原生 Android 推理节点」那条线，不算硬件节点方向。
- **条件**：设计与采购条件见[硬件原型专题](25-硬件原型设计与采购.md)。
- **卡在哪**：短期不推进，属待外部条件。
