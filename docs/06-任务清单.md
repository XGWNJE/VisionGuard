### 推理加速路线评估（未定案）

- [ ] **测完所有组合**：owner 要求在有真机条件时把全部模型 × 全部档位测完。三个包已就绪：`accel-test-package/`（A，`yolo26n` 320/640 × FP32/INT8 × ONNX+LiteRT，256.0 MiB）、`accel-test-packages/B-yolo26s`（276.6 MiB，只 ONNX）、`accel-test-packages/C-yolo26m`（368.2 MiB，只 ONNX）。按 `InferenceProvider.benchmarkOrder`（19 档）核算共 **136 格**（A 80、B/C 各 28；核算脚本 `.local/model-quant/matrix-cells.py`），均已在模拟器验证解包与出读数。B/C 每模型 13 条 LiteRT「缺 .tflite」属预期。已测代表读数见[验证记录](90-验证记录.md#真机全档读数2026-10-11xiaomi-26048rp6ac-api-37)。
- [ ] **完整量化产物 + GPU 复测**（计划已定，等待开工指令）：造 int8/uint8 输入输出的 TFLite，再把之前 GPU 全失败的 12 条组合（3 模型结构 × 4 配置：默认 / FP16 / 纹理权重+关外部张量 / 关外部张量）在真机重测。
  - 起因：现有 `.tflite` 的「INT8」不是整数图——实测 **QUANTIZE 0、DEQUANTIZE 378、DIV 379、ROUND 378，算子 3270 个**（FP32 版仅 421），是 float 图反复反量化，疑为 LiteRT 在 ARM 上慢 6 倍的根因；`onnx2tf` 严格全整数量化在解码段报 `Unsupported op ... ROUND`。
  - 步骤：① 装 `ai-edge-quantizer` 0.10.0（依赖 `ai-edge-litert==2.3.0`，会升级本机 2.1.2；装前 `pip freeze` 留回滚点，装后复跑三个 TFLite 脚本冒烟）；② 三条路径按成本造产物：quantizer 直接量化现有 TFLite（预计不通，10 分钟证伪）→ TF `TFLiteConverter` 全整数量化（需 `keras`，最可能成功）→ `ai_edge_torch` 走 StableHLO；③ 真机复测；④ 结果入[验证记录](90-验证记录.md)。
  - **验收不能只看 I/O 类型**：必须是真整数图（QUANTIZE > 0 且 DIV/ROUND 大幅下降、算子数回到几百量级），否则「接口变 int8、图内仍是 float 骨架」，GPU 照样不吃。
  - 真机执行需 owner 配合（本机 `adb devices` 为 0，只能打包）。
- [ ] **定主线推理路线**：等上面两项测完，再决定主线用哪条（候选：ONNX CPU + INT8 现状 / 其他组合 / 若完整量化救回 GPU 则重新评估）。这一步属发布行为，需 owner 明确授权后执行。
