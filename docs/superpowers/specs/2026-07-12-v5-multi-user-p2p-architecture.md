# VisionGuard 5.0 多用户与纯 P2P 架构方案

> 状态：未来规划，不属于 4.x，目标版本 5.0  
> 日期：2026-07-12  
> 当前结论：方案在通过阶段 0 技术闸门后可实施；不得直接在 4.x 上渐进上线。

## 1. 背景与目标

VisionGuard 4.x 使用共享服务器和共享 API Key。多个用户共同使用同一实例时，账号、设备、在线状态、报警和截图缺少明确的归属边界，容易出现数据混合。

5.0 的目标是建立最基础但完整的账号与租户隔离系统，并把报警数据面从 VPS 中移走：

- 用户可使用用户名和密码开放注册、登录和退出。
- Windows WinForms、Windows WPF、Android 检测端、Android 接收端全部接入同一套账号体系。
- 客户端可选择项目预置服务器，也可填写自定义服务器。
- 同一账号下的设备可以发现和通信，不同账号的数据和设备严格隔离。
- VPS 只承担认证、会话、设备目录、在线信令和 UDP rendezvous，不保存、查看或中继报警、截图及实时业务数据。
- 检测端与接收端使用 KCP + libsodium 建立端到端加密的原生 P2P 数据通道。
- 无法打洞时不回退到 VPS 中继；检测端进入有界离线队列，客户端明确显示不可达状态。

本方案不追求组织、邀请、角色权限、找回密码、第三方登录或计费。这些能力若以后需要，应建立在本方案的租户边界上，不进入 5.0 首发范围。

## 2. 核心原则与非目标

### 2.1 核心原则

1. **先证明可用，再全面改造**：Win7、Android 原生库和真实 NAT 打洞均属于阶段 0 硬闸门。
2. **控制面与数据面分离**：控制面经过 VPS，报警数据面只在已认证的终端之间传输。
3. **默认拒绝跨租户访问**：所有账号、会话、设备和信令查询必须以服务端解析出的 `tenant_id` 为范围，不能信任客户端提交的租户 ID。
4. **端到端加密**：KCP 只负责可靠 UDP；机密性、完整性、防重放和密钥协商由 libsodium 提供。
5. **失败可见且有界**：纯 P2P 无法保证穿透所有 NAT。失败时排队、告警和给出原因，不静默丢失，也不暗中改走中继。
6. **硬切换**：5.0 不兼容 4.x 的共享 API Key，不迁移 4.x 的服务端报警和设备状态。

### 2.2 非目标

- VPS 不提供 TURN、KCP relay、WebSocket 报警转发或截图存储。
- 不承诺对称 NAT、严格企业防火墙或完全封锁 UDP 的网络一定可用。
- 不在 5.0 首发引入多成员组织和细粒度 RBAC。
- 不将模型文件、更新包等公共静态资产改为 P2P；它们仍可由 HTTP 按需下载。

## 3. 总体架构

```text
                     控制面（HTTPS / WSS）
┌────────────────┐        ┌────────────────────────────┐
│ 检测端          │◄──────►│ VisionGuard 5.0 Server     │
│ WinForms/WPF/   │        │ 认证、会话、设备、信令      │
│ Android         │        │ SQLite + UDP rendezvous     │
└───────┬────────┘        └────────────────────────────┘
        │                              ▲
        │ 数据面（UDP）                 │ 控制面
        │ KCP + libsodium               │
        ▼                              ▼
┌────────────────┐        ┌────────────────────────────┐
│ Android 接收端   │        │ UDP :3478                  │
│ 同租户认证设备   │◄──────►│ 只反射公网地址并协调打洞    │
└────────────────┘        └────────────────────────────┘
```

服务端只看到账号元数据、设备元数据、在线状态、临时打洞票据和网络端点。报警正文、检测结果和截图不进入服务端 HTTP、WebSocket、SQLite、日志或磁盘。

## 4. 账号、租户与会话

### 4.1 最小数据模型

- `tenants`：租户主键、创建时间、状态。首发时一个注册账号对应一个租户。
- `users`：用户主键、`tenant_id`、规范化用户名、密码摘要、状态、创建时间。
- `sessions`：随机会话令牌摘要、`user_id`、`tenant_id`、设备说明、创建/最后使用/过期时间、吊销时间。
- `devices`：设备 ID、`tenant_id`、设备名称、客户端种类、公开密钥、最近在线时间、排序和删除状态。
- `p2p_tickets`：短期一次性票据、租户、发起/目标设备、过期时间和消费状态。

所有关联表必须含 `tenant_id`，并建立复合索引。任何设备读取、修改、删除、在线查询和信令转发都必须同时匹配当前会话的 `tenant_id`。

### 4.2 注册与密码

- 开放用户名和密码注册，用户名经统一大小写和 Unicode 规范化后唯一。
- 密码使用 Node.js `crypto.scrypt`，参数固定为 `N=2^15, r=8, p=3`，每个密码使用独立随机 salt。
- scrypt 并发限制为 1，等待队列最多 8 个；超过队列直接返回 `429`，防止低配 VPS 被注册请求拖垮。
- 登录错误采用统一响应，不泄露用户名是否存在。
- 注册、登录按来源 IP 和规范化用户名分别限流；日志不得记录密码、令牌或完整认证请求体。

### 4.3 会话

- 使用至少 256 bit 的不透明随机令牌，不使用客户端可自行解析或伪造租户信息的长效 JWT。
- SQLite 只保存令牌摘要，不保存明文令牌。
- 会话有效期 90 天；剩余有效期小于 30 天且会话活跃时允许轮换刷新。
- 退出登录立即吊销当前会话；修改密码或账号冻结时可吊销该用户全部会话。
- 客户端安全存储令牌：Windows 使用 DPAPI，Android 使用 Keystore 支持的加密存储。

### 4.4 最小 API

```text
POST   /api/v5/auth/register
POST   /api/v5/auth/login
POST   /api/v5/auth/refresh
POST   /api/v5/auth/logout
GET    /api/v5/account
GET    /api/v5/devices
POST   /api/v5/devices/register
PATCH  /api/v5/devices/:deviceId
DELETE /api/v5/devices/:deviceId
POST   /api/v5/p2p/tickets
GET    /api/v5/p2p/bootstrap
WSS    /api/v5/signaling
```

`deviceId`、目标设备和 P2P ticket 的授权均由服务端用当前会话的租户范围验证。客户端请求中即使出现 `tenant_id` 也必须忽略或拒绝。

## 5. 服务器技术选型与资源保险丝

### 5.1 运行时与存储

- Node.js 24 LTS、TypeScript、Express 和 `ws`。
- SQLite，驱动固定为 `better-sqlite3@12.10.0`。
- 数据库启用 WAL、外键和合理的 busy timeout；启动时执行显式、可回滚的 schema migration。
- 认证和设备目录持久化；presence、打洞临时状态和速率限制计数可保存在内存中。

### 5.2 注册资源保险丝

注册属于公开且高成本的入口，需独立于普通限流设置闭锁式保险丝：

- `auth.db` 达到或超过 64 MiB：立即关闭注册。
- 数据盘剩余空间低于 2 GiB：立即关闭注册。
- 可用内存低于 256 MiB：连续 3 次采样后关闭注册。
- Node 进程 RSS 高于 384 MiB：连续 3 次采样后关闭注册。
- 1 分钟 load average 高于 1.5：连续 3 次采样后关闭注册。

保险丝触发后保持关闭，不因单次指标恢复自动重开。管理员检查容量、异常注册和数据库状态后，通过受保护的运维命令显式重新开放。注册关闭不影响已有用户登录和已认证设备通信。

## 6. 设备身份与租户隔离

每次客户端安装生成稳定随机 `device_id` 和 X25519 长期密钥对。私钥只保存在本机安全存储，服务端只保存公开密钥。

客户端种类固定为：

- `windows-winforms-detector`
- `windows-wpf-detector`
- `android-detector`
- `android-receiver`

首发配额为每个账号最多 5 个检测端、3 个接收端。离线设备可由用户删除；重新安装后的新设备必须重新注册。设备更名、排序和删除只允许同租户会话操作。

服务端发送设备清单和信令时，应从认证上下文注入 `tenant_id`；数据库访问层不提供无租户条件的设备查询方法。跨租户 ID 猜测必须统一返回不存在或无权访问，并加入自动化测试。

## 7. P2P 传输协议

### 7.1 固定依赖

- KCP 使用 `skywind3000/kcp`，固定提交 `8004f7eba5d1bf33f0691eef5f887f2cd3140cb5`。
- libsodium 固定 `1.0.22`。
- Android NDK 固定 LTS `27.3.13750724`，CMake `3.22.1`。
- Windows WinForms 原生库必须能由 Visual Studio v141 工具链生成并在真实 Win7 SP1 x64 上运行。

原生依赖通过项目内窄 C ABI 封装层暴露，C# 使用 P/Invoke，Android 使用 JNI。各端共享协议常量和测试向量，不各自重新实现密码算法。

### 7.2 建链流程

1. 发起设备通过已认证 HTTPS 请求同租户目标设备的短期 P2P ticket。
2. 服务端验证两端会话、设备状态、租户和角色组合，签发短期、一次性、绑定双方设备 ID 的票据。
3. 双方向 UDP `3478` 发送带票据的 rendezvous 探测包；服务端只返回观察到的公网 IP/端口并通过 WSS 交换候选地址。
4. 双方同时向局域网候选地址和公网候选地址打洞，首个完成认证握手的路径胜出。
5. 使用双方 X25519 身份和临时密钥完成 `crypto_kx` 会话密钥派生；ticket、防重放 nonce、双方设备 ID 和协议版本进入握手认证数据。
6. 建立 KCP 会话，在 KCP 分片交给 UDP 前使用 XChaCha20-Poly1305 加密和认证。

### 7.3 协议约束

- 应用协议版本从 `5` 开始，帧头包含版本、消息类型、发送设备、接收设备、序列号和时间戳。
- 每个方向使用独立密钥和单调递增 nonce；旧 nonce、重复序列号和过期 ticket 必须拒绝。
- UDP 安全 MTU 固定为 1200 字节，避免常见公网路径上的 IP 分片。
- keepalive 每 15 秒一次，45 秒无有效认证数据判定离线。
- 密钥轮换、重连或网络切换都创建新会话，不复用旧 nonce 空间。
- 报警元数据和截图使用有长度上限的二进制帧；接收前先校验长度、认证标签和消息类型。

KCP 的参数需要由阶段 0 实测确定，不能仅凭局域网结果决定。必须覆盖 10% 丢包条件下的重传、乱序、重复包和 2 MiB 文件完整性。

## 8. 离线队列与失败行为

检测端维护本地加密 outbox：

- 每台检测设备最多保存 200 条报警，最长保留 7 天，先到上限者触发淘汰。
- 报警元数据与截图作为一个可重试事务记录，写入完成后才进入发送队列。
- 接收端按报警 ID 幂等确认；检测端收到认证 ACK 后删除本地记录。
- 网络恢复后按时间顺序限速补发，实时报警优先，避免恢复瞬间挤占推理和 UI。
- 超限淘汰、连续发送失败和队列积压必须在检测端 UI 明确显示并写入脱敏日志。

打洞超时、目标设备离线、UDP 被阻断或密码握手失败时：

1. 不将报警上传到 VPS。
2. 不回退到 WebSocket、HTTP 或其他中继。
3. 将报警保留在本地 outbox，并向用户显示“接收端不可达/等待直连”。
4. 在受控退避后重新获取 ticket 和候选地址，不能无限复用旧票据。

因此，纯 P2P 模式提供的是隐私优先的有界最终投递，不是对所有网络环境的强可达保证。

## 9. 客户端体验与自定义服务器

四类客户端统一增加登录页和服务器选择：

- 默认显示项目预置服务器。
- 用户可填写自定义 HTTPS/WSS 服务器地址并保存多个配置。
- 切换服务器视为切换独立账号域；不同服务器的令牌、设备 ID 注册记录和缓存不得混用。
- 自定义服务器必须通过 TLS 证书校验，不提供“忽略证书错误”的常驻选项。
- 登录后显示当前账号、当前服务器、设备身份、P2P 状态和离线队列状态。

检测端只展示同租户接收端；接收端只展示同租户检测端。旧的共享 API Key 配置在 5.0 中不再参与认证，升级时要求用户重新登录和注册设备。

## 10. 阶段 0 技术闸门

阶段 0 必须在账号系统和全端 UI 大改之前完成。任一硬闸门失败，都应调整 5.0 架构或终止纯 P2P 路线，不能把风险留到发布前。

### 10.1 Windows / Win7 闸门

- 使用 v141 构建 KCP、libsodium 和最小 C ABI 封装。
- WinForms .NET Framework 4.7.2 通过 P/Invoke 完成密钥协商、加解密和 KCP 收发。
- 在真实 Win7 SP1 x64 VM 上验证加载、握手、持续传输、重连、休眠恢复和退出清理。
- 检查发行目录仅含所需 DLL，不引入 Win7 不支持的运行库或 API。

### 10.2 Android 原生闸门

- 使用 NDK `27.3.13750724` 和 CMake `3.22.1` 同时为检测端和接收端构建 JNI 库。
- 验证至少 arm64-v8a，按现有设备支持策略决定是否保留 armeabi-v7a。
- 覆盖后台/前台 Service、网络切换、Doze、进程重启和 JNI 异常边界。
- APK ABI、签名和体积检查进入现有构建/发行验证。

### 10.3 真实 NAT 闸门

测试组合至少覆盖：

1. 家庭宽带 NAT ↔ 移动网络。
2. 两个不同家庭宽带 NAT。
3. CGNAT、对称 NAT 或严格企业网络代表环境。

每一类至少进行 20 次独立建链尝试，重取 ticket 和端口，不用同一长连接冒充多次测试。阶段 0 通过标准：

- 同一局域网直连成功率 100%。
- 三类跨 NAT 环境中至少两类达到 75% 或更高成功率。
- 成功建链中位数不超过 5 秒，P95 不超过 15 秒。
- 10% 模拟丢包下传输 2 MiB 数据，最终 SHA-256 一致。
- 报警正文和截图未出现在 VPS 数据库、文件、日志或抓包后的应用层明文中。

第三类网络失败可以作为“纯 P2P 不可达”的已知边界，但必须被 UI 正确呈现，不能用中继掩盖。

## 11. 分阶段实施

### 阶段 0：可行性原型

完成原生库、Win7、Android JNI、协议测试向量和真实 NAT 验证，只做最小控制面原型，不改现有 4.x 生产协议。

### 阶段 1：服务端控制面

升级 Node 24，加入 SQLite migration、注册/登录/会话、设备目录、资源保险丝、审计和同租户信令。新接口使用 `/api/v5` 和独立 WSS 路径，便于在发布前隔离测试。

### 阶段 2：共享原生传输层

固化 C ABI/JNI、KCP 参数、加密帧、票据握手、重放保护、网络切换和离线队列。建立跨平台协议测试向量与故障注入测试。

### 阶段 3：四端接入

按 WinForms、Android 接收端、Android 检测端、WPF 的顺序或根据维护优先级接入账号、服务器配置、设备注册、P2P 状态和 outbox；每接入一端都保持可独立验证。

### 阶段 4：硬切换和发布

在测试环境完成全端 E2E 后发布 5.0。客户端升级后重新登录，不兼容 4.x API Key；服务端停止 4.x 报警中继入口，但公共更新包和模型下载继续保留。

## 12. 测试与验收

### 12.1 服务端

- 注册成功、用户名冲突、密码错误、令牌轮换和吊销。
- scrypt 并发 1、队列 8、限流和保险丝闭锁/管理员重开。
- SQLite migration、崩溃恢复、WAL 和容量边界。
- 对每个设备和信令 API 做跨租户 ID 猜测测试。
- 证明报警和截图字段无法经服务端 API/WS 写入持久化层。

### 12.2 协议与原生层

- Windows 与 Android 使用同一测试向量验证密钥派生和 XChaCha20-Poly1305。
- 乱序、丢包、重复、篡改、截断、超长帧、nonce 重放和过期 ticket。
- KCP 会话创建/释放、频繁重连、内存增长和并发多接收端。
- 2 MiB 传输 SHA-256、MTU 1200 和 10% 丢包故障注入。

### 12.3 四端 E2E

- 两个账号分别注册检测端和接收端，只能发现并连接自己的设备。
- 四种检测端/接收端组合覆盖 WinForms、WPF、Android 检测和 Android 接收。
- 预置服务器、自定义服务器、切换服务器、退出登录和会话过期。
- 接收端离线后报警进入 outbox，恢复直连后按序补发并去重。
- 无法打洞时没有 VPS 中继流量，UI 显示明确失败，队列上限和 7 天 TTL 生效。
- Windows 真实 Win7 VM 与 Android 真机完成长时间运行和网络切换。

### 12.4 部署验收

- 先部署独立测试实例和数据库，备份/恢复演练通过后再切生产。
- Nginx 继续复用当前 SNI 架构；新增 WSS/HTTPS 路由和 UDP `3478` 前，以 `Server-infra` 当前事实和变更流程为准。
- 防火墙只开放需要的 TCP 控制面和 UDP rendezvous 端口。
- 监控登录失败率、注册保险丝、会话数、在线设备数、ticket 成功率、Node RSS、磁盘和 SQLite 大小；不采集报警内容。
- 发布前完成四端安装包、更新接口、模型按需下载和从 4.x 升级到 5.0 的人工验收。

## 13. 可行性结论与剩余风险

基础账号、SQLite 租户隔离、四端登录和自定义服务器在现有架构上可实现。KCP + libsodium 也能覆盖可靠传输和端到端加密，但真正决定方案是否成立的是 Win7 原生兼容性、Android JNI 稳定性和目标用户网络中的 UDP 打洞成功率。

严格禁止中继意味着某些 NAT 和防火墙环境必然不可达，这是架构选择而不是待修复的小概率 bug。只要阶段 0 达到既定成功率，并接受“失败时本地排队、等待直连”的产品语义，方案可进入 5.0 实施；若真实网络结果明显低于闸门标准，应先重新选择可达性与隐私之间的产品取舍，再开始大规模客户端改造。
