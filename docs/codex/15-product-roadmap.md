## 1. 目标定位

VisionGuard 将从“多端视觉检测与告警应用”演进为“边缘智能探测平台”。产品核心不是某个 YOLO 模型或某一种摄像头，而是稳定完成以下闭环：

```text
多源感知 -> 边缘推理与融合 -> 标准报警事件 -> 可靠加密传输 -> 用户处置 -> 设备持续运维
```

长期能力分为三层：

- **Detector Platform**：视觉、毫米波、PIR、门磁、振动、声音和环境传感器的统一接入、健康检查、推理与融合。
- **Reliable Event Network**：统一事件信封、本地 outbox 和幂等 ACK；所有公网业务数据统一通过 Server，使用 HTTPS/WSS `443` 加密传输，由 Server 负责权威入库、可靠投递、设备在线感知和离线兜底，不再规划 P2P、ICE、STUN 或 TURN 通道。
- **Device & Fleet Cloud**：Server 与 Web 控制台属于完整交付系统，以控制台为最高权限管理入口，覆盖账号租户、场地、探测器、传感器、事件数据、配置、模型、OTA、调试、审计、运行指标和商业配额。

### 1.1 产品对象

产品不再把 WinForms、WPF 和 Android 检测端仅称为泛化“客户端”，而是统一纳入探测器体系：

| 对象 | 定义 |
|---|---|
| Detector | 能够产生标准 Observation / AlertEvent 的探测器总称 |
| Visual Detector | 现有 WinForms、WPF、Android 检测端；以屏幕、窗口或摄像头视觉推理为核心 |
| Edge Detector | 未来 Linux ARM64 开发板探测器；可组合视觉、毫米波、PIR、门磁和环境传感器 |
| Sensor | 被探测器采集和管理的单一感知来源，本身不一定具备完整联网与事件判断能力 |
| Receiver | 接收、解密、展示和处置报警的终端 |
| Web Management Console | 管理场地、探测器、传感器、配置、模型、OTA 和审计的 Server Web 控制台 |

三类现有 Visual Detector 是长期正式产品对象，后续应逐步接入统一设备身份、能力声明、Event Protocol、Management Agent 和 Web 控制台；不能因为开发板成为未来重点而将现有视觉探测器降级为临时兼容实现。

## 2. 产品原则

1. **可靠送达高于链路优化**：所有公网业务统一经 Server，优先保证报警入库、送达、可追踪和可诊断，不以 P2P 直连率或节省中继带宽增加系统复杂度。
2. **边缘判断优先**：原始传感器数据尽量留在现场；向外发送标准事件和必要证据，减少隐私风险与网络依赖。
3. **协议先于客户端**：所有检测端共享设备身份、能力声明、事件、ACK 和错误语义；界面和运行时可以不同。
4. **视觉是证据，不是全部事实**：使用低功耗触发传感器发现异常，使用视觉、毫米波或其他确认传感器提高可信度。
5. **漏报优先于误报**：允许在可管理范围内误报，不接受已知、可避免或静默发生的漏报；通过高召回目标、冗余传感器、故障报警和真实样本验证降低漏报风险，但不做无法证明的“绝对零漏报”承诺。
6. **Win7 当前实现与计划边界**：Windows WinForms / Visual Detector 与 Windows 驻留程序均以 .NET Framework 4.7.2 x64 作为 Win7 SP1 x64 技术基线；驻留程序的 Win7 SP1 x64 兼容仍以目标系统上的启动、WSS、握手和远控实测为发布硬门槛；WPF、Android、Server、Web 控制台和未来硬件不承担 Win7 兼容义务。WinForms 检测端定位为 Windows 7 专属兼容端，Windows 10 及以上的 Windows 检测由 WPF 承担，两端部署的系统不重叠；因此 WinForms 的能力只需按 Win7 设计，不需要为更高版本系统分派实现。Win7 兼容是运行环境的下限要求，不是功能上限，也不得为了保住 Win7 而限制其他端的技术栈。
7. **失败必须可诊断并报警**：每个阶段都要能区分感知失败、融合失败、认证失败、Server 连接失败、设备离线和接收端离线；会造成探测盲区的故障本身也是报警事件。
8. **先证明场景价值**：开发板是验证载体，不是产品定义；首个商业版本必须聚焦一个明确场景和可量化效果。
9. **检测端功能基线跨端统一**：WinForms、WPF 和 Android 检测端共享同一份功能基线与布局范式，差异只允许出现在硬件加速后端和宿主平台相关的实现方式上。Win7 兼容约束的是运行时、依赖与可用 API，不构成降低功能要求的理由；平台差异不是长期功能缺口的免责理由，也不允许反向要求其他端退回低功能形态。

### 2.1 商业分层

| 产品层 | 组成 | 商业定位 |
|---|---|---|
| 免费版：纯软件视觉方案 | 当前已实现的 WinForms、WPF、Android Visual Detector，以及维持现有纯软件报警闭环所需的 Server 与 Receiver 能力 | 不接入检测硬件探测器时长期免费；云端存储、Server 转发和历史数据仍需合理配额，避免产生无限持续成本 |
| 付费版：硬件探测器方案 | 免费版全部能力 + Edge Detector、集成传感器检测单元或其他检测硬件探测器 | 系统一旦注册并启用检测硬件探测器即进入付费版；提供硬件设备管理、传感器拓扑、融合检测、独立运行、OTA 和诊断能力 |

免费版以目前已经实现的纯软件视觉方案为边界；系统一旦接入检测硬件探测器，即进入付费版。判定依据是系统中是否激活硬件探测器，不取决于硬件由 VisionGuard 自研、合作厂商提供还是兼容第三方设备。免费与付费共享 Detector Protocol、Event Protocol、账号、Server、Receiver 和 Web 控制台底座，不建立两套互不兼容的系统。具体免费配额、硬件售价或授权方式、服务期限和增值服务在试点成本数据形成后确定。

免费版是“免费使用的源码可见软件”，不等于开源软件。当前主线使用 `VGSAL-1.0`：纯软件视觉方案允许个人和组织免费内部使用；接入硬件探测器、再分发、对外托管或集成到第三方产品需要商业授权。`c43c0ff122043d477b442b7507d193b62ea321bb` 及其祖先和 `v4.4.3` 及更早发行版本继续适用发布时的 MIT License。许可证切换不能替代第三方依赖、模型、数据和素材的商业兼容性审查。

### 2.2 交付范围与目标市场

整套系统均属于产品交付物，包括：

- Visual Detector；
- Edge Detector 软件、固件与硬件；
- Android Receiver；
- VisionGuard Server；
- Web Management Console；
- 模型、升级、部署、备份恢复和诊断工具。

首个销售市场暂定中国大陆。产品设计需从第一阶段考虑个人信息告知、数据最小化、保存期限、删除机制、账号注销、访问审计和安全事件处置。是否提供客户私有化部署作为后续商业选项单独评估，不预设为首发必需能力。

## 3. 目标架构

```text
现场传感器
  摄像头 / 毫米波 / PIR / 门磁 / 振动 / 环境量
                         |
                         v
Edge Detector 或现有 Visual Detector
  采集 -> 推理 -> 融合 -> Event -> 本地加密 outbox
                         |
                         | HTTPS/WSS 443 / 设备身份 / ACK
                         v
                 VisionGuard Server
 权威事件存储 / 证据 / 在线状态 / 离线报警 / 去重 / 重试 / 审计
                    |             |
          WSS / 系统推送          | Web API
                    v             v
             Android Receiver   Server Web Console
           去重 -> 报警 -> ACK   场地 / 设备 / 数据 / 配置 / OTA / 调试
```

统一传输路径计划为：

1. 探测器主动建立出站 WSS `443`，用于认证、心跳、报警和控制；
2. 截图、证据、模型和固件使用 HTTPS `443` 上传或下载；
3. WSS 暂不可用时，探测器保留本地 outbox，并可按协议使用 HTTPS 补发事件；
4. Server 权威入库后再向在线 Receiver 分发，并对离线 Receiver 使用适合中国大陆终端的系统推送通道唤醒；
5. 实时画面若进入产品范围，只允许通过受控 Server 转发，并独立核算带宽、权限和容量，不重新引入端到端直连。

不再规划 P2P、ICE、STUN 或 TURN，减少跨端原生依赖、NAT 穿透测试和多路径状态机。代价是 Server 带宽、容量和可用性责任上升，因此必须优先建设持久化 outbox、幂等入库、逐接收端 ACK、容量监控、备份恢复和独立的 Server 外部健康监测。

## 4. 统一探测模型

### 4.1 Observation

传感器适配器只产生观察值，不直接决定云端接口或接收端 UI：

```text
Observation
- sourceId
- sensorType
- occurredAt
- confidence
- measurements
- region
- health
```

### 4.2 AlertEvent

融合层把一个或多个观察值变成标准报警：

```text
AlertEvent
- eventId
- detectorId
- eventType
- severity
- confidence
- evidence[]
- occurredAt
- expiresAt
```

同一个 `eventId` 允许重试，但接收端只能落库和提示一次。多接收端分别维护 ACK 状态，探测端或服务器不能用单个“已发送”布尔值替代逐设备送达结果。

### 4.3 系统状态报警

Server 必须把设备连通性当作受监控信号，而不是只在设备列表上显示灰色状态：

- 探测器按设备类型上报心跳和业务状态，Server 维护 `online -> suspected_offline -> offline -> recovered` 状态机；
- 超过可配置的失联阈值后，由 Server 生成标准 `DeviceOfflineAlert`，进入与检测报警相同的入库、分发、ACK、重试和审计链路；
- 同一次失联只生成一个活动报警，避免重连抖动造成报警风暴；恢复连接后生成关联的 `DeviceRecoveredEvent`，保留失联开始、恢复时间和持续时长；
- 离线报警只能说明设备、供电、现场网络或客户端进程至少一项异常，在设备恢复并上报诊断前不得伪造具体原因；
- 传感器断开、摄像头不可用、推理线程停滞、存储不足和 outbox 堵塞等可能导致漏报的状态，也必须形成可送达的故障报警；
- Receiver 不在线时，Server 保留待送达状态，并使用系统推送或下次连接补发，不能因为接收端离线静默丢弃；
- Server 自身宕机时无法由自身产生报警，必须由独立于 VisionGuard 业务进程的外部监控检查公网健康、队列和数据库，并通过另一条通知通道告警。

失联阈值和抖动宽限需要按探测器类型配置。当前 4.x 的 45 秒幽灵阈值可作为兼容起点，但商业硬件最终值必须根据心跳周期、网络环境和可接受盲区通过故障注入确定。

## 5. 开发板边缘探测器方向

### 5.1 原型定位

第一代 Edge Detector 采用 Linux ARM64 开发板验证产品闭环，至少包含：

- 一个摄像头输入；
- 一个低功耗触发传感器，优先毫米波或 PIR；
- 一个确定性数字输入，优先门磁；
- 本地 ONNX 推理与两类传感器融合；
- 本地持久化 outbox；
- WSS/HTTPS 可靠传输、网络切换和断线补发；
- 独立设备身份和独立联网；
- 接受 Server Web 控制台的远程配置、诊断、模型更新和 OTA；
- 72 小时连续运行、断网恢复和异常断电验证。

首版不同时接入大量传感器，避免驱动、供电、安装和测试矩阵失控。

### 5.2 商业硬件边界

开发板原型通过后，商业硬件再评估工业 SOM 或定制载板。正式设备至少需要 eMMC、硬件看门狗、掉电保护、设备唯一密钥、温度监控、A/B 升级回滚、有线网络以及可选 Wi-Fi / 4G。普通开发板和 SD 卡仅用于验证，不作为长期批量交付方案。

### 5.3 传感器接入边界

- 板内低速器件：GPIO、I2C、SPI；
- 工业或较远距离：RS-485 / Modbus；
- 网络传感器：版本固定且有身份认证的 MQTT 或项目适配协议；
- 视频：USB、CSI 或 RTSP；
- 对外报警：统一 VisionGuard Event Protocol。

传感器不得绕过 Edge Detector 直接把私有格式扩散到云端。

### 5.4 独立联网与网关模式

开发板探测单元必须具备独立联网能力，不能依赖现场中控或另一台 PC 才能发送报警。基础网络能力为：

- 有线 Ethernet 作为商业设备的优先接入方式；
- Wi-Fi 作为常用可选接入；
- 4G / 蜂窝网络作为特定 SKU 或外接模块，不要求首个原型内置；
- 主动连接 VisionGuard Cloud，完成认证、配置同步、心跳、事件入库与可靠兜底、模型和 OTA；
- 所有公网报警、证据和管理流量统一通过 Server，不建立到 Receiver 的直连数据通道；
- 无互联网时继续本地检测、融合、联动和持久化排队，网络恢复后补发；
- 网络切换不改变设备身份、事件 ID 或逐接收端 ACK 状态。

同一套 Edge Runtime 支持三种角色；现有 Visual Detector 仍以 Detector 模式参与统一网络和管理体系：

| 模式 | 适用场景 | 行为 |
|---|---|---|
| Detector | 单个智能探测器 | 自己采集、判断、联网和发送事件 |
| Gateway | 多个轻量或第三方传感器 | 提供协议转换、身份代理、离线队列和现场网络出口 |
| Detector + Gateway | 首代推荐形态 | 自身完成视觉/融合检测，同时管理少量下游传感器 |

第一代不单独开发中控硬件。开发板以 `Detector + Gateway` 运行，需要时管理门磁、PIR、毫米波或 Modbus 设备；只有现场规模、接口数量或性能证明确有必要时，才拆分专用网关。

### 5.5 探测器管理代理

每台开发板探测器内置受控的 Management Agent，向 Web 控制台提供以下机器可验证能力：

- 首次配网、设备激活、证书和稳定 `deviceId`；
- 上报硬件、系统、传感器、模型和协议能力清单；
- 上报在线状态、温度、存储、内存、推理耗时、传感器健康、Server 连接质量和 outbox 积压；
- 接收带版本的目标配置，回报实际生效配置和失败原因，能够识别配置漂移；
- 管理传感器绑定、命名、区域、校准、启停、阈值和融合规则；
- 下载、校验、启用和回滚模型；
- 执行签名固件 OTA、A/B 切换和失败回滚；
- 导出脱敏诊断包和有限诊断动作，不默认提供无限制远程 Shell；
- 对配置、模型、固件、重启和恢复出厂等操作生成审计记录。

Management Agent 不参与具体 UI。它只实现稳定的设备管理协议，使 Android 接收端、Web 控制台和未来其他管理端使用同一套授权与状态语义。

## 6. Server Web 管理控制台

### 6.1 定位

Web 控制台是整套系统的最高权限管理中控，直接复用 Server 的账号、租户和设备权限体系。它负责完整的数据与设备管理，包括 Visual Detector、Edge Detector 和下游传感器；它不承担现场推理，Android Receiver 继续负责移动端即时报警。

个人或少量设备可以主要使用 Android Receiver，但系统所有者仍可通过 Web 控制台获得最高管理和调试能力。当前 Windows 检测端不扩张为中控，Win7 兼容端不承担商业设备管理职责。

### 6.2 管理范围

Web 控制台最终覆盖：

- **组织与场地**：租户、成员、角色、场地、区域和设备拓扑；
- **设备生命周期**：激活、配对、命名、移动、停用、替换、证书轮换和恢复出厂；
- **探测器管理**：能力清单、运行状态、传感器健康、推理性能、网络路径和本地队列；
- **传感器管理**：绑定、类型、端口、区域、校准、阈值、融合关系和故障状态；
- **配置管理**：单设备配置、场地模板、版本、下发结果、差异和回滚；
- **模型与 OTA**：版本清单、兼容约束、灰度、暂停、回滚和失败设备列表；
- **事件与处置**：报警查询、接收人送达状态、确认、备注和必要证据访问；
- **诊断与审计**：脱敏日志、网络测试、运行指标、操作审批和完整审计记录。
- **数据管理**：事件检索、证据查看、导出、删除、保留策略、备份状态、容量和数据完整性检查。

### 6.3 安全与操作边界

- 控制台最高权限不等于所有账号共享同一权限；至少区分系统管理员、租户所有者、运维人员和只读审计角色；
- 默认不保存原始连续视频；报警事件和必要证据按权限与保留策略进入 Server，控制台可在授权范围内查看和管理；
- 所有公网 HTTPS、WSS 和 Server 转发通信必须加密；Server 内部可以处理业务明文，但数据库、对象存储、备份、日志和导出文件仍需访问控制、最小暴露和必要的静态数据保护；
- 控制台登录、最高权限操作和紧急运维入口必须使用强认证、完整审计和会话保护；
- 配置和命令必须带目标版本、操作者、设备范围和幂等请求 ID；
- 批量升级、恢复出厂、密钥轮换等高影响操作需要二次确认、分批执行和停止开关；
- 控制台显示“期望配置”和“设备实际配置”，不能在下发请求成功后直接假定已经生效；
- 探测器离线时允许保存待执行配置，但必须显示尚未生效；
- 不把浏览器到设备的临时直连当作管理前提，所有管理状态经 Server 可审计控制面协调。

### 6.4 分步交付

Web 控制台不一次做成完整运营平台：

1. **最小控制台**：登录、场地、设备列表、详情、健康、单设备配置和审计；
2. **探测器控制台**：传感器拓扑、校准、融合规则、模型与 OTA；
3. **商业控制台**：成员角色、配置模板、批量灰度、事件处置、多场地和运营指标。

每一步都要求 Server API 和自动化权限测试先成立，再增加页面；不能让 Web 页面成为唯一实现业务规则的位置。

## 7. 数据传输与保留政策

### 7.1 概念

**传输政策**回答“什么数据何时进入 Server、失败时如何重试、如何送达 Receiver”。当前路线统一采用 Server 中心架构，不再保留 P2P 分支。

**保留政策**回答“数据保存在哪里、保存多久、谁能查看、何时删除、备份多久后消失”。报警文字、截图、连续视频、设备状态、调试日志和审计记录应分别制定，不使用同一个期限。

### 7.2 建议的传输政策

| 数据类型 | 主要路径 | Server 行为 |
|---|---|---|
| 报警事件与检测结果 | 探测器通过 WSS/HTTPS 立即上传 Server | 权威入库、去重、分发、记录逐接收端送达状态 |
| 报警截图与短证据 | 探测器可靠上传 Server | 按事件关联保存，供控制台和授权 Receiver 查看 |
| 设备离线与恢复 | Server 根据心跳状态机生成系统事件 | 按报警入库并送达 Receiver；恢复时关联关闭或更新活动报警 |
| 实时视频/实时画面 | 默认不进入首版；需要时由 Server 受控转发 | 不录制、不长期保存，单独实施并发、带宽、权限和限流 |
| 配置、命令、校准 | Server 控制面 | 记录期望值、设备实值、操作者、结果和审计日志 |
| 模型、固件与 OTA | HTTPS 下载 | 校验版本、目标硬件、签名、灰度和回滚状态 |
| 设备遥测与诊断 | 探测器定期批量上传 | 限频、聚合，异常时允许短期提高采样率 |

报警事件以 Server 成功持久化或 Receiver 成功持久化作为 ACK 条件，不能以“网络发送函数返回成功”当作已送达。探测器在收到满足策略的 ACK 前保留本地 outbox。

### 7.3 建议的首版保留政策

以下是产品默认值草案，不是法律固定期限；上线前应根据成本、客户合同和实际处理目的调整：

| 数据 | 免费版默认 | 付费版默认 | 说明 |
|---|---:|---:|---|
| 报警事件元数据 | 7 天 | 90 天 | 用户可主动删除；付费层可提供可配置期限 |
| 报警截图/短证据 | 72 小时 | 30 天 | 明显高于元数据的隐私与存储成本 |
| 连续视频 | 不保存 | 不保存 | 若以后提供录像，作为独立功能重新做容量与合规设计 |
| 原始设备遥测 | 7 天 | 30 天 | 更长周期只保留聚合指标 |
| 普通调试日志 | 7 天 | 30 天 | 默认脱敏，不记录密码、令牌和完整图片内容 |
| 安全与管理审计 | 90 天 | 180 天 | 包括登录、配置、导出、删除、升级和高权限操作 |
| 配置历史 | 最近 10 个版本 | 最近 30 个版本 | 支持回滚并限制无限增长 |
| 在线备份 | 主数据删除后最多 30 天自然过期 | 主数据删除后最多 30 天自然过期 | 删除期间停止其他处理并保持必要保护 |

控制台必须显示各类数据的当前保留规则、预计占用、删除结果和备份过期时间。用户删除与账号注销需要覆盖主数据库、对象存储、搜索索引和异步队列；备份无法立即逐条删除时，应在约定周期内自然过期且不得恢复用于正常业务。

中国大陆首发需遵循“为实现处理目的所必要的最短时间”原则，并向用户明确告知处理目的、数据种类、保存期限或确定方法以及删除和注销途径。具体合规文本和敏感信息判断在上线前由熟悉目标场景的专业人员复核。

### 8.2 可行性与已发现的改造点

总体可行。主要工程量在来源状态隔离、跨端协议、窗口采集稳定性和加速真实性验证，不是简单增加 GPU 开关或复制四套界面。

- 两端退出都会释放控制连接，必须由独立驻留组件接收远程启动请求；当前业务级暂停/恢复不能启动已退出的进程。
- WPF 已接入 DirectML/CPU 后端选择，并实现多路独立窗口配置、引擎、定时器与报警冷却的来源协调器；停止时等待执行中 Tick 后再释放 Session。当前实现仍以四路为落地规模、并在运行层拒绝多路 CPU，2026-09-13 的边界重划要求改为容量档位与性能提示（见第 8.12 节）。真实窗口人员捕获和逐路 3 FPS 已自动验证，动态窗口重定位和故障矩阵仍需补验。
- 窗口采集包含同步 `PrintWindow`，黑屏、最小化、权限差异及目标窗口阻塞需要实测；不能把捕获失败当成无目标。
- 窗口重定位仅靠标题首个匹配不适用于多路及远程重新打开，需要处理重名、标题变化和绑定歧义。
- Server 当前连接身份会让相同角色和设备 ID 的新连接替换旧连接，驻留不能直接冒充主程序连接。
- 控制回执已按请求者关联并区分转发与完成；接收端只消费字段完整的最终结果，仍需在隔离通道做真实多端并发和超时 E2E。
- 报警、历史及设备状态目前以设备为单位，新增来源必须覆盖 WS、HTTP 校验、持久化、历史响应、缓存、通知和截图关联，不能仅增加实时消息字段。

### 8.3 推理后端与设备支持策略

WPF 建议先验证 ONNX Runtime DirectML，CUDA 作为性能或兼容性不达标时的候选。DirectML 可沿用 ONNX/C# 并为核显扩展保留空间，但已处于持续维护阶段，新功能转向 WinML；推理业务必须通过后端接口隔离。CUDA 需要另外验证 ORT、CUDA、cuDNN 版本及发行依赖，不能盲目升级。

WinForms 固定使用 CPU，并维持现有 ONNX Runtime 1.1.0：它是 Windows 7 专属端，而 Win7 上没有可维护的推理硬件加速路径，因此不为它规划 GPU 后端、也不升级推理运行时。WinML 要求 Windows 11 24H2 以上、OpenVINO 不支持 Win7、DirectML 需要 DirectX 12、CUDA 只到 10.2 且需老驱动配老版本运行时，都不进入 WinForms 的候选。若多路 CPU 帧率实测不可接受，出路是重新评估运行时升级，而不是降低路数或帧率。

Android 建议先验证 QNN/Hexagon NPU；小米 15 的骁龙 8 Elite 对应 HTP v79。若量化精度、集成或持续运行不达标，再验证 NCNN Vulkan GPU。首期只需交付其中一种合格加速，不同时铺开多种未经验证的后端。

2026-09-08 核验的官方 QNN 代表性移动平台如下，属于候选清单，不是 VG 已支持清单：

| SoC | HTP 目标 | 本次安排 |
|---|---|---|
| 骁龙 888 | v68 | 未适配前 CPU |
| 骁龙 8 Gen 1 / 8+ Gen 1 | v69 | 未适配前 CPU |
| 骁龙 8 Gen 2 | v73 | 后续候选，未适配前 CPU |
| 骁龙 8 Gen 3 | v75 | 后续候选，未适配前 CPU |
| 骁龙 8 Elite | v79 | 小米 15 首期验证 |
| 骁龙 8 Elite Gen 5 | v81 | 后续候选，未适配前 CPU |

不能从系列名称推断所有骁龙 7/8 系列都可用，也不对其他 SoC 家族默认开放加速。设备匹配只是资格检查，随后必须通过运行库加载、模型加载、真实推理和实际执行后端确认。支持规则应记录设备/SoC、系统与驱动、运行库、模型变体及验证结果。

设置页区分 CPU 运行、正在验证、GPU 已启用、NPU 已启用、加速失败并回退 CPU；显示当前硬件、可用类型及失败原因。初次验证，以及驱动、模型或运行库变化后重新检查。部分计算回退 CPU 时诊断信息必须如实记录，不能以发现 GPU、加载库成功或速度变快作为唯一证据。

模型清单和缓存增加后端、输入尺寸、精度、目标架构及校验信息。QNN 专用模型不能直接作为 CPU 回退模型，继续保留 CPU ONNX 下载路径；新模型变体同样按需下载，不打包进入客户端。

RTX 2080 Ti 四路各 3 次/秒是验证目标，不是已证明的任意模型组合性能。要同时检查采集、预处理、推理、报警和 UI 开销；不以总计 12 次/秒代替每路达标。

### 8.4 设备、来源与控制协议

采用设备 → 来源两层结构：同一检测设备是父组，来源数量按容量档位与协议协商确定（2026-09-13 起不再固定四路，四路是当时的落地规模）；来源使用持久 `sourceId`，不以显示名称作为身份。WinForms、Android 检测端、旧客户端及旧历史映射到默认单来源，保留原 `deviceId` 和 `alertId`。

| 对象 | 职责 |
|---|---|
| 设备 | 设备身份、驻留状态、主程序状态、硬件与控制能力 |
| 来源 | 窗口绑定、检测配置、运行状态、独立冷却 |
| 报警事件 | 事件 ID、设备 ID、来源 ID、事件发生时的来源名称快照 |
| 控制请求 | 请求 ID、目标设备/来源、作用域、操作、有效期和执行结果 |

驻留组件使用独立组件身份与连接表，同主程序归入同设备。能力声明区分应用级启动和来源级启停，不复用现有 resume 表达进程启动。

请求增加 `requestId`、目标来源、有效期、去重与幂等处理。回执区分接收/转发、执行完成、失败及超时，按请求关联返回；启动成功以主程序完成握手为准，不以创建进程或 Server 转发成功为准。保留授权检查，仅向相应请求者返回结果或使用明确定义的状态订阅。

历史增加设备和来源联合筛选；来源改名不改写旧事件名称，删除来源不删除其历史身份，新建同名来源不混入旧记录。截图继续按唯一事件 ID 关联，延迟补图也必须归入正确来源。检查历史保留配额，避免高频来源无意挤掉其他来源的全部历史。

新协议不再承载旧字段兼容：通过独立 Server 进程、端口、数据目录和强制 `channel` 将仍运行的旧版本隔离。新接收端与检测端只在同一通道联调，不支持来源控制或缺少当前字段的客户端不能进入该广播域。

### 8.5 驻留远控行为

建议采用用户登录会话中的独立后台程序：启用后随用户登录启动，主程序退出不影响它；首期不由 Windows 系统服务直接承担窗口采集。后台保持 WSS，通过受限本地通信与主程序交互，只接受固定 VG 操作，不接受任意路径、Shell 或脚本。

| 情形 | 行为 |
|---|---|
| 主程序关闭或崩溃 | 上报状态，保持停止，不自动拉起 |
| 远程打开 | 打开指定 WPF 或 WinForms；所有检测来源保持停止，等待手动启停 |
| 主程序已运行 | 返回已运行，不创建第二实例，也不修改监控状态 |
| 远程关闭 | 请求正常退出；驻留保持在线；退出失败如实报告 |
| 驻留禁用 | 关闭驻留连接、取消登录启动，并说明失去远程打开能力 |
| 不符合首期运行边界 | 如实报告失败或不可用，不自动改设备设置或解锁 |

接收端区分驻留在线、主程序运行、主程序响应、各来源监控状态。两种 Windows 客户端共用驻留实现，但区分应用类型和受控安装路径，加入单实例处理，防止用户启动和远程启动竞争。驻留配置独立保存，不直接与主程序并发写同一设置文件。

### 8.6 多来源检测、界面与降级（已批准计划）

每个来源拥有独立配置、监控状态、模型和冷却，公共调度器公平分配资源。每路只保留最新待处理画面，防止旧帧排队；同路禁止重入，同一推理 Session 的并发规则服从后端限制。停止和切换模型时，可靠等待正在执行的任务结束后再释放资源。2026-09-13 起本节的「四路」不再表示固定上限：来源数量由后端容量与协议协商决定；第 8.6.1 节的布局与操作范式继续作为跨端基线与验收依据。

通过采集接口预留其他设备来源，首期实现窗口采集。窗口重定位结合应用身份、窗口类别和标题规则；无匹配或有歧义时保持停止并提示重新绑定。一路窗口阻塞不得拖住其他来源；采集失败、黑屏和超时必须显式报告。

2026-09-13 修订：不再以「CPU 只允许单路」作为架构性禁止，也不能仅禁用 UI 按钮。容量档位与实测性能只作为提示基线：超出时明确提示性能可能不足，但不阻止启动、不自动减路、不自动降帧，档位由用户配置。GPU 运行中失败仍须上报原因、保留配置并让性能变化可见，不再默认停机全部来源；完整边界见第 8.12 节。

若模型组合不达标，先优化并报告瓶颈；不能静默降低频率或替换小模型，改变已确认目标须再由 owner 决定。

3 次/秒是性能能力基线；owner 主动延长某路检测间隔时，该路按配置验收。

#### 8.6.4 分批交付与通过条件

1. 先用四个独立浏览器窗口验证现有捕获方式取得真实画面。出现黑屏先定位捕获兼容性问题，再进行大规模改造；不使用图片直读绕过失败。
2. 交付 2×2 四路界面、逐路选择和配置交互，由 owner 在实际 Windows 桌面目检；确认后接通完整运行行为。
3. 四路分别显示正确图片与检测框，各至少命中一次 person。将一路换成无人画面再恢复，确认画面和检测结果确实更新。
4. 覆盖单路停止、换窗口、修改模型/阈值/遮罩，其他三路持续有效检测；验证关闭、重绑、移动、缩放、遮挡、最小化，以及容量提示、GPU 失败、远控目标隔离和迁移后不自动监控。
5. 运行相关契约测试、WPF Release 构建与产物检查，以及文档检查。四路 GPU 性能重新实测，按第 8.9 节逐路验收，不沿用三路结果、不以总吞吐代替逐路达标。

浏览器静态图片只证明真实窗口采集、人员检测与四路操作，不等同于动态业务视频、持续运行或完整检测端→Server→接收端报警链验收。未覆盖项与失败如实记入验证报告。保留 owner 已有改动；不自动改版本、提交或发布。

### 8.7 接收端体验

设备页使用可展开父组，组内显示来源名称、状态、模型、实际检测频率及异常。组状态聚合为全部运行/部分运行/全部停止等；保留现有设备排序和离线管理规则，不能把原有在线状态分组误当物理设备组。

逐路启停与配置操作有独立执行反馈。历史提供设备及来源筛选。通知偏好建议保存在当前接收端，以设备和来源为键，支持继承默认值或独立声音、振动和静音；系统通知渠道行为需要按 Android 约束验证。静音只影响提示，不停止检测或历史收录；四路报警不能被一个全局冷却互相压制。

### 8.12 检测端功能基线（跨端统一）

> 保存日期：2026-09-13。依据：owner 本次对话提出「把检测端的功能底座统一、只在硬件加速上做平台适配、解除 CPU 不可多路的边界、Android 只做宽屏布局、未来用外接 USB 摄像头或采集卡扩展来源」。状态：仅重新划定边界与规划，未开始实施，未修改任何代码。

**动机**：现行架构把「CPU 只允许一路」写成了运行层硬禁止，而 WinForms 在其主要兼容目标 Win7 上只能使用 CPU 推理，因此只要该限制存在，WinForms 在 Win7 上就不可能支持多来源，「三端功能对齐」也无从成立。Android 检测端同样是单来源、单相机、没有来源维度，且即将被改动的采集、推理、服务与存储层目前没有自动化测试覆盖。

**统一范围（基线要求，三端一致）**

| 能力 | 基线要求 |
|---|---|
| 来源模型 | 一个设备下可有多个来源；来源数量由后端容量与协议协商决定，不写死常量 |
| 来源身份 | 稳定 `sourceId` 与可改 `sourceName`；改名不改身份；槽位数量上限、每槽身份与配置持久化 |
| 逐来源配置 | 名称、采集目标、模型、类别、阈值、检测频率、报警冷却、遮罩、启停各自独立 |
| 逐来源运行 | 独立推理会话与独立冷却；一路停止、异常或采集失败不影响其他路 |
| 心跳与控制 | 上报 `sources` 数组与 `source-control`；逐来源命令与参数携带 `targetSourceId` |
| 告警链路 | 告警携带 `sourceId`/`sourceName`；持久发件箱；先发告警、收到确认后再发截图；离线补发时事件全量入历史，实时通知只取每路最新一条 |
| 故障与后端 | 区分采集、黑帧、推理、处理故障；实际后端与回退原因对用户可见 |
| 汇总操作 | 运行路数、异常计数、启动已配置来源、全部停止 |

**明确不统一的部分（只做平台适配）**

| 维度 | WinForms | WPF | Android |
|---|---|---|---|
| 运行时 | .NET Framework 4.7.2 x64 | .NET 9 + WPF | Kotlin / ART |
| 推理后端 | CPU（Win7 无可用加速技术） | DirectML，回退 CPU | NNAPI，回退 CPU |
| 采集来源 | 窗口、屏幕区域 | 窗口、屏幕区域 | 内置相机多路；外接 USB 摄像头与采集卡只保留设计预留 |
| 平台独有能力 | stunnel 兜底隧道、Win7 兼容 | Windows 宿主能力 | 前台服务与通知、SoC 白名单、NTP、网络感知、应用内更新 |
| UI 实现方式 | WinForms 控件 | XAML | Compose |

统一的是基线与布局范式，不是共享同一个运行时、同一个 UI 框架或同一份二进制。三端各自用本平台最合适的技术实现同一套能力和操作流，也不允许以平台差异为由要求其他端退回低功能形态。

**布局基线**

- 基准取第 8.6.1 节已批准的 WPF 布局：顶部汇总与整机操作，中部实时预览网格，右侧单一配置入口，配置遵循「采集目标 → 识别设置 → 检测参数 → 区域排除 → 保存」的操作流。
- WinForms 用 WinForms 控件实现同一分区、同一操作流和同一状态文案，不引入 WPF/XAML 依赖。
- Android 强制横屏：检测端锁定横屏方向，只做一套宽屏布局，平板竖放时同样显示横屏界面；**不实现窄屏折叠方案**，窄屏手机不作为支持目标。现有以竖屏布局为一等形态的实现需要收敛为宽屏，不保留两套控制台分支。相机竖装与横装属于部署方向，与 UI 方向是两件事，不应继续耦合在同一条布局分支上。

**接收端的同步范围（2026-09-13 追加）**

接收端纳入统一范围，但同步的是**来源模型而不是布局**：来源数量变化后卡片要能装下来（展开或分组），逐来源命名、启停、参数入口与通知偏好与检测端保持一致。接收端自身仍是手机竖屏形态，不套用检测端的宽屏布局。

**并发容量与性能提示（替代 CPU 单路硬禁止）**

- 不设「超过容量就拒绝启动」的准入闸门：容量配置与实测性能只作为**提示基线**，超出时明确提示该路性能可能不足，由 owner 决定是否继续运行；运行层不阻止、不自动减路、不自动降帧。
- 容量变化必须可见：DirectML 回退 CPU 会改变可用性能，此时上报变化与实际占用，不再默认停机全部来源。
- 保留推理类故障的保护与可诊断性：采集失败、黑帧、推理异常和后端初始化失败仍按故障处理并对用户可见，「回退到 CPU」本身不再是禁止条件。故障与性能不足必须分开表达，既不能把性能问题报成故障，也不能把故障当成性能问题放过。
- 移除「CPU 仅支持一路」这类固定文案，改为显示容量档位、当前占用与实际帧率。
- 每个后端的容量档位由用户自行配置，三端都要有对应设置入口；实现只提供可配置范围和说明，不预设产品档位。
- **红线不变**：不允许静默降级——不得悄悄降低帧率、悄悄少开来源或悄悄替换模型来掩盖性能问题。性能不足必须表现为可见提示，而不是「看起来正常但什么都没检测到」。

**WinForms 硬件加速：调研后撤销（2026-09-13）**

owner 先要求 WinForms 也开放硬件加速，随后确认了决定性的产品边界：**WinForms 检测端只在 Windows 7 上运行，Windows 10 及以上由 WPF 承担**，否则 WPF 就没有存在价值。因此 WinForms 的能力只需按 Win7 设计，不需要按运行环境分派后端。核实后的平台事实如下：

- DirectML 需要支持 DirectX 12 的设备和 Windows 10（作为系统组件自 Windows 10 1903 引入，也可经 `Microsoft.AI.DirectML` 可再分发包在更早的 Windows 10 版本上使用）。**Win7 既不具备 DirectX 12 也不具备 DirectML，因此 Win7 上的 WinForms 恒为 CPU**——这是平台限制，不是实现取舍。
- ONNX Runtime 从 v1.22 起把最低 Windows 版本提高到 10.0.19041，Windows 8.1 及以下不再被支持；Win7 从未被正式支持，只在旧版本中标注为「可能兼容」。
- `Microsoft.ML.OnnxRuntime.DirectML` 的目标框架是 `netstandard2.0`，兼容 .NET Framework 4.6.1–4.8.1，因此 `net472` 可以引用，并依赖 `Microsoft.AI.DirectML` 原生库。
- 现状差距：WinForms 锁定在 ONNX Runtime 1.1.0，远早于 DirectML 后端出现的版本，所以这不是「打开一个开关」，而是一次推理依赖升级。
- **Win7 上的替代加速技术调研结论（2026-09-13）**：DirectML 与 WinML 都要求 Windows 10 及以上；OpenVINO 经 Intel 官方确认不支持 Windows 7。CUDA 理论上存在但窗口极窄——CUDA 10.2 是最后一个支持 Win7 的版本（CUDA 11.0 起要求 Windows 10），需要 NVIDIA 显卡与 441.22 以上的老驱动，并且只配得上 ONNX Runtime 1.4–1.6 这一档老版本（新版本要求 CUDA 11/12）。NCNN Vulkan 在 Win7 SP1 上历史可用（NCNN 官方把 Windows 列为 known-working），但需要自研一整套 C++ 推理层与 P/Invoke 封装，且 Win7 的 Vulkan 驱动已停止更新、老驱动还可能被 NCNN 列入黑名单。**结论：Win7 上没有可维护的推理硬件加速路径**，因此 Win7 上的 WinForms 固定为 CPU，多路能力按容量模型保留，不因缺少加速而退回单路。
- **net472 的真实版本上限**：包元数据与社区实践一致显示 ONNX Runtime 对 .NET Framework 的显式支持止于 1.15.x，1.16 起不再显式面向 .NET Framework——这与 owner「更高版本在 net472 上不可用」的实测吻合。而 `Microsoft.ML.OnnxRuntime.DirectML` 1.15.0 确实存在，目标为 `netstandard2.0`（兼容 net472），依赖 `Microsoft.ML.OnnxRuntime.Managed ≥ 1.15.0`。因此 **net472 上存在可用的 DirectML 版本区间（约 1.4–1.15）**——该路径已核实存在，但按 2026-09-13 决定不采用（见下方结论）。附带核实的目标框架边界：`.NET Framework 4.7.3` 并不存在（微软从未发布），Windows 7 SP1 可安装的最高版本是 4.8、4.8.1 起不再支持 Win7；升级 TFM 到 4.8 在 Win7 上可行，但**不能解锁 ONNX Runtime 1.16+**，因为它止掉的是对整个 .NET Framework 的支持，与 4.7.x 还是 4.8 无关。

由此得出的结论：

- **WinForms 撤销硬件加速规划**：Win7 上没有可维护的加速路径（见上），而 WinForms 不部署在 Windows 10 及以上，所以面向 Windows 10 的 DirectML 方案对 WinForms 没有产品价值。WinForms 固定为 CPU 推理，不再规划 GPU 后端，也不引入按环境分派后端或双 ONNX Runtime 运行时。
- **ONNX Runtime 维持 1.1.0（2026-09-13 决定）**：不升级推理运行时，WinForms 保持现有的 1.1.0 + YOLOv5 + CPU 组合。已知代价：Win7 上的多路 CPU 帧率会停留在现版本水平，而升级 ONNX Runtime 是唯一仍可能生效的改善手段（DirectML、WinML、OpenVINO、CUDA、NCNN 五条路径均已排除）。若实测认为多路 CPU 不可用，应回到本条重新评估，而不是静默降低路数或帧率。
- CPU 容量纳入同一套提示模型：容量档位由用户配置，超出时提示性能可能不足但不阻止运行，不允许为规避性能问题退回单路。
- WinForms 的模型格式锁定为 YOLOv5 系列（`yolov5nu/su/mu` 的 320/640），不随 WPF 迁移到 YOLO26。三端因此不共用模型清单与输出解析器，「模型」在各端是各自支持的集合；逐来源的模型选择仍在功能基线之内。
- 验收边界：Win7 上的多路 CPU 帧率与稳定性必须实测取证，这是「CPU 多路可用」的唯一证据；实测不可用时回到 ONNX Runtime 升级评估，不得静默降级。

**来源数量与协议协商**

- 来源数量上限由 Server 配置持有（不在客户端可改范围内），容量档位由用户在本机配置。Server 不再用固定上限静默截断来源列表；客户端在心跳中声明来源，Server 按该上限校验，超限部分必须明确告知设备与接收端，而不是静默丢弃——静默丢弃会让超出部分既不报警也不可见，属于已知的不可诊断漏报风险。
- 保留 `sourceId` 字符集与长度约束，以及逐来源命令只接受最近心跳中存在来源的规则。
- 接收端的来源渲染以能力声明为准，不假设固定路数。

**共享策略**

- 规格级共享（三端）：功能基线与布局范式、协议字段、配置字段语义与默认值。
- 代码级共享（仅两个 Windows 端）：可共享核心以 `netstandard2.0` 类库形式抽取（来源协调、逐来源配置模型、告警链路、持久发件箱、协议类型），使 `net472` 的 WinForms 与 `net9` 的 WPF 引用同一份实现；Android 按同一契约独立实现。
- 不共享：UI 与采集实现。
- 推理后端不共享：WinForms 固定 CPU，WPF 使用 DirectML/CPU 双后端，两者的 ONNX Runtime 版本区间也不同；只共享协议与配置语义，不共享后端选择实现。
- 模型清单与输出解析器不共享：WinForms 保持 YOLOv5，WPF 与 Android 使用 YOLO26，逐来源的模型选择在各端按各自支持的集合实现，协议字段保持一致。
- 扩大共享层前先补测试：WinForms 当前没有任何自动化测试覆盖；Android 现有单测只覆盖消息序列化、后端状态判定与控制台状态，不覆盖采集、帧处理链路、服务与存储层。直接在这些层做多来源改造将没有回归基线。
- 两个 Windows 端保持单一 `settings.ini`，用前缀分节隔离，各端只写自己的节（2026-09-13 决定）。但仅靠分节不够：现有 `SettingsStore` 的 `Save()` 是整文件覆写，且按「仅 UI 线程调用」的假设无锁（`Utils/SettingsStore.cs` 注释），两端同时运行时会互相覆盖整个文件。该方案必须配「读—改—写 + 原子替换」语义：写入前重读磁盘、只替换自己的节、经临时文件原子替换。此外 WPF 的旧键迁移只执行一次，不能依赖迁移标记碰运气。

**前置技术验证（先做再扩）**

- WPF：容量提示改动后的行为回归，确认多路 CPU 可以运行、不再被准入拒绝，且性能不足以可见提示呈现而不是静默降级。
- WinForms：多来源加 CPU 多路的真实帧率与稳定性实测，这是容量模型是否成立的第一份硬证据，也是判断「维持 1.1.0」是否可接受的唯一依据。
- Android：真机可获取的相机数量与并发打开限制（Camera2 多逻辑相机需要 HAL 协商）、NNAPI 并发会话、单帧内存峰值。外接 USB 摄像头与采集卡本期只保留设计预留，不进入验证范围。

**Win7 虚拟机的验证工具链（2026-09-13 定）**

owner 自备 VMware Workstation Pro 与 Win7 系统安装，实施侧只需把验证工具定下来。目标是让 Win7 上的 WinForms 验证可重复、能出机器可读证据，而不是靠人工点界面。

| 环节 | 选型 | 理由 |
|---|---|---|
| 虚拟机 | VMware Workstation Pro，2–4 核 / 4GB / 动态磁盘 | owner 自行安装软件与系统 |
| 系统前置 | 六步补丁顺序：KB4490628 → KB4474419 → KB3140245 → TLS 注册表 → KB4019990 → .NET 4.7.2 | 前四步决定 WSS/TLS 链路，后两步是程序运行前提 |
| 前置核验 | 新增 `scripts/check-win7-prerequisites.ps1`，一次性检查补丁、.NET 版本与 TLS 注册表项 | 人工确认容易漏，脚本一次判定 |
| 被测产物 | `visionguard-build` 产出的 WinForms 与驻留 Release 目录 | 不在虚拟机内编译 |
| Server | 跑在宿主机上，走隔离通道 | 不与虚拟机争抢 CPU，避免污染帧率数据 |
| 测试窗口源 | 新增 net472 工具 `detector/windows-winforms-smoke/`，打开 N 个窗口各显示一张本地含人图片 | 不在 Win7 上用浏览器：Win7 可用的浏览器版本过旧、行为不可控；WPF 用浏览器是因为宿主机是 Win11 |
| 驱动与断言 | 同一个 smoke 工具驱动逐路启停，从 Server 侧读回每路报警与帧率，断言每路至少一次 `person` | 观察点放在 Server，避免为测试改被测端 |
| 证据 | JSON 报告与 WPF 报告同结构，便于横向比对 | 沿用现有 e2e 产物目录约定 |
| 人工项 | Win7 桌面 UI 目检、WSS/TLS 证书链确认、登录重启与断网恢复 | 脚本不能替代，必须单独报告 |

两条红线：

- **不为测试在被测端开后门**：断言所需字段（逐路状态、帧率、错误）本身就在功能基线之内，smoke 只消费已上报的数据。
- **smoke 工具自身必须能在 Win7 上跑**（net472），不能依赖 .NET 9，否则验证又要另一台现代机器。

分两阶段落地：

1. **单路阶段（现在就能做）**：验证 WinForms 当前版本在 Win7 上的启动、WSS/TLS 证书链、驻留远控、推理与退出清理。这一段补的是一直挂着的「Win7 实机验收待补」欠账，不依赖多来源改造。
2. **多路阶段（多来源实现后）**：窗口源数量与配置的来源数量一致，验证逐路启停隔离、多路 CPU 帧率与稳定性、容量提示可见性；四路保留为回归基线。

**已确认决策（2026-09-13）**

1. WinForms 模型格式锁定 YOLOv5 系列，不迁 YOLO26；owner 已实测更高的 ONNX Runtime 版本在 net472 上不可用。三端不共用模型清单与输出解析器。
2. 后端并发容量的默认档由用户自行配置，实现只提供可配置范围。
3. Android 多路采集先做内置相机；外接 USB 摄像头与采集卡本期只保留设计预留，不实现接口。
4. Android 只做宽屏布局，不支持窄屏，默认宽屏；相机竖装与横装属于部署方向，与 UI 宽窄解耦。
5. 验收夹具：Android 真机若只能取到一个相机，允许复制同一相机模拟多个来源以验证联通性，但该结果不能作为多相机并发能力的证据；发行形态仍按设备实际可获取的相机数量运行，不为凑路数引入虚拟来源。
6. WinForms 定位为 Windows 7 专属端，Windows 10 及以上的 Windows 检测由 WPF 承担；WinForms 因此撤销硬件加速规划，固定 CPU 并维持现有 ONNX Runtime 1.1.0。
7. CPU 多路保留：Win7 上以纯 CPU 运行多来源是可接受的降级，不接受为规避性能问题而退回单路。
8. 超容量时允许运行、只提示性能不足：不拒绝启动、不自动减路、不自动降帧；红线是不静默降级，且性能不足与故障必须分开表达。
9. 来源是固定槽位、只改数量上限，不提供运行时的增删操作：因此不需要为动态增删重构配置存储。但每个槽位的身份与配置仍需持久化（稳定 `sourceId`、改名不改身份），这与「不做增删」并不冲突。
10. 接收端一并纳入统一范围，同步来源模型与逐来源通知偏好；接收端自身保持手机竖屏形态。
11. Android 强制横屏锁定，只做一套宽屏布局。
12. ONNX Runtime 维持 1.1.0，不升级推理运行时；多路 CPU 实测不可用时回到本条重新评估，而不是降路数或降帧率。
13. smoke 验收入口改为按当前配置的来源数量取证，不再写死四个独立窗口；四路保留为回归基线。
14. 来源数量上限由 Server 配置持有，容量档位由用户在本机配置。
15. 两个 Windows 端保持单一 `settings.ini`，用前缀分节隔离。
16. 离线补发时**合并的只是通知，不是事件**：离线期间的全部报警都要补发并进入接收端历史记录，**实时通知只对每路最新一条触发**，因此重连不刷屏、历史也不丢事件。「每路只发最新一条」指的是通知，不是数据丢弃。需要新增的能力是接收端识别补发批次并只对最新一条出通知；补发时截图与元数据的上行量控制属实现细节，落地时按带宽与存储成本决定。
17. 接收端不决定来源设置：「采哪个窗口 / 哪个摄像头」只在检测端本地配置。接收端远程可调的范围限于通用参数（模型、类别、阈值、检测频率、报警冷却、启停），不含采集目标。

**仍待确认**

无。截至 2026-09-13，本节列出的边界项已全部确认；后续新出现的分歧继续记入本节。

## 9. 平台与硬件演进路线

本节保留平台和硬件方向的阶段 0–6，描述能力依赖及验收条件；阶段编号不等于版本号。当前执行优先级见第 11 节，已确认的 5.0 以内视觉更新见第 8 节。

阶段 1 的现有端可靠性工作与第 8 节共享回归证据；阶段 2 复用第 8 节形成的设备/来源身份、能力声明及控制请求关联，再扩展账号租户、可靠投递与 Web 管理。硬件场景选择约束定制硬件和多传感器开发，不阻塞已确认的视觉端更新。

### 阶段 0：产品、市场与数据政策闸门

目标：在大规模重构前确定免费/付费边界、中国大陆首发要求、首个硬件使用场景和失败代价。

交付：

- 固化免费 Visual Detector 层与付费 Edge Detector 层的产品边界；
- 为付费版硬件探测器选择一个首发使用场景，例如无人值守空间入侵、仓库门禁或人员危险接近；
- 以漏报风险为最高优先级定义召回率、故障覆盖、报警延迟和最大无感失联时间；允许一定误报，但必须定义误报上限、静音和复盘机制；
- 建立真实环境样本和事件回放集；
- 明确各类数据的传输、保存、查看、导出、删除、注销和备份过期政策；
- 明确中国大陆首发所需的个人信息告知、同意、最小必要、安全保护和事件处置清单。
- 完成依赖库、模型、数据集、素材和构建产物的许可证清单，确认商业分发兼容性并生成必要归属声明。

闸门：没有明确场景、样本和量化指标时，不进入定制硬件和大规模多传感器开发。

### 阶段 1：4.x 商业可靠性基线

目标：在新架构研发期间保持现有产品可用，并提炼统一协议所需证据。

交付：

- 记录当前报警生成、截图、WS 发送、Server 持久化和 Android 展示的端到端语义；
- 为事件 ID、重试、重复报警、截图缺失、设备离线报警、恢复事件和网络恢复建立确定性测试；
- 形成故障码、脱敏日志和基本运行指标；
- 明确未来 Web 控制台所需的设备状态、配置版本和审计字段，但不在 4.x 内复制一套临时管理协议；
- 保持版本、模型下载、更新与现有发布链路稳定。

闸门：关键报警链路能够自动复现，修改前后可机器判定，不依赖只看 UI 猜结果。

### 阶段 2：统一身份、事件与可靠投递

目标：建立所有未来端都能使用的 Server 中心商业网络底座，不引入 P2P 多路径复杂度。

交付：

- 账号、租户、设备身份和能力声明；
- 版本化 Event Protocol、公网加密传输和跨平台测试向量；
- 探测端持久化 outbox、接收端幂等 inbox、逐接收设备 ACK；
- HTTPS/WSS `443` 可靠中继、权威事件存储和短期离线转发；
- Server 基于心跳生成设备离线报警和恢复事件，并纳入标准事件、ACK、重试和审计；
- Android 系统推送唤醒与前台 WSS 协同；
- Win7 / WinForms 继续以 TLS 1.2 可靠兜底链路运行；
- 提供最小 Server Web 控制台：场地、设备列表、设备详情、健康状态、单设备配置和审计记录。

闸门：设备失联能在策略阈值内生成一次离线报警，恢复时生成关联恢复事件；接收端离线、Server 重启和重复投递情况下不丢报警、不重复提示；跨租户访问自动化测试全部拒绝；控制台不能越权查看或修改其他租户设备，并能区分配置“已下发”“待设备接收”“已生效”和“失败”。

### 阶段 3：Server 高可用与多通道报警

目标：在统一 Server 路径上提升可用性、送达率和可观察性，使设备离线、Receiver 离线和 Server 自身异常都能被不同层次感知。

交付：

- WSS/HTTPS 连接状态机、退避重连、网络切换、outbox 补发和可观察状态；
- Server 离线判定、防抖、单次失联去重、恢复关联和逐 Receiver 送达状态；
- Android 前台 WSS 与适合中国大陆终端的系统推送协同；
- Server 带宽、连接数、队列积压、存储、限流、配额和滥用防护；
- 独立外部健康监测、备份恢复演练和必要的服务冗余，防止业务 Server 自监控失效；
- Win7 SP1 x64 Visual Detector 的 TLS 1.2、长连接、休眠恢复和断线补发验证，以及 Android 真机、家庭网络、移动网络和企业网络测试矩阵。

闸门：拔网线、断电、杀进程和现场路由故障都能在规定时间内形成可追踪的设备离线报警；恢复后不重复旧报警且能记录失联时长；业务 Server 故障能由独立监控通道发现；容量压测达到目标设备数。Win7 兼容端必须通过握手、长连接、休眠恢复、退出清理和发行目录检查。

### 阶段 4：Detector SDK 与开发板原型

目标：把产品核心从视觉客户端提升为可扩展探测平台。

交付：

- Sensor Adapter、Inference Engine、Fusion Engine、Event Engine、Outbox、Transport Manager 和 OTA Manager 边界；
- Linux ARM64 Edge Detector 原型；
- 摄像头 + 毫米波/PIR + 门磁的最小组合；
- Ethernet 独立联网、Wi-Fi 可选联网，以及 Detector + Gateway 双模式；
- 统一 Observation、AlertEvent、设备健康和能力清单；
- 传感器断开、异常值、时间漂移、推理超时和降级策略；
- Management Agent 与 Web 控制台联调；
- 远程配置、模型更新、日志导出和失败回滚。

闸门：72 小时稳定运行；断网和异常断电后事件不损坏；不依赖现场 PC 或专用中控即可完成远程报警；两传感器融合相对单视觉优先改善漏报指标，误报处于可管理上限内；传感器、推理、进程或网络故障不会静默形成探测盲区；控制台能准确显示能力、配置、健康、Server 连接和 outbox 状态。

### 阶段 5：首个垂直场景试点

目标：证明客户价值，而不是继续堆积通用能力。

交付：

- 小规模真实场地部署；
- 安装、校准、网络诊断和设备替换流程；
- 误报/漏报复盘与带版本的数据闭环；
- 多接收人、值班和事件处置记录；
- Web 控制台的传感器拓扑、校准、融合规则、模型与 OTA 进入试点；
- 存储、带宽、推送和人工支持成本测量。

闸门：达到阶段 0 定义的业务指标，并证明单设备交付与持续服务成本可接受。

### 阶段 6：设备规模化与商业运营

目标：在试点成立后建设批量交付能力。

交付：

- 工业 SOM 或定制载板评估；
- 工厂烧录、设备证书、批量注册和密钥轮换；
- A/B OTA、灰度、回滚和固件物料清单；
- 组织、成员、角色、审计、配额和商业套餐；
- 免费版纯软件视觉方案的云资源配额、付费版硬件探测器的服务权益和续费策略；
- Web 控制台的场地模板、批量配置、灰度升级、审批和运营指标；
- 多区域服务接入、容量规划、备份恢复和服务等级指标。

闸门：批次可追溯、升级失败可恢复、租户隔离可审计、容量与成本可以按设备数量预测。

## 10. 暂不进入主线的事项

- 重新引入 P2P、ICE、STUN、TURN 或浏览器到设备直连，除非未来有经过成本与场景验证、Server 转发无法满足的明确需求；
- 在阶段 0 场景未确定前，同时支持大量传感器；
- 第一代原型即自研完整主板；
- 第一代原型同时开发独立中控硬件；
- 让开发板探测器依赖现场 PC 或中控才能联网报警；
- 为追求 Win7 兼容而限制 Server、Web 控制台、Android、WPF、Linux Edge Detector 或未来硬件技术栈；
- 让每种传感器直接定义 Server API 和接收端页面；
- 把无限制远程 Shell 当成 Web 控制台的日常管理能力；
- 在缺少真实环境数据时用局域网演示代替商业可用性结论；
- 把未来规划写进 CHANGELOG 或描述成当前已交付能力。
