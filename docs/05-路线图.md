# 路线图

负责：后续方向、顺序、预计工程量与启动条件。不负责：本次任务进度、当前模块实现或验证证据。更新时机：owner 确认新的方向、范围或顺序时。

Web 是唯一控制台；Android 相机与通知节点继续支持手机和平板。Android 控制台已淘汰，源码、维护和服务接入已移除，历史发行资料保留。

## 后续开发

以下方向按 owner 确认的顺序编号；第 1、2 项已随 [0.6.11](releases/v0.6.11.md) 发布，第 3 项继续定位，后续从该项推进。外部摄像头接入安排在原生 Android 推理节点之后；硬件原型、Android 推理节点、外部摄像头依次为第 4、5、6 项。当前开发、修复与维护事项见[任务清单](06-任务清单.md)，证据与未覆盖项见[验证记录](90-验证记录.md)。真实使用问题由 owner 主动反馈后登记处理，不单列真实验收方向。工程量按当前实现粗估，需结合启动条件与依赖安排实际顺序；设备兼容性与局域网方案明确后再调整。

| 顺序 | 规划内容 | 预计工程量与原因 | 范围、启动条件与依赖 |
|---|---|---|---|
| 1 | 将“视觉节点”改名为“视觉推理节点” | 小：主要为显示文案、默认名称、应用元数据及相关文档同步 | Windows 应用与后续 Android 推理应用统一使用新显示名；工程目录、包名、协议中的 `visual` 等技术标识不随显示名机械替换。实施前仍以[当前命名规范](15-命名规范.md)为准 |
| 2 | Web 控制台刷新保持登录，默认超过 24 小时重新登录 | 中：涉及浏览器会话保存 / 恢复、服务端有效期校验与自动续期边界 | 有效期内刷新恢复会话，不切回登录界面；默认从本次登录成功起计 24 小时，到期重新登录，刷新或自动续期不能无限延长。退出、撤销与账号失效及时清除会话；这是登录会话保持，与现有账号密码记忆分开处理 |
| 3 | 深度验证并修复通知节点锁屏后告警接收问题 | 较大，修复量待根因确认：涉及长时间真机验证、后台运行、连接恢复与完整报警链 | 以小米 15 为目标，先确认真实锁屏且不受蓝牙自动解锁影响；通过真实服务器独立测试通道与实际组件，覆盖短时 / 较长锁屏、期间多次报警、断连重连及解锁后的表现。分别取证后台服务存活、服务转发、节点收件持久化与声音播放，记录漏收时间、日志及是否补收，定位后修复并回归。解锁按[已授权的环境变量入口](60-构建验证与发布.md#设备验收操作)读取，不记录密码；设备测试全程静音，以收件回执、持久化与队列等证据验证送达；静音结果不证明可听声音 |
| 4 | 使用现成传感器、开发板和电池制作硬件原型 | 较大：涉及器件组合、现场检测、供电与续航验证 | 室外固定，监测人或骑行者经过；首轮预算 500 元以内，先用 Wi-Fi / 手机热点。采购草案见下方；联网和告警现场验证后确定最终组合，验证 2–8 米慢走和快速骑行、供电与续航，不提前设计 PCB |
| 5 | 使用原生 Android 复刻当前 Windows 视觉推理节点 | 大：新增完整推理端，覆盖原生界面、模型运行、多来源管理及告警链 | 对齐当前 Windows 的界面结构、来源管理、模型 / 检测参数、遮罩、报警、状态上报与控制台远控，适配手机和平板；Windows 专属窗口采集、选区及驻留机制按 Android 能力另行评估。具体工程、安装身份及与现有相机推流节点的关系在实施前确定；推理性能、发热与持续运行须真机验证 |
| 6 | 视觉推理节点接入 USB 有线摄像头或夜视摄像头，Android 支持 OTG 输入；按需扩展采集卡等视频输入 | 较大：增加采集来源，涉及 Windows / Android 两端的设备接入、格式和断连处理 | Windows 直接将 USB 摄像头作为推理输入；Android 视觉推理节点通过 OTG 接入外部摄像头，复用来源配置、遮罩、推理与报警链。按真实设备核对驱动、格式、供电及拔插恢复；Android 部分依赖第 5 项原生推理节点；采集卡及其他视频设备按真实需要逐类接入现有节点职责 |
| 7 | 传感器融合、结构与电路板优化 | 很大，待细化：涉及多传感器协作及结构、电路设计与迭代 | 有硬件原型、设备性能与使用频率证据后再细化；Android 手机 / 平板推理由原生 Android 项统一覆盖 |
| 8 | 所有组件支持局域网与公网两种模式 | 预计最大，方案待定：涉及全组件连接、服务承载、认证、媒体、控制与通知链路 | 覆盖视觉推理、相机推流、通知节点、Web 控制台及统一服务。可能需要一个终端充当局域网服务端；由哪类终端承载、如何接入与切换，到启动此项时再规划，不提前确定实现。公网继续遵循统一服务转发边界 |

实施进度以任务清单为准。原 Vigil 仍独立维护；架构职责见[当前架构](10-当前架构.md)。

选型与到货后判断：

- [官方雷达资料](https://wiki.dfrobot.com.cn/sku_sen0609_c4001_mmwave_presence_sensor_25m)给出的测距范围为 1.2–25 米、测速范围为 0.1–10m/s（约 0.36–36km/h），支持调整距离、灵敏度与触发延迟。这是器件标称能力，不是室外慢走 / 骑行检出率；存在与测速属于不同工作模式，现场分别比较，不照抄例程的 1 秒触发延迟。
- 下单定位是经过检测试验件，不能据此承诺只识别人或骑行者；单雷达缺少已验证的人 / 车 / 动物分类。风吹草木、车辆、雨水与安装晃动需单独测误报；2 / 4 / 6 / 8 米分别覆盖慢走、靠近 / 远离、横向经过和骑行。横向测速可能低估真实速度，不能把测速值直接当骑行速度；不以长延迟或要求两个传感器同时触发掩盖漏报。
- [开发板资料](https://wiki.dfrobot.com/dfr0654/)确认支持 2.4GHz Wi-Fi、USB 5V 供电及 3.3V 电源输出；热点启用 2.4GHz。雷达优先按厂家支持的 3.3V 供电接入，装配时核对供电与 UART 电平；先用电脑 USB 验证，再切充电宝。联网及 TLS / WebSocket 固件仍需开发，购买器件不表示已能登录现有服务。
- 原型先放在遮雨遮阳处，装机开孔后重新检查密封，盒子等级不等于整机防护认证。保留塑料雷达窗口并检查积水 / 水膜影响；若树木误报或骑行漏报无法通过朝向和距离配置控制，停在检测选型，不先堆电池或制作外壳定型。
- 连续监测时保持雷达工作，先测整机平均功率与告警期间峰值；不拿 ESP32 深睡电流推算联网运行续航。续航按实测充电宝可用 Wh ÷ 整机平均 W 计算，尚未承诺运行天数；接入后分别记录节点上报、服务转发和通知收件，不能用连接成功代替送达。
